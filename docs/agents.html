7Agent Design, Frameworks & Tool Use

An agent is an LLM in a loop with tools and state. Most production failures come from the loop, the tools or the state, not from the model.

7.1

Building an agent where a deterministic workflow would do

ReliabilityCost

Problem statement

An "autonomous onboarding agent" decides at runtime which steps to run to provision a new employee: create the account, assign licenses, order a laptop, enrol in training. It occasionally skips the security training step, and nobody can explain why.

The anti-pattern

A known, fixed business process is handed to an LLM to orchestrate freely, because "agentic" is the goal rather than the means.

Why the current design fails

  • Non-determinism where you need guarantees. Mandatory steps become probabilistic.
  • Harder to test and audit. Every run can take a different path.
  • Higher cost and latency. Each step adds a reasoning call that a workflow engine does for free.

Recommended solution

Apply an autonomy spectrum and pick the least autonomous design that solves the problem:

Level Pattern Use when
0 Single LLM call One transformation
1 Fixed workflow / prompt chain Known steps, LLM for judgment inside steps
2 Router + workflows A few known paths, selected by input
3 Agent with constrained tools Path genuinely unknown in advance; open-ended tasks
4 Multi-agent Clear separation of expertise or context, proven necessary

Implement level 1–2 in a workflow engine (Step Functions, Temporal, Logic Apps, Cloud Workflows, LangGraph with fixed edges), and reserve agent loops for steps that genuinely need exploration.

Why it succeeds

Mandatory steps are guaranteed by code. LLM judgment is applied where it adds value, such as reading documents or drafting emails. Workflows are testable, observable and cheap. You can still promote a step to agentic later, with evidence.

Reference implementation

# LangGraph-style: fixed edges for the process, LLM nodes only for judgment
g = StateGraph(OnboardingState)
g.add_node("create_account",  create_account)          # deterministic
g.add_node("assign_licenses", assign_licenses)         # deterministic
g.add_node("pick_equipment",  llm_pick_equipment)      # LLM judgment from role description
g.add_node("security_training", enroll_training)       # mandatory, cannot be skipped
g.add_edge(START, "create_account")
g.add_edge("create_account", "assign_licenses")
g.add_edge("assign_licenses", "pick_equipment")
g.add_edge("pick_equipment", "security_training")
g.add_edge("security_training", END)
Key takeaway

Start with the least autonomy that solves the problem. Agents are for unknown paths, not for running a process you already know.

7.2

Too many tools with vague descriptions

QualityCost

Problem statement

An IT-operations agent is given 120 tools, auto-generated from internal API specs, with descriptions like "Gets data". It routinely calls the wrong tool, passes malformed parameters, and its prompt is 30K tokens before the user says anything.

The anti-pattern

Every available API is exposed as a tool, with names and descriptions taken straight from the spec, all loaded into context on every turn.

Why the current design fails

  • Selection accuracy drops as the tool count grows and descriptions overlap.
  • Context bloat. Tool schemas consume a large share of tokens on every call.
  • Ambiguous parameters lead to invalid or dangerous calls.

Recommended solution

Design tools for a model, not a programmer:

  • Curate: group low-level endpoints into task-level tools (restart_service(service, env) rather than five raw calls).
  • Write descriptions that say when to use the tool, when not to, parameter formats, and an example.
  • Use strict JSON schemas with enums and patterns.
  • Load tools on demand using tool search, a router, or skill/toolbox grouping, so only relevant tools are in context.
  • Evaluate tool selection accuracy as its own metric.

Why it succeeds

Fewer, clearer choices raise selection accuracy. Strict schemas block malformed calls before they reach systems. On-demand loading recovers context budget for the actual task. Measuring selection makes tool design an iterative, data-driven activity.

Reference implementation

@tool(
  name="restart_service",
  description=("Restart ONE application service in a given environment. Use after diagnosing a hung "
               "process. Do NOT use for databases (use failover_db). Example: "
               "restart_service(service='checkout-api', env='staging')"),
  schema={"service": {"type": "string", "pattern": "^[a-z0-9-]+$"},
          "env": {"type": "string", "enum": ["dev", "staging", "prod"]}},
)
def restart_service(service, env): ...

relevant = tool_index.search(task_description, k=8)       # on-demand tool loading
agent.run(task, tools=relevant)
Key takeaway

Tools are a model-facing API. Curate them, describe them like documentation, constrain their schemas, and load them on demand.

7.3

Tools with no input validation, idempotency or blast-radius limits

SecurityReliability

Problem statement

A finance-ops agent retries a timed-out issue_refund call. The first call had in fact succeeded, so the customer is refunded twice. In another run, a hallucinated amount of $45,000 instead of $450 goes through.

The anti-pattern

Tools are thin wrappers that pass model-generated arguments straight to production APIs. No validation, no idempotency keys, no limits.

Why the current design fails

  • Model arguments are untrusted input, just like user input, and can be wrong, hallucinated or injected.
  • Retries duplicate side effects without idempotency.
  • Unbounded blast radius. One bad call can move money, delete data or email thousands of customers.

Recommended solution

Wrap side-effecting tools in a safe-action layer:

  • Validate schema and business rules (amount ≤ original charge, account exists, status allows refund).
  • Enforce policy limits: per-call caps, per-session totals, and an approval threshold above which a human must approve.
  • Use idempotency keys derived from intent (refund:{order_id}:{amount}) so retries are safe.
  • Prefer reversible operations (draft, schedule, soft-delete) and give the agent a dry-run mode.
  • Log every action with the agent session, reasoning summary and approver.

Why it succeeds

Validation catches hallucinated or injected arguments before they cause harm, idempotency makes retries safe, and limits bound the worst case. Together these turn agent actions from "hope it's right" into controlled transactions that risk and audit teams can sign off.

Reference implementation

@tool
def issue_refund(order_id: str, amount: Decimal, reason: str, ctx: AgentCtx):
    order = orders.get(order_id) or reject("unknown order")
    if amount > order.captured_amount - order.refunded: reject("exceeds refundable amount")
    if ctx.session_total("refund") + amount > SESSION_CAP: reject("session cap reached")
    if amount > APPROVAL_THRESHOLD:
        return approvals.request(action="refund", order_id=order_id, amount=amount, reason=reason,
                                 requested_by=ctx.agent_id)          # human-in-the-loop
    key = f"refund:{order_id}:{amount}"
    return payments.refund(order_id, amount, idempotency_key=key)     # exactly-once
Key takeaway

Treat every model-generated argument as untrusted input. Validate it, bound it, make it idempotent, and require approval above a risk threshold.

7.4

Unbounded loops with no step, time or cost budget

CostReliability

Problem statement

A research agent gets stuck alternating between two searches that return nothing new. It runs for six hours and makes 1,900 model calls before someone notices the cost alert.

The anti-pattern

while not done: agent.step(). Termination is left to the model deciding it's finished. No caps, no progress detection.

Why the current design fails

  • Agents can loop on repeated failures, oscillate between strategies, or chase ever-growing subtasks.
  • Costs grow without bound, and context grows each turn, so later steps cost more.
  • No graceful exit. When it does stop, there's no partial result.

Recommended solution

Wrap every agent run in a budget envelope:

  • Hard caps on steps, tokens, wall-clock time and dollar cost, set per task type.
  • Stall detection: identical tool calls repeated, no new information in N steps, or error loops.
  • Escalation on breach: return the best partial result with a summary of what was tried, and hand off to a human or queue.
  • Emit budget usage as trace attributes and alert on outliers.

Why it succeeds

Worst-case cost per run becomes bounded and predictable, which finance needs before approving agents at scale. Stall detection catches the common loop patterns early. Partial results mean the user gets value even when the agent can't finish.

Reference implementation

@dataclass
class Budget: steps=25; tokens=200_000; usd=2.00; seconds=300

def run_agent(task, budget=Budget()):
    state, seen, t0 = init(task), Counter(), time()
    for step in range(budget.steps):
        action = agent.decide(state)
        sig = (action.tool, frozenset(action.args.items()))
        seen[sig] += 1
        if seen[sig] > 2:                         return escalate(state, "repeating action")
        if state.usd > budget.usd or state.tokens > budget.tokens or time() - t0 > budget.seconds:
            return escalate(state, "budget exhausted")
        if action.final:                          return action.answer
        state = observe(state, execute(action))
    return escalate(state, "step limit")
Key takeaway

An agent without a budget is an open-ended cost commitment. Cap steps, tokens, time and money, detect stalls, and exit gracefully.

7.5

No state persistence or checkpointing

Reliability

Problem statement

A contract-review agent works through a 200-page agreement for 25 minutes. A container restart at minute 22 loses everything, and the job starts again from the beginning, including the expensive steps.

The anti-pattern

Agent state lives in process memory. Long-running tasks have no checkpoints, can't be paused for human input, and can't resume after failure.

Why the current design fails

  • Lost work and money on any crash, deploy or timeout.
  • No human-in-the-loop pauses. Waiting hours for an approval is impossible if state is in RAM.
  • No replay. Debugging needs the exact sequence of states, which is gone.

Recommended solution

Use durable execution for agents:

  • Persist state after every step (a LangGraph checkpointer on Postgres or Redis, a Temporal workflow, or managed agent runtimes with session state such as Bedrock AgentCore, Foundry Agent Service or Vertex Agent Engine).
  • Model human approvals as interrupts that persist state and resume on callback.
  • Make steps idempotent so replay after a crash is safe.
  • Keep the checkpoint history for debugging and audit ("time-travel" through states).

Why it succeeds

Crashes and deploys cost one step, not the whole run. Human approvals can take minutes or days without holding resources. The checkpoint trail becomes the debugging and audit record that regulators and engineers both need.

Reference implementation

from langgraph.checkpoint.postgres import PostgresSaver

graph = builder.compile(checkpointer=PostgresSaver.from_conn_string(DB_URL),
                        interrupt_before=["send_to_counterparty"])     # human approval gate
cfg = {"configurable": {"thread_id": f"contract-{contract_id}"}}

graph.invoke({"doc": contract}, cfg)          # runs until the interrupt, state persisted
# ... hours later, after legal approves in the UI:
graph.update_state(cfg, {"approved_by": "j.smith"})
graph.invoke(None, cfg)                       # resumes from the last checkpoint
Key takeaway

Long-running agents are workflows. Give them durable state, interrupts for humans, and replayable history.

Follow-up to expect

7.6

Port-in processing built as a free-roaming agent

ReliabilityTelco

Problem statement

A carrier builds a ReAct agent to process mobile number port-in requests: validate the account number and PIN from the losing carrier, check the number is portable, submit the port request, schedule activation and notify the customer. The steps never change, yet the agent takes 9-14 LLM calls per request, sometimes skips the portability check, and 1 in 10 ports fails or is delayed.

The anti-pattern

A fully autonomous ReAct loop for a fixed process.

Think of it this way: Hiring a creative chef to run a vending machine. The job is the same every time, and creativity only adds ways to get it wrong.

Why the current design fails

Mechanism: Each LLM decision adds latency, cost, and a chance of error. Errors compound: 95% reliability per step over 10 steps gives about 60% success.

  • Every step is an LLM decision, so each one adds latency, cost and a chance of error.
  • Errors compound; 95% reliability per step over 10 steps gives about 60% end-to-end success.
  • The model sometimes reorders or skips steps that the process requires.

Root cause: An autonomous loop was used for a fixed, well-understood business process.

Where it breaks: Orchestration design.

Recommended solution

  1. Model the port-in as a deterministic workflow (state machine or durable workflow engine) with explicit steps and retries.
  2. Use the LLM only where judgement is needed, such as interpreting a free-text rejection reason from the losing carrier or drafting the customer message.
  3. Validate each step's output in code before moving on.

Why it succeeds

Trade-off to manage: Workflows are less flexible for unexpected cases; add an "exception" branch that hands off to an agent or a human.

How you prove it worked:

  • Step-completion and skip rates per run, and port success rate by version.

Same pattern elsewhere: FinTech: account-opening checks (ID verification, sanctions screening, credit pull, account creation) run as an agent and occasionally skip sanctions screening.

Reference implementation

port_in = StateMachine(steps=[
    Step("validate_request", validate_port_request),          # deterministic
    Step("submit_to_npac", submit_port, retries=3),
    Step("await_losing_carrier", wait_for_response, timeout="48h"),
    Step("interpret_rejection", llm_interpret_rejection, when=lambda s: s.rejected),  # LLM judgement
    Step("draft_customer_msg", llm_draft_message),
    Step("activate", activate_number),
])
for step in port_in:
    out = step.run(state)
    step.schema.model_validate(out)                            # validate before moving on
Key takeaway

Autonomy is a cost, so spend it only where the path is unknown.

7.7

Reconciliation agent loops all night on one break

ReliabilityCostFinTech

Problem statement

A payments company runs a reconciliation agent that investigates unmatched transactions between the ledger and bank statements. One break involves a transaction split across two settlement files. The agent keeps re-querying the same files with slightly different filters for 6 hours, making 2,400 LLM calls and costing $310, then produces nothing.

The anti-pattern

while not done: with no ceiling.

Think of it this way: A dishwasher with no timer that keeps rinsing the same plate because a spot won't come off.

Why the current design fails

Mechanism: Models can repeat the same failing tool call or never decide they are done.

  • The loop has no ceiling on steps, tokens, time or money.
  • The model doesn't recognise that it is repeating itself.
  • No partial result or escalation path exists.

Root cause: An unbounded agent loop with no circuit breaker.

Where it breaks: Agent runtime.

Recommended solution

  1. Cap steps, tokens, wall-clock time and dollars per run, with per-tenant budgets.
  2. Detect loops (same tool and arguments, or no new information after N steps) and stop.
  3. On a cap, return a partial result with what was tried, and route to a human queue.

Why it succeeds

Trade-off to manage: Caps can stop legitimately long investigations; set them per task type and allow a human to extend.

How you prove it worked:

  • Alerts on steps per run, run duration and cost outliers.

Same pattern elsewhere: Telco: a network-diagnosis agent keeps re-running the same ping and traceroute on a dead site overnight.

Reference implementation

for step in range(MAX_STEPS):                       # hard ceiling
    if budget.spent_usd > MAX_USD or clock() > deadline:
        return escalate(state, reason="budget")
    call = agent.next_action(state)
    sig = (call.tool, canonical_json(call.args))
    if seen[sig] >= 2:                              # loop detector
        return escalate(state, reason="repeating")
    seen[sig] += 1
    state = state.with_result(run_tool(call))
return escalate(state, reason="max_steps")
Key takeaway

Every loop needs a circuit breaker.

7.8

Care agent exposed to 60 BSS APIs

ReliabilityCostTelco

Problem statement

A carrier gives its care agent every BSS API as a tool: 60 tools across CRM, billing, ordering, inventory, payments and loyalty. Tool definitions take 22k tokens per call. The agent picks the wrong tool 25% of the time, for example calling get_invoice instead of get_bill_explanation, or update_product instead of add_addon.

The anti-pattern

Exposing every API as a tool to a single agent.

Think of it this way: Giving a new hire a 60-button remote control on day one and asking them to change the channel.

Why the current design fails

Mechanism: Tool definitions consume context, and similar tools confuse selection.

  • Similar tools confuse selection.
  • Tool definitions consume context and money on every call.
  • Accuracy degrades as the toolbox grows.

Root cause: APIs were exposed one-to-one as tools, with no grouping or routing.

Where it breaks: Tool design and agent architecture.

Recommended solution

  1. Route by intent first (billing, orders, tech support), then load only that domain's tools.
  2. Design fewer task-shaped tools that wrap several APIs, instead of one tool per endpoint.
  3. Keep about 10-20 tools visible at a time; use tool search for the long tail.

Why it succeeds

Trade-off to manage: Routing adds a classification step and can misroute; keep a fallback that loads more tools.

How you prove it worked:

  • Tool-selection accuracy on a labelled eval set; tool-call error rates.

Same pattern elsewhere: FinTech: a banking agent with 45 core-banking tools confuses transfer_internal with transfer_external.

Reference implementation

DOMAIN_TOOLS = {
    "billing":  [explain_bill, apply_payment_arrangement, get_balance],
    "orders":   [track_order, change_delivery],
    "tech":     [run_line_test, check_outage, reset_router],
}

def tools_for(msg):
    intent = router.classify(msg)                              # route first
    tools = DOMAIN_TOOLS[intent.domain]
    if len(tools) < 10:
        tools += tool_search(msg, k=5)                         # long tail on demand
    return tools[:20]
Key takeaway

Tool choice degrades as the toolbox grows.

7.9

Payment tool amount in cents read as dollars

ReliabilityFinTechCritical

Problem statement

A small-business banking agent can schedule supplier payments. The tool parameter is amount: integer, documented only as "payment amount". The API expects minor units (cents). A user asks to pay an invoice of $4,500. The agent passes 4500, and $45.00 is sent. Another time it passes 450000 for $45, sending $4,500, which is only caught by an approval limit.

The anti-pattern

One-line tool descriptions and free-text parameters.

Think of it this way: A form field labelled "amount" with no currency or units. Half the people write dollars, half write cents.

Why the current design fails

Mechanism: The tool description is the model's only documentation. Ambiguity becomes wrong calls.

  • The tool description doesn't state units, format or limits.
  • The model guesses the convention, inconsistently.
  • The API accepts any positive integer.

Root cause: Tool schemas were written like internal API signatures, not like documentation for a new user.

Where it breaks: Tool definition and validation.

Recommended solution

  1. Use explicit, typed parameters (amount as a decimal string plus an ISO 4217 currency code) and convert to minor units inside the tool.
  2. Write the description as for a new hire (when to use it, examples, units, limits, what not to do).
  3. Validate inside the tool (amount equals the invoice amount on file, within limits) and return an actionable error.
  4. Echo back a human-readable confirmation for approval before execution.

Why it succeeds

Trade-off to manage: Stricter schemas reject some legitimate free-form requests; respond with a clarifying question instead.

How you prove it worked:

  • Mismatch alerts between payment amount and invoice amount; distribution of amounts per payee.

Same pattern elsewhere: Telco: a data-add-on tool takes size as an integer and the agent mixes MB and GB, selling 1 MB packs instead of 1 GB.

Reference implementation

class SchedulePayment(BaseModel):
    """Schedule a supplier payment. Amount is in MAJOR units (e.g. "4500.00" = $4,500).
    Use only after the user confirmed payee and amount. Never infer the amount."""
    payee_id: str
    amount: Decimal = Field(gt=0, max_digits=12, decimal_places=2)
    currency: Literal["USD", "EUR", "GBP"]
    invoice_id: str          # tool checks amount == invoice.amount_due
Key takeaway

Tool descriptions are prompts, so engineer them.

7.10

Care agent issues a $400 goodwill credit on its own

ReliabilityTelco

Problem statement

A carrier's care agent has a tool to apply bill credits. A frustrated customer claims three outages and demands compensation. The agent, aiming to be helpful, applies a $400 credit. Similar patterns spread on a forum, and goodwill credits triple in a month.

The anti-pattern

Write and irreversible tools called autonomously.

Think of it this way: Giving a new receptionist the company credit card with no spending limit and asking them to keep customers happy.

Why the current design fails

Mechanism: The model can be wrong or manipulated, and some actions can't be undone.

  • A write tool with financial impact runs autonomously.
  • The limit is in the prompt ("don't give more than $50"), which the model can be talked out of.
  • No check against actual outage records.

Root cause: Business limits and approvals are enforced by instructions instead of by the tool and a human gate.

Where it breaks: Tool layer and approval workflow.

Recommended solution

  1. Classify tools by risk; credits above a small limit require human approval with the conversation and evidence attached.
  2. Enforce the limit inside the tool and the billing system, not in the prompt.
  3. Check outage claims against network incident records (OSS) before offering anything.

Why it succeeds

Trade-off to manage: Approvals slow resolution; keep small credits automatic and fast.

How you prove it worked:

  • Credits per agent version, per customer and per reason; spike alerts.

Same pattern elsewhere: FinTech: a bank agent reverses a $300 overdraft fee for every customer who says they are a student.

Reference implementation

@tool(risk="write")
def issue_goodwill_credit(account_id: str, amount: Decimal, reason: str, ctx: Session):
    outage = oss.incidents.affecting(account_id, window=days(7))   # verify the claim first
    if reason == "outage" and not outage:
        return {"status": "REFUSED", "why": "no outage recorded for this service"}
    if amount > AUTO_CREDIT_LIMIT:                                  # enforced in the tool, not the prompt
        return approvals.request(account_id, amount, evidence=[ctx.transcript_id, outage.id if outage else None])
    return billing.credit(account_id, amount, idempotency_key=f"gw:{ctx.case_id}")
Key takeaway

Put the guardrail in the tool, not the prompt.

7.11

Retry after timeout sends a wire twice

ReliabilityLatencyFinTechCritical

Problem statement

A treasury agent initiates a $250,000 vendor wire. The payment gateway processes it but the response times out. The framework's automatic retry calls initiate_wire again, and a second wire is sent. Recovering it takes nine days and a recall request through the correspondent bank.

The anti-pattern

Retrying side-effecting calls with no idempotency key.

Think of it this way: Pressing the lift button again because the light was slow. For lifts it's harmless. For money, it orders a second lift.

Why the current design fails

Mechanism: The first call succeeded but the response was lost.

  • The first call succeeded, but the response was lost.
  • Generic retry logic treats all tools as safe to repeat.
  • The API has no idempotency key.

Root cause: Side-effecting tool calls are retried without idempotency.

Where it breaks: Tool layer and payment API contract.

Recommended solution

  1. Send an idempotency key derived from the business request (payment instruction id) on every write call.
  2. Before retrying, query the status of the original request.
  3. Mark tools as read or write; the framework never auto-retries writes.
  4. Run payment execution in a durable workflow with exactly-once semantics at the business level.

Why it succeeds

Trade-off to manage: Status checks add latency to error paths only, which is acceptable for payments.

How you prove it worked:

  • Duplicate detection on (beneficiary, amount, date) within a window; reconciliation alerts.

Same pattern elsewhere: Telco: a retry on a timed-out SIM activation creates two orders and two ICCIDs bound to the same number.

Reference implementation

@tool(kind="write", auto_retry=False)                         # framework never retries writes
def send_wire(instr: WireInstruction):
    key = f"wire:{instr.instruction_id}"                       # from the business request
    try:
        return payments.send(instr, idempotency_key=key, timeout=10)
    except Timeout:
        status = payments.status(idempotency_key=key)          # check before any retry
        if status in ("ACCEPTED", "SETTLED"):
            return {"status": status}
        return payments.send(instr, idempotency_key=key)       # safe: same key
Key takeaway

Assume every tool call might run twice.

7.12

B2B order agent loses state on a pod restart

ReliabilityTelco

Problem statement

An enterprise ordering agent coordinates a 40-site SD-WAN order over several hours: site surveys, feasibility, pricing approvals and order creation. A Kubernetes pod is rescheduled during a deploy. The agent's in-memory state is lost, and it restarts from scratch, re-requesting surveys and creating duplicate draft orders.

The anti-pattern

Agent state held only in process memory.

Think of it this way: Writing a long report without saving. When the laptop restarts, you start over.

Why the current design fails

Mechanism: Long-running agents outlive containers, deploys, and network blips.

  • State lives only in process memory.
  • Long-running work outlives containers, deploys and network blips.
  • Restarting re-executes side effects.

Root cause: No durable execution or checkpointing.

Where it breaks: Agent runtime.

Recommended solution

  1. Checkpoint state after every step to a durable store (LangGraph checkpointers, Temporal, a database).
  2. Resume from the last checkpoint after a restart, skipping completed side effects.
  3. Combine checkpointing with idempotent tools so replays are safe.

Why it succeeds

Trade-off to manage: Checkpointing adds write latency and storage; it is small relative to multi-hour tasks.

How you prove it worked:

  • Count of runs restarted from step 1; duplicate draft orders per order id.

Same pattern elsewhere: FinTech: a commercial loan document-collection agent loses progress overnight and re-emails the borrower for documents already received.

from langgraph.checkpoint.postgres import PostgresSaver
