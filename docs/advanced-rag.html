4.1

GraphRAG or agentic RAG where simple RAG works

CostLatencyReliability

Problem statement

A retailer's FAQ assistant answers return-policy questions. The team builds a knowledge graph, a multi-step agentic retriever and a reflection loop. Latency is 14 seconds and accuracy is no better than a basic pipeline.

The anti-pattern

Architecture is chosen by trend, not by query profile. Every question goes through the most complex path: graph traversal, iterative tool calls, self-critique.

Why the current design fails

  • Complexity without benefit. Most enterprise queries are single-hop lookups that hybrid retrieval plus a reranker handles well.
  • Latency and cost multiply with every extra LLM call and traversal.
  • More failure surface. Graph extraction errors, entity-resolution mistakes and agent loops each add new ways to be wrong.
  • Maintenance burden. Knowledge graphs need schema design, entity resolution and continuous curation.

Recommended solution

Route by query complexity, and justify each advanced technique with evaluation:

Technique Use when Avoid when
Hybrid + rerank Default for lookups and how-tos —
Query decomposition Multi-part, comparative questions Single facts
Agentic retrieval Open-ended research, needs iteration across tools Latency-critical UX
GraphRAG Relationship / aggregation questions ("which suppliers share a parent company?"), global summaries Flat FAQ or policy corpora

Profile real queries first. Build the simple pipeline and its eval set, then add a technique only when a measured query segment fails and the technique fixes it.

Why it succeeds

Most traffic takes the fast, cheap path. Advanced techniques run only where they add measurable value, so average latency and cost stay low while hard queries still get answered. Each component earns its place through evidence, which keeps the architecture explainable and maintainable.

Reference implementation

ROUTES = {"lookup": simple_rag, "multi_hop": decomposed_rag,
          "relationship": graph_rag, "research": agentic_rag}

def route(q):
    label = classifier.predict(q)              # small fine-tuned model or cheap LLM call
    if label not in ROUTES or classifier.confidence < 0.6:
        label = "lookup"                       # safe, fast default
    metrics.inc(f"route.{label}")
    return ROUTES[label](q)
Key takeaway

Advanced RAG is a tool, not a maturity level. Profile the queries, default to simple, and escalate only for the segments that measurably need it.

4.2

No citation or grounding verification

QualityCompliance

Problem statement

A compliance assistant cites "Policy AML-7, section 4.2" for a transaction-monitoring threshold. The section exists, but it says something different. An auditor finds it.

The anti-pattern

The model is asked to "include citations", and they're displayed as-is. Nobody checks whether the cited passage actually supports the sentence it's attached to.

Why the current design fails

  • Citation hallucination. Models can attach plausible references to claims that came from parametric memory, or misattribute between sources.
  • False trust. A citation looks like evidence, so users check less, which makes wrong answers more dangerous.
  • No measurement. Without verification, there's no faithfulness metric to manage.

Recommended solution

Make citations structural and verified:

  • Give each source passage a stable ID and require structured output: [{claim, source_ids, quote}]. Use native citation features where the model API provides them.
  • Verify each claim against its cited passages with an entailment/NLI model or an LLM judge, and confirm that quoted spans really exist in the source text (string match).
  • Remove or flag unsupported claims, and show users the exact supporting passage on hover.
  • Track faithfulness rate and citation precision in offline and online evals.

Why it succeeds

Citations become checkable facts instead of decoration. Exact-span matching catches fabricated quotes cheaply, and entailment checks catch misattribution. Users and auditors can verify any claim in one click, and the faithfulness metric gives leadership a number to govern.

Reference implementation

out = llm.generate_structured(schema=AnswerWithClaims, sources=ev, question=q)
verified = []
for c in out.claims:
    texts = [src[i].text for i in c.source_ids if i in src]
    quote_ok = any(c.quote in t for t in texts)                       # exact span exists
    entailed = nli.entails(premise=" ".join(texts), hypothesis=c.claim) > 0.8
    if quote_ok and entailed:
        verified.append(c)
    else:
        metrics.inc("citation.rejected")
return render(verified, show_sources=True)
Key takeaway

A citation nobody verified is decoration. Make citations structured, check them claim by claim, and measure faithfulness.

4.3

Ignoring temporal freshness and document validity

QualityCompliance

Problem statement

A travel-policy assistant tells an employee the hotel cap is $250 a night. That was the 2024 policy; the 2026 policy says $300. Both versions are in the index and the older one ranked higher.

The anti-pattern

Retrieval is purely semantic. Policy versions, superseded documents and dated facts compete on similarity alone, and older documents (with more cross-references) often win.

Why the current design fails

  • Superseded content wins because it's similar, longer or more linked.
  • Time-relative questions ("current", "last quarter", "as of today") aren't resolved to dates.
  • Mixed answers. The model blends old and new versions into a hybrid that matches neither.

Recommended solution

Model time explicitly:

  • Store effective_from, effective_to, version and status on every chunk (see the metadata contract).
  • Resolve temporal expressions in the query to concrete dates, defaulting to "as of today".
  • Filter to versions valid at that date. For time-series facts, add a recency decay to the ranking score.
  • Show the effective date with the answer, and explicitly support historical questions ("what was the policy in 2024?").

Why it succeeds

Superseded versions can no longer be retrieved for current questions, which removes the most common source of confidently wrong policy answers. Showing the effective date lets users verify currency at a glance, and historical questions still work because versioned content is kept, not deleted.

Reference implementation

as_of = resolve_time(q, default=today())                  # "last quarter" → date range
flt = {"effective_from": {"$lte": as_of},
       "$or": [{"effective_to": None}, {"effective_to": {"$gt": as_of}}],
       "status": {"$ne": "draft"}}
hits = hybrid_retrieve(q, filter=flt)
for h in hits:                                            # mild recency boost for dated facts
    h.score *= exp(-DECAY * (as_of - h.meta["published"]).days) if h.meta["doc_type"] == "bulletin" else 1
answer = generate(q, hits, footer=f"Policy version effective {hits[0].meta['effective_from']}")
Key takeaway

"Correct" is time-dependent. Index validity dates, resolve the question's time frame, and filter before ranking.

Follow-up to expect

4.4

Using RAG to fix behaviour, or fine-tuning to add knowledge

CostQuality

Problem statement

Team A fine-tunes a model on the product catalog so it "knows" prices. Prices change weekly and the model keeps quoting old ones. Team B puts 40 pages of style guide into every RAG prompt to get answers in the brand voice and JSON format, and it's still inconsistent.

The anti-pattern

The wrong lever for the problem: fine-tuning to inject frequently changing facts, or retrieval and prompt stuffing to change stable behaviours such as format, tone and domain reasoning style.

Why the current design fails

  • Fine-tuning is a poor knowledge store. Facts can't be updated, cited or access-controlled, and models may blend or hallucinate memorized facts.
  • Prompts are a poor behaviour store at scale. Long instructions cost tokens on every call and are followed inconsistently.
  • Expensive iteration. Every fact change triggers a retraining cycle.

Recommended solution

Apply a simple decision rule:

Need Lever
Facts that change, must be cited, or are permissioned RAG / tool calls to systems of record
Exact values (prices, balances, inventory) Tool/API call, not retrieval of text
Output format, tone, domain style Structured output + few-shot, then fine-tuning if still inconsistent
Specialized reasoning on stable patterns, latency/cost at scale Fine-tune or distill a smaller model

Start with prompting and RAG, establish an eval baseline, and fine-tune only for a measured behaviour gap at volume.

Why it succeeds

Knowledge stays live, cited and governed in the systems that own it. Behaviour is learned once rather than paid for in every prompt. Separating the two levers makes each one cheaper to change and easier to evaluate. Distilled or fine-tuned small models can then cut serving cost for high-volume, stable tasks.

Reference implementation

# Facts: call the system of record, don't memorize
tools = [Tool("get_price", lambda sku: pricing_api.current(sku)),
         Tool("search_policies", secure_search)]

# Behaviour: schema + few-shot first; fine-tune only if eval shows a persistent gap
resp = llm.generate(system=BRAND_VOICE_SHORT, examples=FEW_SHOT[:3],
                    tools=tools, response_schema=QuoteResponse, user=q)

if eval_report["format_adherence"] < 0.97 and monthly_calls > 2_000_000:
    start_finetune(base="small-model", data=curated_pairs, eval_gate=eval_suite)
Key takeaway

RAG and tools for knowledge, prompting or fine-tuning for behaviour. Mixing them up produces stale facts or bloated prompts.

4.5

Contextual chunking rolled out without a cost model

CostQuality

Problem statement

Contextual retrieval (an LLM-written situating sentence per chunk) improved recall in a pilot. The team now wants to run it on all 40 million chunks.

The anti-pattern

A per-chunk LLM enrichment is approved corpus-wide with no cost estimate, caching or prioritization.

Why the current design fails

  • Contextual enrichment calls an LLM once per chunk at ingest, so cost scales with corpus size.
  • Every re-ingest repeats the bill unless unchanged chunks are skipped.
  • The gain is concentrated in a few sources, but the cost is spread over all of them.

Recommended solution

Approve it as a staged rollout with a cost model:

  1. Estimate cost: chunks × tokens per call × price, minus prompt-cache savings for the shared document prefix.
  2. Pilot on the sources with the worst retrieval failures.
  3. Measure recall gain per dollar, and roll out by priority.
  4. Only re-contextualize chunks whose content hash changed.

Why it succeeds

The technique is applied where it pays back first, with a known budget. Prompt caching of the document prefix and hash-based skipping keep both the one-off and recurring cost bounded.

Reference implementation

def contextual_cost(n_chunks, doc_tokens_per_call, chunk_tokens, out_tokens,
                    in_price_per_m, out_price_per_m, cache_hit=0.9, cached_discount=0.9):
    doc_cost = doc_tokens_per_call * in_price_per_m / 1e6 * (1 - cache_hit * cached_discount)
    chunk_cost = (chunk_tokens * in_price_per_m + out_tokens * out_price_per_m) / 1e6
    return n_chunks * (doc_cost + chunk_cost)
# plug in your provider's current prices; compare with recall gain on the pilot sources
Key takeaway

Good retrieval techniques still need a budget. Price per-chunk enrichment, start where retrieval is worst, and skip unchanged chunks.

4.6

Fine-tuning a model to answer credit-card policy questions

QualityFinTech

Problem statement

A card issuer fine-tunes a model on its policy manual so the assistant "knows" policies. It answers fluently, but can't cite sources, mixes old and new versions of policy, and every policy update requires a new fine-tuning run that takes weeks.

The anti-pattern

Fine-tune the policy manual into the model.

Think of it this way: Memorising the rulebook instead of keeping it on the desk and looking things up.

Why the current design fails

  • Knowledge baked into weights can't be cited or updated quickly.
  • Fine-tuning blends versions present in training data.
  • Compliance requires traceable answers.

Root cause: Fine-tuning chosen for a knowledge problem.

Where it breaks: Approach selection.

Recommended solution

  1. Use RAG over versioned policy documents with citations for knowledge.
  2. Use prompting for format and tone; consider fine-tuning only if behaviour still fails after that.
  3. Run error analysis to decide what kind of problem you have.

Why it succeeds

Trade-off to manage: RAG adds retrieval latency and index operations.

How you prove it worked:

  • Answer staleness after policy updates; citation coverage.

Same pattern elsewhere: Telco: fine-tuning on the roaming guide produces answers that go stale with every tariff change (see ops-03).

Reference implementation

def card_policy_answer(q, card_product):
    hits = search(q, filter={"product": card_product, "status": "in_force"})   # versioned policy docs
    return generate(q, hits, system=TONE_AND_FORMAT_PROMPT, require_citations=True)

def error_analysis(failures):
    return Counter(label_failure(f) for f in failures)      # knowledge vs behaviour → RAG vs fine-tune
Key takeaway

Fine-tune for how to say it. Retrieve what to say.

4.7

Adding more retrieval to fix the bot's tone

QualityTelco

Problem statement

A carrier's bot answers correctly but sounds robotic and off-brand. The team adds brand guidelines and example conversations to the retrieval index. Retrieval now sometimes returns style guides instead of product facts, and tone barely changes.

The anti-pattern

Retrieve style guides to fix tone.

Think of it this way: Buying more books to fix your handwriting.

Why the current design fails

  • A behaviour problem treated as a knowledge problem.
  • Style documents compete with facts in retrieval.
  • Tone needs consistent instruction or training, not lookup.

Root cause: Approach chosen without diagnosing the failure type.

Where it breaks: Approach selection.

Recommended solution

  1. Put tone and style in the system prompt with a few good examples.
  2. If prompting isn't enough at scale, fine-tune on curated on-brand responses.
  3. Keep retrieval for facts only.

Why it succeeds

Trade-off to manage: Fine-tuning for tone needs curated data and evals.

How you prove it worked:

  • Brand-voice judge scores; retrieval precision for factual queries.

Same pattern elsewhere: FinTech: a bank indexes its writing style guide to make letters sound warmer, and retrieval quality drops.

Reference implementation

SYSTEM = """Voice: warm, direct, no jargon. Use the customer's name once.
Examples:
- "Good news, Priya: your bill went down by $8 this month because the promo kicked in."
- "I'm sorry about the outage, Mark. Here's what's happening and when we expect it back."
"""
reply = llm(system=SYSTEM, context=retrieve_facts(q), user=q)    # retrieval for facts only
# if prompting isn't enough at scale: fine-tune on curated on-brand responses
Key takeaway

Retrieval fixes what the model knows, not how it talks.

4.8

Prompt with 400 ticket categories for routing

QualityCostTelco

Problem statement

A carrier routes support tickets into 400 categories by putting all category descriptions into the prompt. The prompt is 25k tokens, accuracy is 71%, and cost is high. The company has three years of tickets labelled with the right queue.

The anti-pattern

400 categories in one prompt.

Think of it this way: Reading the whole phone directory before connecting each call.

Why the current design fails

  • Huge label sets strain prompting.
  • Labelled data exists but is unused.
  • Cost and latency scale with prompt size.

Root cause: Prompting used where supervised learning fits.

Where it breaks: Approach selection.

Recommended solution

  1. Fine-tune a small model or train a classifier on labelled tickets (hierarchical labels help).
  2. Use the LLM for low-confidence or new categories.
  3. Evaluate both approaches on the same held-out set.

Why it succeeds

Trade-off to manage: Fine-tuned classifiers need retraining when categories change.

How you prove it worked:

  • Accuracy by category and confidence band.

Same pattern elsewhere: FinTech: a bank classifies complaints into 150 regulatory categories by prompt alone.

Reference implementation

clf = train_hierarchical_classifier(labelled_tickets, levels=["domain", "category"])   # small model

def route(ticket):
    pred = clf.predict(ticket.text)
    if pred.confidence >= 0.85:
        return pred.category
    return llm.classify(ticket.text, candidates=pred.top_k(10))     # low-confidence / new categories

compare(clf, llm_prompted, heldout)                                 # same held-out set
Key takeaway

Lots of labels plus lots of data means train, don't prompt.

4.9

Fine-tuned model shipped without a held-out evaluation

QualityFinTech

Problem statement

A bank fine-tunes a model to extract fields from trade confirmations. Training loss looks great, and spot checks pass. There's no held-out test set and no comparison with the prompted baseline. In production, it's worse than the original prompted model on confirmations from smaller counterparties.

The anti-pattern

Ship on training loss and spot checks.

Think of it this way: Judging a new recipe by how good the dough looked, without tasting the bread.

Why the current design fails

  • Training loss isn't task accuracy.
  • No baseline comparison.
  • Test data doesn't cover the long tail.

Root cause: Fine-tuning without rigorous evaluation.

Where it breaks: ML process.

Recommended solution

  1. Hold out a test set stratified by counterparty and document type.
  2. Compare against the prompted baseline on the same set.
  3. Ship only if the fine-tune beats the baseline on the slices that matter.

Why it succeeds

Trade-off to manage: Smaller training set.

How you prove it worked:

  • Field-level accuracy by slice, before and after.

Same pattern elsewhere: Telco: a fine-tuned intent model looks good in training and underperforms the prompted model on prepaid-brand slang.

Reference implementation

train, test = stratified_split(docs, by=["counterparty", "doc_type"], test_frac=0.2)
tuned = finetune(BASE, train)
results = {"prompted": evaluate(prompted_baseline, test), "tuned": evaluate(tuned, test)}
important = ["isda", "csa", "top_10_counterparties"]
ship = all(results["tuned"].slice(s) >= results["prompted"].slice(s) for s in important)
Key takeaway

A fine-tune must beat the baseline on held-out data, or it doesn't ship.

4.10

Fine-tuning on the bot's own past answers

QualityCostLatencyTelco

Problem statement

To save labelling cost, a carrier fine-tunes its next care model on transcripts of the current bot's answers that customers didn't complain about. The new model inherits the old one's mistakes, with more confidence, and quality slowly declines with each round.

The anti-pattern

Train on the bot's unverified outputs.

Think of it this way: Photocopying a photocopy; each generation gets blurrier.

Why the current design fails

  • Model outputs used as training targets without verification.
  • A lack of complaints isn't correctness.
  • Errors are amplified.

Root cause: Self-generated training data without quality control.

Where it breaks: Data curation.

Recommended solution

  1. Use verified data (expert-reviewed answers, resolved cases with confirmed outcomes).
  2. If using synthetic or model-generated data, filter with strong checks and mix with human data.
  3. Track quality across generations.

Why it succeeds

Trade-off to manage: Expert review costs.

How you prove it worked:

  • Eval trend across successive fine-tunes.

Same pattern elsewhere: FinTech: a bank trains its document classifier on its own previous predictions.

Reference implementation

def training_examples():
    expert = answers.where(reviewed_by_expert=True, verdict="correct")
    resolved = cases.where(outcome_confirmed=True).answers()
    synthetic = [s for s in generate_synthetic(n=2000) if strong_checks(s)]
    data = expert + resolved + synthetic[: len(expert)]           # synthetic never dominates
    lineage.record(sources={"expert": len(expert), "resolved": len(resolved), "synthetic": len(synthetic)})
    return data
Key takeaway

Don't teach a model its own mistakes.

4.11

Fine-tune makes the model forget its refusals

QualityFinTech

Problem statement

A wealth platform fine-tunes a model on advisor conversations to sound more like its advisors. After deployment, the model readily gives specific buy and sell recommendations to retail users, which the base model used to decline. The training data contained advisors giving recommendations to clients with whom they had a suitability relationship.

The anti-pattern

No safety evals after fine-tuning.

Think of it this way: Teaching someone a new accent and finding they've forgotten their manners.

Why the current design fails

  • Fine-tuning shifts behaviour beyond the target.
  • Safety and compliance behaviours regress.
  • No safety evals after fine-tuning.

Root cause: No regression testing of safety behaviour after fine-tuning.

Where it breaks: Fine-tuning process.

Recommended solution

  1. Run the full safety and compliance eval suite after every fine-tune.
  2. Include refusal and boundary examples in training data.
  3. Keep runtime guardrails independent of the model.

Why it succeeds

Trade-off to manage: More training and eval effort.

How you prove it worked:

  • Safety eval deltas between base and fine-tuned models.

Same pattern elsewhere: Telco: a fine-tuned care model starts revealing account details without verification because training chats came from already-verified sessions.

Reference implementation

train_data = core_examples + refusal_and_boundary_examples       # keep refusals in the training mix
tuned = finetune(BASE, train_data)

safety = run_suite(tuned, suites=["safety", "compliance", "refusals"])
assert safety.critical_failures == 0, "fine-tune broke safety behaviour"
# runtime guardrails stay independent of the model:
reply = output_guard.check(tuned.generate(msg))
Key takeaway

Fine-tuning can unlearn safety. Re-test it every time.

4.12

Fine-tuning teaches a confident tone, not correct answers

QualityTelco

Problem statement

A carrier fine-tunes its troubleshooting bot on polished agent responses to reduce hedging. Customers like the confident tone, but the model now states guesses about network faults as facts, and wrong-diagnosis rates rise.

The anti-pattern

Fine-tune away the hedging.

Think of it this way: Training someone to speak confidently without teaching them anything new.

Why the current design fails

  • Style training changes certainty, not knowledge.
  • Hedging was a useful signal of uncertainty.
  • No grounding or diagnostics behind answers.

Root cause: Fine-tuning used to fix a symptom (hedging) instead of the cause (missing data).

Where it breaks: Approach and data.

Recommended solution

  1. Give the bot diagnostic tools (line tests, outage data) so answers are grounded.
  2. Keep calibrated uncertainty language when evidence is weak.
  3. Evaluate correctness, not just tone.

Why it succeeds

Trade-off to manage: Less confident tone where evidence is weak, which is honest.

How you prove it worked:

  • Wrong-diagnosis rate before and after.

Same pattern elsewhere: FinTech: a fine-tuned bot sounds certain about fee outcomes it can't check.

Reference implementation

TOOLS = [run_line_test, check_outage, device_status]               # grounded diagnostics

SYSTEM = ("If the line test or outage data doesn't confirm the cause, say what you checked and "
          "that the cause isn't confirmed yet.")

eval_metrics = ["diagnosis_correct", "resolution_correct", "calibrated_uncertainty"]   # not just tone
Key takeaway

Confidence should come from evidence, not training.

4.13

Fifty examples expected to teach a complex task

QualityFinTech

Problem statement

A bank fine-tunes a model with 50 examples of commercial-loan covenant analysis, expecting it to learn the task. Results are worse than prompting with good instructions and three examples, because 50 examples can't cover the variety of covenant structures.

The anti-pattern

Fine-tune on 50 examples.

Think of it this way: Expecting someone to learn a language from fifty sentences.

Why the current design fails

  • Too little data for a complex task.
  • Fine-tuning chosen before prompting was optimised.
  • No learning curve measured.

Root cause: Unrealistic expectations of fine-tuning.

Where it breaks: Approach selection.

Recommended solution

  1. Optimise prompting and retrieval first.
  2. Estimate data needs with a learning curve (train on 50, 200, 1,000 examples).
  3. Use fine-tuning when you have enough diverse, high-quality data.

Why it succeeds

Trade-off to manage: Collecting quality data takes time.

How you prove it worked:

  • Learning curve and comparison with the prompted baseline.

Same pattern elsewhere: Telco: 40 examples of enterprise contract review are used to fine-tune a model.

Reference implementation

def learning_curve(train_pool, sizes=(50, 200, 1000)):
    return {n: evaluate(finetune(BASE, sample(train_pool, n)), heldout).score for n in sizes}

curve = learning_curve(pool)
# fine-tune only if the curve is still rising and enough diverse, high-quality data exists
Key takeaway

Fine-tuning needs data. Measure the learning curve first.

4.14

Fine-tuned model's base version is being retired

QualityTelco

Problem statement

A carrier's fine-tuned intent model is built on a hosted base model the provider will retire in 90 days. The training data, scripts and evals are scattered in notebooks. Re-creating the fine-tune on a new base becomes a scramble.

The anti-pattern

One-off fine-tune on a retiring base.

Think of it this way: Customising a car model that's going out of production, without keeping the parts list.

Why the current design fails

  • Fine-tunes are tied to specific base models.
  • No reproducible training pipeline.
  • Deprecation dates not tracked.

Root cause: Fine-tuning treated as a one-off.

Where it breaks: MLOps.

Recommended solution

  1. Keep training data, configs and evals versioned in a reproducible pipeline.
  2. Track base-model deprecation dates and re-tune proactively.
  3. Re-validate fine-tunes on new bases with the same evals.

Why it succeeds

Trade-off to manage: Pipeline maintenance effort.

How you prove it worked:

  • Days to deprecation for each fine-tune's base.

Same pattern elsewhere: FinTech: a bank's fine-tuned KYC extractor must be revalidated by model risk after the base model is retired.

Reference implementation

PIPELINE = {"data": "datasets/disputes@v7", "config": "configs/ft_disputes.yaml",
            "evals": "evals/disputes_suite@v5", "base": "base-model-2025-06"}

def retune(new_base):
    model = finetune(new_base, load(PIPELINE["data"]), config=load(PIPELINE["config"]))
    assert evaluate(model, PIPELINE["evals"]) >= baseline_scores(PIPELINE["evals"]) - 0.01
    return model

if provider.deprecation_date(PIPELINE["base"]) - today() < timedelta(days=120):

  • Text retrieval returns fragments.
  • Indirect ownership needs graph traversal and multiplication.

  2. Compute indirect ownership with graph queries in code, and let the LLM explain the result with sources.
  3. Use GraphRAG patterns where narrative and relationships both matter.

Why it succeeds

Trade-off to manage: Graph construction and maintenance effort.

How you prove it worked:

  • Accuracy against analyst-verified UBO determinations.

G = nx.DiGraph()

Fine-tuned model never A/B tested against the old one

QualityFinTech

Problem statement

A bank replaces its prompted model with a fine-tuned one after offline evals show a small gain. No online test is run. Three months later, complaint rates are slightly higher, but nobody can tell whether the fine-tune is responsible.

The anti-pattern

Replace the model after offline evals only.

Think of it this way: Changing a medicine without a control group.

Why the current design fails

  • No online comparison.
  • Small offline gains may not translate.
  • Later attribution is impossible.

Root cause: No online experiment for a model change.

Where it breaks: Release process.

Recommended solution

  1. Run an A/B test or canary against the existing model with business metrics (resolution, complaints, escalations).
  2. Decide based on online results with pre-agreed thresholds.
  3. Keep the old model available for rollback.

Why it succeeds

Trade-off to manage: A/B tests take time and traffic.

How you prove it worked:

  • Online metric differences by arm.

Same pattern elsewhere: Telco: a carrier swaps in a fine-tuned care model and can't later tell whether it changed repeat-contact rates.

Reference implementation

exp = experiment("disputes_model", arms={"control": OLD_MODEL, "treatment": TUNED_MODEL}, split=0.1)
THRESHOLDS = {"resolution_rate": +0.01, "complaints_rate": 0.0, "escalation_rate": 0.0}   # pre-agreed

def decide(results):
    ok = all(results.delta(m) >= t if t > 0 else results.delta(m) <= t for m, t in THRESHOLDS.items())
    return "ramp" if ok else "rollback_to_control"           # old model kept for rollback
Key takeaway

A model change is an experiment. Run it like one.
