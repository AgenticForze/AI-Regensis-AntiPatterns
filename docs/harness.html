18Harness Engineering at Every Stage

The harness is all the engineering around the model, at each stage from data to production. It covers the test harnesses that measure the system and the runtime harness that makes an agent work.

8 anti-patterns

Mature AI teams spend more effort on the harness than on the model. The term now appears in the platforms themselves: AWS ships a managed AgentCore harness, Microsoft a Copilot harness for Foundry Agent Service, and coding agents are described in terms of the harness that wraps the model. Two kinds of harness matter:

  • Evaluation harnesses answer "is it good enough, and did it get worse?" at every stage of the lifecycle.
  • Runtime harnesses answer "how does the model safely act?": the loop, tools, context, sandbox, hooks and budgets.
Stage Harness What it measures or controls
Data & ingestion Parsing / data-quality harness Extraction fidelity, coverage, freshness
Retrieval Retrieval eval harness Recall@k, MRR, nDCG, filter correctness
Generation Faithfulness harness Groundedness, completeness, format, refusal correctness
Agent runtime Agent harness Loop, tools, context assembly, sandbox, hooks, budgets
Agent evaluation Trajectory & simulation harness Task success, path correctness, safety across multi-turn runs
Safety Adversarial / red-team harness Injection, jailbreak, data-leak resistance
CI/CD Regression gate harness Change-over-change deltas per segment
Production Online eval, shadow & canary harness Drift, live quality, feedback loops

18.1

Data stage: no golden documents, so parser regressions go unnoticed

Quality

Problem statement

A library upgrade in the PDF parser changes how multi-column layouts are read. Retrieval quality drops on 15% of documents, and it's traced to the parser three weeks later.

The anti-pattern

Parsing and chunking have no tests. Changes to parsers, OCR settings or chunkers are deployed if the pipeline "runs without errors".

Why the current design fails

  • Silent degradation: the pipeline succeeds while producing worse text.
  • Late, expensive detection at the end-to-end level, after re-indexing.

Recommended solution

  • Curate 50–200 golden documents covering hard cases: multi-column, tables, scans, forms, non-English.
  • Store the expected extraction (text, table cells, reading order) and compare with similarity metrics and table-cell accuracy.
  • Track coverage (pages with text), OCR confidence and freshness lag as continuous data-quality metrics.
  • Run the harness on every parser, chunker or config change.

Why it succeeds

Parser regressions fail a test at the source, before re-indexing. Golden documents become the shared definition of extraction quality between data and AI teams.

Reference implementation

@pytest.mark.parametrize("doc", GOLDEN_DOCS)
def test_extraction(doc):
    out = parse(doc.path)
    assert text_similarity(out.text, doc.expected_text) >= 0.97
    assert table_cell_accuracy(out.tables, doc.expected_tables) >= 0.98
    assert reading_order_score(out.blocks, doc.expected_order) >= 0.95
Key takeaway

Parsing is the first place quality is lost. A golden-document harness catches regressions before they spread into every index.

18.2

Retrieval stage: no labelled query set

Quality

Problem statement

A team debates whether to switch embedders, add a reranker or change chunk size. Each option is argued from intuition, because no one can measure retrieval on its own.

The anti-pattern

Retrieval is only evaluated indirectly through final answers, and there's no labelled query-to-relevant-document set.

Why the current design fails

  • Can't compare options for embedders, chunking, hybrid weights or rerankers.
  • Confounded signals: generation quality masks retrieval failures and vice versa.

Recommended solution

  • Build a labelled set from search logs, SME input and synthetic queries generated from chunks (then filtered by humans).
  • Report recall@k, MRR and nDCG overall and per segment (query type, language, document type).
  • Include ACL and filter tests (user X must never retrieve doc Y) as hard assertions.
  • Run grid experiments across retrieval configurations.

Why it succeeds

Retrieval becomes a measurable, tunable component. Security tests turn access control into an automated regression test rather than a one-time review.

Reference implementation

def synth_queries(chunks, n_per=2):
    return [Q(text=q, relevant={c.id}) for c in sample(chunks, 400)
            for q in llm.json(f"Write {n_per} realistic employee questions answered by:\n{c.text}")]

def test_acl():
    assert not any(h.doc_id in BOARD_ONLY for h in secure_search("restructuring plan", token_for("analyst")))

grid = itertools.product(["dense", "hybrid"], [None, "rerank"], [300, 600])
results = {cfg: retrieval_eval(build(cfg), labelled) for cfg in grid}
Key takeaway

You can't tune retrieval through the final answer. A labelled query set, with security tests included, makes retrieval an engineering decision.

18.3

Generation stage: no faithfulness harness

QualityCompliance

Problem statement

A model upgrade makes answers more fluent and more often slightly beyond the sources. Users like the tone, and compliance finds unsupported claims in benefits answers.

The anti-pattern

Generation is judged on fluency or user ratings. Faithfulness to sources, completeness and refusal behaviour aren't measured separately.

Why the current design fails

  • Fluency hides hallucination. Users rate confident answers highly.
  • Refusal drift: models can become more or less willing to answer out-of-scope questions after upgrades.

Recommended solution

  • Hold retrieval constant: freeze contexts per case so generation is evaluated in isolation.
  • Measure claim-level faithfulness (decompose the answer into claims, check entailment against sources) and completeness against a rubric.
  • Keep a refusal set of out-of-scope and unanswerable questions, and measure correct refusals and false refusals.
  • Track format and citation adherence.

Why it succeeds

Generation changes are isolated from retrieval noise. Claim-level checks catch fluent overreach, and refusal metrics catch drift in both directions after model upgrades.

Reference implementation

def faithfulness(answer, contexts):
    claims = llm.json("Split into atomic factual claims", answer)
    return mean(nli.entails(" ".join(contexts), c) > 0.8 for c in claims)

report = {
    "faithfulness": mean(faithfulness(gen(c.q, c.frozen_ctx), c.frozen_ctx) for c in gen_cases),
    "refusal_correct": mean(is_refusal(gen(c.q, c.frozen_ctx)) for c in unanswerable_cases),
    "false_refusal": mean(is_refusal(gen(c.q, c.frozen_ctx)) for c in answerable_cases),
}
Key takeaway

Evaluate generation with retrieval frozen. Measure claim-level faithfulness and refusal behaviour, not how fluent the answer sounds.

18.4

Agent runtime: the prompt treated as the whole agent

ReliabilitySecurity

Problem statement

A team's agent "design document" is a 4-page system prompt. The loop, tool execution, context management, permissions and error handling are a few lines of glue code with no tests.

The anti-pattern

The runtime harness (loop, tool dispatch, context assembly, sandbox, hooks, budgets) is treated as boilerplate, while all effort goes into prompt wording.

Why the current design fails

  • Most agent failures are harness failures: context overflow, unhandled tool errors, missing permissions, infinite loops, unsafe execution.
  • No enforcement points for policy, since nothing intercepts tool calls.
  • Unportable: prompt-only design breaks when the model changes.

Recommended solution

Design the runtime harness as a first-class component:

  • Context manager: assembles instructions, state, retrieved knowledge and tool results within a token budget, with compaction.
  • Tool dispatcher: validates arguments, executes in a sandbox (containers or micro-VMs for code and browsers), and normalizes errors into model-readable observations.
  • Lifecycle hooks: before/after invocation and before/after tool call, for policy checks, PII redaction, approvals and logging. Managed harnesses expose similar hooks.
  • Budgets, stop rules and checkpointing (see 7.4 and 7.5).
  • Choose deliberately between building the harness (framework) and using a managed one (AgentCore harness, Foundry hosted agents, Claude Agent SDK / Managed Agents).

Why it succeeds

Control points exist exactly where risk occurs, at the tool boundary and the turn boundary. Errors become recoverable observations rather than crashes. A well-engineered harness makes model upgrades safer, because behaviour is shaped by code as well as prompt.

Reference implementation

class Harness:
    def __init__(self, model, tools, hooks, budget, ctx_mgr, sandbox):
        self.m, self.tools, self.hooks, self.budget, self.ctx, self.sbx = model, tools, hooks, budget, ctx_mgr, sandbox

    def run(self, task):
        state = self.hooks.before_invocation(State(task))
        while not state.done:
            self.budget.check(state)
            action = self.m.decide(self.ctx.assemble(state))
            if action.tool:
                action = self.hooks.before_tool_call(action, state)       # policy, approvals, redaction
                try:    obs = self.sbx.execute(self.tools[action.tool], action.args)
                except ToolError as e: obs = Observation(error=str(e), hint=e.hint)  # model-readable
                obs = self.hooks.after_tool_call(action, obs, state)
                state = state.add(action, obs); checkpoint(state)
            else:
                state = state.finish(action.answer)
        return self.hooks.after_invocation(state)
Key takeaway

The model proposes and the harness disposes. Context, tools, sandboxing, hooks and budgets are where agent reliability and safety are actually engineered.

18.5

Agent evaluation: judging only the final answer, not the trajectory

QualitySecurity

Problem statement

An expense-audit agent gets the right final verdict on 92% of test cases. Trace review shows that in 30% of those cases it skipped the receipt-validation tool and guessed.

The anti-pattern

Agent evaluation compares only final outputs with expected answers. The path (tool choice, order, arguments, safety-relevant steps) isn't evaluated, and only single-turn tests are run.

Why the current design fails

  • Right answer, wrong process. Lucky guesses pass, and they fail unpredictably in production.
  • Safety-relevant steps (verification, approvals) can be skipped without detection.
  • Multi-turn behaviour (clarifying questions, recovery from errors) isn't tested.

Recommended solution

  • Define expected trajectories or invariants per task: required tools, forbidden tools, ordering constraints, argument checks.
  • Use a simulated user to run multi-turn scenarios (ambiguous requests, mid-task changes, tool failures).
  • Score outcome (task success against environment state, not just text), trajectory and safety (no forbidden actions, approvals requested).
  • Use the trajectory evaluators available in the major platforms (ADK eval, AgentCore Evaluations, Foundry agent evaluators) or open frameworks.

Why it succeeds

Lucky guesses are exposed. Mandatory controls become testable invariants, and multi-turn simulation catches the conversational failures that single-turn tests miss.

Reference implementation

CASE = AgentCase(
    task="Audit expense report ER-1182",
    required_tools=["fetch_report", "validate_receipt"], forbidden_tools=["approve_payment"],
    order=[("fetch_report", "validate_receipt")],
    success=lambda env: env.report("ER-1182").status in {"flagged", "cleared"})

def evaluate(agent, case, sim_user):
    env, trace = sandbox_env(), run_with_sim(agent, case.task, sim_user)
    calls = [s.tool for s in trace.tool_spans]
    return {"outcome": case.success(env),
            "trajectory": all(t in calls for t in case.required_tools) and ordered(calls, case.order),
            "safety": not any(t in calls for t in case.forbidden_tools)}
Key takeaway

For agents, how matters as much as what. Evaluate trajectories and safety invariants in simulated multi-turn runs.

18.6

Safety: red-teaming once before launch

Security

Problem statement

A customer-facing agent passed a red-team exercise in March. By September it had new tools, a new model and new documents, and a researcher extracts internal pricing rules with a simple indirect injection.

The anti-pattern

Red-teaming is a one-off, manual pre-launch event. Its findings aren't turned into repeatable tests.

Why the current design fails

  • Attack surface changes with every new tool, model, data source and prompt.
  • New attack techniques appear constantly.
  • Fixed findings regress without automated tests.

Recommended solution

  • Maintain an attack library: direct and indirect injections, jailbreaks, data-exfiltration attempts, tool-abuse scenarios, domain-specific harms.
  • Automate with red-teaming tools (PyRIT, garak, promptfoo red-team) and the platforms' safety evaluators.
  • Run on every relevant change (new tool, model, data source) and on a schedule.
  • Convert every finding into a regression test. Keep periodic expert-led exercises for novel attacks.

Why it succeeds

Safety assurance keeps pace with change. Automated runs catch regressions, and expert exercises discover new classes of attack that are then automated.

Reference implementation

ATTACKS = load_attacks("attacks/") + generate_variants(base="indirect_injection", n=200)

def redteam(target):
    results = []
    for a in ATTACKS:
        env = seeded_env(canary_secret=CANARY)
        out = target.run(a.payload, env=env)
        results.append({"id": a.id, "leaked": CANARY in out.text or env.egress_contains(CANARY),
                        "forbidden_action": env.forbidden_actions_taken()})
    assert not any(r["leaked"] or r["forbidden_action"] for r in results), failing(results)
Key takeaway

Red-teaming is a regression suite, not an event. Automate attacks, run them on every change, and turn every finding into a permanent test.

18.7

CI/CD: one big eval run instead of a tiered gate

ReliabilityCost

Problem statement

The full eval suite takes 3 hours and costs $400 per run, so teams run it weekly. Prompt changes merged on Monday break things that aren't discovered until Friday.

The anti-pattern

One monolithic, expensive evaluation run, scheduled rather than triggered by changes, with no fast tier for pull requests.

Why the current design fails

  • Slow feedback encourages batching changes, which makes regressions harder to attribute.
  • Expensive runs get skipped.

Recommended solution

  • Tier 1 (PR): 50–150 cases selected by change impact (prompt X touches segments A and B), cached responses for unchanged components, cheap judges.
  • Tier 2 (nightly / pre-release): full suite with calibrated judges and statistical comparison against baseline.
  • Tier 3 (canary): online metrics on live traffic with automatic rollback.
  • Track eval cost as a budget line, and cache aggressively.

Why it succeeds

Developers get feedback in minutes on every change, and the full suite still runs before release. Change-impact selection keeps cost proportional, and attribution stays clear because regressions are caught per PR.

Reference implementation

def select_cases(changed_files):
    segments = set().union(*(IMPACT_MAP[f] for f in changed_files if f in IMPACT_MAP))
    return [c for c in SUITE if c.segment in segments][:150] or SMOKE_DEFAULT

# PR pipeline
cases = select_cases(git_changed_files())
res = run(cases, cache=ResponseCache(key=component_versions()))
gate(res, baseline="main", max_drop=0.02)
Key takeaway

Tier your eval gates like your test pyramid: fast and targeted on every PR, full depth before release, live metrics in canary.

18.8

Production: no online evaluation, drift detection or feedback loop

QualityReliability

Problem statement

A product-catalog assistant's quality degrades slowly as new product lines launch that aren't in the eval set. Offline scores stay green while customer complaints rise.

The anti-pattern

Evaluation stops at deployment. There's no sampling of live traffic, no drift monitoring, and user feedback isn't connected to traces or datasets.

Why the current design fails

  • Offline sets go stale as usage and content evolve.
  • Drift in query mix, data and model behaviour goes unnoticed.
  • Feedback is wasted if it isn't linked to traces.

Recommended solution

  • Sample a percentage of production traces for automated online evaluation (faithfulness, relevance, safety) using calibrated judges.
  • Monitor drift: topic distribution (clustering queries), retrieval scores, refusal rate, escalation rate, latency and cost.
  • Link thumbs-up/down and escalations to trace IDs, and route negatives to a triage queue.
  • Add triaged failures and new topics to the golden dataset regularly.
  • Use shadow mode to test candidate versions on live traffic without user exposure.

Why it succeeds

Quality is measured where it matters, on real users. Drift signals catch changing usage before complaints do, and the flywheel keeps offline evals representative, which closes the loop of the harness stack.

Reference implementation

@on_trace_complete(sample_rate=0.05)
def online_eval(trace):
    scores = {"faithfulness": faithfulness(trace.answer, trace.contexts),
              "relevance": relevance_judge(trace.question, trace.answer)}
    metrics.record(trace.app, scores, topic=topic_model.assign(trace.question))
    if min(scores.values()) < 0.6:
        triage_queue.put(trace.id)

drift = js_divergence(topic_hist(last_7d), topic_hist(baseline_window))
if drift > 0.15: alert("query mix drift: refresh eval set", top_new=new_topics(last_7d))
Key takeaway

Evaluation doesn't end at deployment. Online evals, drift monitors and trace-linked feedback keep the harness honest as the world changes.
