11.1

Shipping on "vibe checks" with no evaluation suite

QualityReliability

Problem statement

A procurement assistant is approved after a demo where five stakeholders tried a dozen questions each and "it looked good". Two weeks after launch, it's answering 18% of contract-term questions incorrectly.

The anti-pattern

Quality is judged by manual spot checks. There's no golden dataset, no defined metrics, no thresholds, and no record of what was tested.

Why the current design fails

  • Small, biased samples. Demo questions are easy and favourable, not representative.
  • No regression detection. Every prompt, model or data change is a leap of faith.
  • No go/no-go criteria. Launch decisions rest on opinion, not evidence.

Recommended solution

Build an evaluation suite as a core asset:

  • Golden dataset: 200–1,000 representative cases with expected answers or rubrics, stratified by segment (topic, difficulty, language, risk). Include adversarial and out-of-scope cases.
  • Metrics per use case: correctness, faithfulness, answer relevance, retrieval recall, format adherence, refusal correctness, latency and cost.
  • Thresholds agreed with the business and risk owners, per segment.
  • Flywheel: sample production traffic, label failures, and add them to the dataset.
  • Use an eval framework (Ragas, DeepEval, promptfoo, or the evaluation services in Bedrock, Vertex and Foundry) so runs are repeatable.

Why it succeeds

Quality becomes a number with a trend line, so launch and change decisions are evidence-based. Segmenting shows where the system is weak. The production flywheel keeps the dataset representative as usage evolves. Over time the eval suite becomes the organization's most valuable AI asset.

Reference implementation

suite = EvalSuite.load("procurement_qa@v7")            # 640 cases, 9 segments
metrics = [Correctness(judge=calibrated_judge), Faithfulness(), RetrievalRecall(k=8),
           RefusalCorrectness(), Latency(p95_ms=4000), CostPerAnswer(max_usd=0.02)]
report = suite.run(pipeline=candidate, metrics=metrics)

for seg, m in report.by_segment().items():
    assert m["correctness"] >= THRESHOLDS[seg], f"{seg} below threshold"
publish(report, compare_to="prod")
Key takeaway

No eval suite, no production. The golden dataset and thresholds are how you turn a demo into a decision.

11.2

Only end-to-end evaluation, nothing per component

Quality

Problem statement

End-to-end accuracy drops from 86% to 79% after a release. The team spends a week arguing whether the cause is the new chunker, the reranker, the prompt or the model.

The anti-pattern

The only metric is final-answer quality. Retrieval, reranking, tool selection and generation are never measured separately.

Why the current design fails

  • No fault isolation. End-to-end scores show that something broke, not where.
  • Misattributed fixes. Teams tune the prompt when retrieval is the problem.
  • Slow iteration. Every experiment needs the full pipeline.

Recommended solution

Use layered evaluation:

Stage Metric Data
Parsing Text and table extraction accuracy Golden documents
Retrieval Recall@k, MRR, nDCG Query → relevant-chunk labels
Reranking Precision@k Same
Tool use Tool-selection and argument accuracy Task → expected call
Generation Faithfulness, completeness, format Context → answer rubric
End to end Task success, user satisfaction Golden cases + production

Run component evals in CI on every change to that component.

Why it succeeds

Regressions are localized immediately. Component datasets are cheaper to run than full pipelines, so iteration is faster. Teams that own components get their own quality metrics.

Reference implementation

def retrieval_eval(retriever, labelled):
    return mean(len(set(retriever(q.text, k=8)) & q.relevant) / len(q.relevant) for q in labelled)

def tool_eval(agent, cases):
    return mean(agent.plan(c.task).first_call.name == c.expected_tool for c in cases)

CI_GATES = {"retrieval_recall@8": (retrieval_eval, 0.90),
            "tool_selection":      (tool_eval, 0.95),
            "faithfulness":        (faithfulness_eval, 0.93)}
Key takeaway

Evaluate the pipeline the way you'd test software: unit metrics per stage, integration metrics end to end.

11.3

No tracing of agent trajectories

ReliabilityCompliance

Problem statement

A customer complains that the billing agent cancelled their add-on service. The logs show the final message, but not which tools were called, with which arguments, on what reasoning.

The anti-pattern

Only inputs and outputs are logged, if anything. Multi-step agent runs (LLM calls, retrievals, tool calls, hand-offs) are invisible.

Why the current design fails

  • Undebuggable. You can't reproduce or understand failures.
  • No accountability. You can't show regulators or customers why an action was taken.
  • No optimization data. Latency and cost per step are unknown.

Recommended solution

Instrument with distributed tracing for AI:

  • Use OpenTelemetry with the GenAI semantic conventions. Each LLM call, retrieval, tool call and agent hand-off is a span within one trace.
  • Record model, prompt version, token counts, cost, latency, tool name and arguments (redacted), and outcome.
  • Send traces to an LLM-observability backend (Langfuse, Arize Phoenix, LangSmith, Datadog, or the cloud-native tracing in AgentCore, Foundry and Agent Platform).
  • Link traces to user feedback and eval scores.

Why it succeeds

Any decision can be replayed step by step, which turns debugging from guesswork into inspection. Auditable action trails satisfy accountability requirements, and per-span cost and latency show exactly where to optimize.

Reference implementation

from opentelemetry import trace
tracer = trace.get_tracer("billing-agent")

def traced_tool(tool):
    def run(**args):
        with tracer.start_as_current_span(f"tool.{tool.name}") as s:
            s.set_attribute("gen_ai.tool.name", tool.name)
            s.set_attribute("tool.args", redact(json.dumps(args)))
            result = tool(**args)
            s.set_attribute("tool.status", result.status)
            return result
    return run
Key takeaway

If you can't replay an agent's trajectory, you can't debug it, defend it or optimize it. Trace every step with OpenTelemetry.

11.4

LLM-as-judge without calibration

Quality

Problem statement

An LLM judge rates 94% of a legal assistant's answers as correct. A lawyer reviews 100 samples and agrees with only 71% of them. The judge prefers longer, confident answers.

The anti-pattern

An LLM grades outputs on vague 1–10 scales with no rubric, and its scores are reported as ground truth without ever being compared to expert judgment.

Why the current design fails

  • Known judge biases: verbosity, position, self-preference (favouring its own model family's style).
  • Vague criteria produce noisy, unrepeatable scores.
  • False confidence. Inflated scores mislead launch decisions.

Recommended solution

Validate the judge like a model:

  • Write specific, mostly binary rubric questions ("Does the answer state the notice period?", "Is every claim supported by a cited source?").
  • Have experts label 100–300 samples. Measure judge–expert agreement (accuracy, Cohen's kappa) and iterate on the rubric until it meets target.
  • Use a judge from a different model family where possible. Randomize answer order in pairwise comparisons.
  • Re-calibrate periodically and whenever the judge model changes.
  • Keep humans reviewing a sample of high-risk segments.

Why it succeeds

Binary criteria reduce noise and make failures specific. Measured agreement turns "the judge says 94%" into "the judge agrees with experts 92% of the time", which is defensible. Ongoing calibration keeps automated evaluation trustworthy as models change.

Reference implementation

RUBRIC = ["States the governing clause number", "Every factual claim has a supporting citation",
          "Does not give legal advice beyond the document", "Mentions applicable exceptions"]

def judge(answer, sources):
    return {c: judge_llm.yes_no(criterion=c, answer=answer, sources=sources) for c in RUBRIC}

expert = load_labels("legal_expert_200.jsonl")
agree = cohen_kappa([all(judge(x.answer, x.sources).values()) for x in expert],
                    [x.expert_pass for x in expert])
assert agree >= 0.75, "judge not calibrated, fix rubric before trusting scores"
Key takeaway

An LLM judge is a classifier. Give it a binary rubric, measure its agreement with experts, and re-calibrate it before trusting its numbers.

11.5

No regression gating in CI/CD

ReliabilityQuality

Problem statement

A provider retires a model version and the team switches to the successor "since it's newer". Extraction accuracy on handwritten forms drops 12%, and nobody notices for a month.

The anti-pattern

Prompt, model, retrieval and dependency changes deploy without automated quality checks. Model upgrades are treated as safe by default.

Why the current design fails

  • Silent regressions from any change, including the provider's.
  • Fear of change. Teams avoid improvements because they can't verify them.
  • Forced migrations (deprecations) become emergencies.

Recommended solution

Add AI quality gates to the delivery pipeline:

  • PR stage: fast smoke eval (50–100 cases) on any change to prompts, models, retrieval or tool definitions.
  • Pre-release: full eval suite compared against the production baseline, with per-segment thresholds and tolerance for noise.
  • Canary: route 5% of traffic, monitor online metrics (feedback, groundedness, escalations), and roll back automatically.
  • Model lifecycle: track provider deprecation dates, and pre-evaluate successors well before forced migration.

Why it succeeds

Regressions are caught before users see them. Teams can ship improvements confidently because the safety net exists. Deprecations become planned upgrades with evidence instead of emergencies.

Reference implementation

# .github/workflows/ai-quality.yml (excerpt) runs on changes to prompts/, retrieval/, models.yaml
#   - run: python -m evals.run --suite smoke --candidate $GITHUB_SHA --baseline prod
#   - run: python -m evals.gate --max-drop 0.01 --segments all

def gate(candidate, baseline, max_drop=0.01):
    failures = [s for s in candidate.segments
                if candidate[s].score < baseline[s].score - max_drop - noise_margin(s)]
    if failures:
        sys.exit(f"Blocked: regression in {failures}")
Key takeaway

Every prompt, model and retrieval change is a release. Gate it with evals in CI, canary it, and plan model deprecations ahead.

11.6

A golden set of 50 questions from one team

QualityScale

Problem statement

Offline scores look great and keep improving. Support tickets about wrong answers keep rising. The corpus has millions of documents across dozens of departments and three languages.

The anti-pattern

A small, static, hand-written eval set covering only the head of the distribution, written by one team.

Why the current design fails

  • Failures live in the long tail: other departments, other languages, rare document types and permission edge cases.
  • Optimizing against a narrow set overfits to it, so offline gains don't reach production.
  • The set never changes, while the corpus and users do.

Recommended solution

Use stratified evaluation:

  • Sample real production queries by segment (domain, tenant size, language, query type, doc type) and label them.
  • Synthesize extra questions from under-covered corpus regions.
  • Keep separate slices for freshness, permissions and unanswerable questions.
  • Report metrics per slice, never only the average, and add every production failure to the set.
  • Re-run evals when the corpus changes, not only when code changes.

Why it succeeds

Offline scores now predict production quality because the set reflects real traffic and its tail. Labeling costs are controlled with LLM judges calibrated against a human-labeled subset, and per-slice regression gates in CI plus online signals (thumbs down, reformulated queries, escalations) catch what's left.

Reference implementation

SEGMENTS = ["domain", "tenant_size", "language", "query_type", "doc_type"]

def build_golden(prod_queries, per_cell=15):
    strata = group_by(prod_queries, SEGMENTS)
    sample = [q for cell in strata.values() for q in random.sample(cell, min(per_cell, len(cell)))]
    gaps = [c for c in corpus_regions() if coverage(sample, c) < 0.01]
    sample += [synth_question(chunk) for c in gaps for chunk in c.sample(5)]
    sample += special_slices(["freshness", "permissions", "unanswerable"])
    return label(sample)

def gate(results):
    for slice_, score in results.by_slice().items():
        assert score >= THRESHOLD[slice_], f"regression in {slice_}"
Key takeaway

A golden set from one team measures one team's questions. Stratify by real traffic, keep special slices, and gate on every slice.

11.7

Bill-explanation prompt shipped after a vibe check

QualityTelco

Problem statement

A carrier's "explain my bill" assistant gets frequent complaints that it is too long. A product manager adds "Be concise, max 3 sentences" to the prompt, tries ten bills, likes the result and ships it. First-bill questions (proration after a plan change mid-cycle) now get a three-sentence answer that skips the proration, and first-bill calls to care rise 18% in two weeks.

The anti-pattern

Manual spot checks as the release gate.

Think of it this way: Tasting one spoonful from the top of the pot and declaring the whole stew seasoned. The salt sank to the bottom.

Why the current design fails

Mechanism: Ten cherry-picked examples miss regressions in the other 99% of traffic. Humans remember the wins.

  • Ten hand-picked bills were all simple, single-line accounts.
  • The change had a global side effect on complex bills, the cases that drive most calls.
  • Nothing compared old and new behaviour on a representative set.

Root cause: Manual spot checks were the release gate, with no versioned golden dataset.

Where it breaks: Release process and eval harness.

Recommended solution

  1. Build a golden set of 300-500 real (anonymised) bills covering first bills, proration, roaming, device installments, taxes and credits.
  2. Define pass criteria per case (mentions proration amount, correct total, under N words) and run old vs new on every prompt change.
  3. Block release if any high-volume intent regresses beyond a threshold.

Why it succeeds

Trade-off to manage: Building and anonymising the golden set takes a few weeks of effort, but it is reused for every future change.

How you prove it worked:

  • Care call-reason codes for "bill explanation" per bot version.
  • Weekly eval trend per bill type.

Same pattern elsewhere: FinTech: a "concise" tweak to a card-statement assistant drops the minimum-payment warning that Reg Z disclosures require.

Reference implementation

CASES = load_jsonl("golden/bill_explanations.jsonl")       # 400 anonymised bills, tagged by intent

def check(case, out):
    return {"total_correct": case.total in out,
            "mentions_proration": (not case.prorated) or "prorat" in out.lower(),
            "short_enough": len(out.split()) <= 120}

def gate(old, new):
    for intent, rows in group_by(CASES, "intent").items():
        d = pass_rate(new, rows, check) - pass_rate(old, rows, check)
        if volume[intent] > 0.05 and d < -0.02:
            sys.exit(f"blocked: {intent} regressed {d:.1%}")
Key takeaway

If it isn't in the eval set, it isn't protected.

11.8

ROUGE scores a collections-call summary that drops the dispute

QualityComplianceFinTechCritical

Problem statement

A lender auto-summarises collections calls for the next agent. The team evaluates summaries with ROUGE against human summaries and gets 0.61, which looks good. In a compliance review, 7% of summaries omit that the customer disputed the debt. Under the FDCPA, a dispute must stop collection until the debt is validated, so the next agent keeps collecting.

The anti-pattern

N-gram overlap metrics for free-form generation.

Think of it this way: Grading a medical handover note by how many words it shares with a model note. A note that leaves out "allergic to penicillin" can still score well.

Why the current design fails

Mechanism: A correct answer phrased differently scores low. A fluent wrong answer with matching words scores high.

  • ROUGE rewards word overlap, not the presence of critical facts.
  • A fluent summary missing one key sentence loses little score.
  • The facts that matter legally are rare and short.

Root cause: A generic NLP metric was used instead of task-specific, risk-weighted criteria.

Where it breaks: Eval design.

Recommended solution

  1. Define required elements per call type (dispute raised, promise to pay amount and date, cease-contact request, hardship) as binary checks.
  2. Score each element with a validated LLM judge or a classifier, and weight compliance elements as must-pass.
  3. Add a structured field extraction (dispute = true/false) that downstream systems read, not just a free-text summary.

Why it succeeds

Trade-off to manage: Element checklists take domain effort to define and keep up to date with regulations.

How you prove it worked:

  • Recall of each required element on a labelled set, tracked separately.
  • Compliance QA sampling of summaries where a dispute keyword appears in the transcript.

Same pattern elsewhere: Telco: care-call summaries miss "customer requested cancellation", so the retention team never calls back and the line churns.

Reference implementation

REQUIRED = {"collections": ["dispute_raised", "promise_to_pay", "cease_contact", "hardship"]}
MUST_PASS = {"dispute_raised", "cease_contact"}               # compliance elements

class CallSummary(BaseModel):
    dispute_raised: bool; promise_amount: float | None; promise_date: date | None
    cease_contact: bool; hardship: bool; narrative: str

def score(transcript, summary: CallSummary, labels):
    checks = {e: getattr(summary, e) == labels[e] for e in REQUIRED["collections"] if hasattr(summary, e)}
    return all(checks[e] for e in MUST_PASS), checks
Key takeaway

Measure what customers and regulators care about, not word overlap.

11.9

LLM judge loves retention chats humans rate poorly

QualityTelco

Problem statement

A retention-chat bot is scored by an LLM judge on "helpfulness" and averages 4.6 out of 5. Human QA reviewers score the same chats 2.8, because the bot offers long, friendly answers but rarely presents the save offer the customer qualifies for. Leadership has been reporting the 4.6 for a quarter.

The anti-pattern

Trusting an LLM judge without validating it against humans.

Think of it this way: A thermometer that was never checked against a real one. It always reads a comfortable 21 degrees, so nobody notices the heating is broken.

Why the current design fails

Mechanism: Judges have biases: verbosity, position, self-preference, and leniency.

  • The judge prefers long, polite answers (verbosity and style bias).
  • Helpfulness was never defined in terms of the business goal (right offer presented).
  • Judge scores were never compared with human labels.

Root cause: The evaluator itself was never evaluated.

Where it breaks: Judge design and calibration.

Recommended solution

  1. Label 150-200 chats by expert QA reviewers on specific criteria (eligible offer presented, correct price, no false promises).
  2. Rewrite the judge as binary checks per criterion, with reasoning before the verdict and access to the eligibility data.
  3. Measure agreement (precision and recall per criterion, Cohen's kappa) and iterate until acceptable; re-check quarterly.

Why it succeeds

Trade-off to manage: Human labelling is slow and expensive; keep the calibration set small but representative and refresh it.

How you prove it worked:

  • Running human-judge agreement on a weekly sample.
  • Correlation between judge scores and the business metric (save rate).

Same pattern elsewhere: FinTech: a judge rates a robo-advice bot's explanations highly even when the recommended portfolio does not match the client's risk profile.

Reference implementation

CRITERIA = ["eligible_offer_presented", "price_matches_catalog", "no_false_promises"]

def judge(chat, eligibility):
    return {c: judge_llm.json(f"Criterion: {c}. Reason step by step, then answer PASS or FAIL.",
                              chat=chat, eligibility=eligibility)["verdict"] == "PASS" for c in CRITERIA}

expert = load("retention_qa_labels_180.jsonl")
for c in CRITERIA:
    kappa = cohen_kappa([judge(x.chat, x.elig)[c] for x in expert], [x.labels[c] for x in expert])
    print(c, round(kappa, 2))                                 # iterate until acceptable; re-check quarterly
Key takeaway

A judge is a model too, so evaluate the evaluator.

11.10

Complaint classifier judged on a 1-10 scale

QualityComplianceFinTech

Problem statement

A bank uses an LLM to classify customer complaints into regulatory categories and route them. Quality is tracked with an LLM judge giving a 1-10 "accuracy" score averaging 7.4. Nobody knows what 7.4 means. A regulator exam later finds that complaints alleging discrimination were often classified as general service complaints and not escalated.

The anti-pattern

Vague Likert-scale scoring.

Think of it this way: Rating a restaurant "7 out of 10" without saying whether the problem was the food, the service, or food poisoning.

Why the current design fails

Mechanism: LLMs and humans are inconsistent on fine-grained scales. The number has no defined meaning.

  • A fuzzy scale with no definition gives unstable, uninterpretable scores.
  • Critical misroutes and minor wording issues get similar scores.
  • The average hides the rare, high-risk category.

Root cause: Likert scoring was used instead of explicit, binary criteria tied to outcomes.

Where it breaks: Rubric design.

Recommended solution

  1. Evaluate classification as classification, with a confusion matrix against labelled data.
  2. Define binary checks for high-risk routing ("Allegation of discrimination routed to fair-lending queue, yes or no").
  3. Set zero-tolerance thresholds for the high-risk categories, separate from overall accuracy.

Why it succeeds

Trade-off to manage: Binary criteria need more upfront definition but make every failure actionable.

How you prove it worked:

  • Recall per high-risk category, reviewed by compliance monthly.

Same pattern elsewhere: Telco: a ticket classifier scored 1-10 hides that outage reports are misrouted to billing, delaying network incident detection.

Reference implementation

from sklearn.metrics import confusion_matrix, classification_report

y_true, y_pred = labelled.category, [classify(t) for t in labelled.text]
print(classification_report(y_true, y_pred))
cm = confusion_matrix(y_true, y_pred, labels=CATEGORIES)

HIGH_RISK = ["discrimination_allegation", "udaap", "elder_abuse"]
for cat in HIGH_RISK:                                         # zero tolerance, separate from accuracy
    missed = [t for t, yt, yp in zip(labelled.text, y_true, y_pred) if yt == cat and yp != cat]
    assert not missed, f"{cat}: {len(missed)} misrouted"
Key takeaway

Binary criteria beat fuzzy scales.

Eval set frozen before the eSIM-only phone launch

QualityTelco

Problem statement

A carrier built its chatbot eval set at launch. A year later, a major handset maker ships eSIM-only phones in the market, and eSIM transfer questions jump to 14% of chats. The eval set has three eSIM questions. Evals pass at 94% while eSIM conversations fail half the time and stores are flooded with walk-ins.

The anti-pattern

A static golden set built at launch.

Think of it this way: Studying for this year's exam with last year's past papers when the syllabus has changed.

Why the current design fails

Mechanism: User behavior drifts, and new features and intents appear. The eval set measures last year's traffic.

  • The eval set represents last year's traffic mix.
  • New intents appear with product launches, regulations and seasons.
  • Nobody compares eval intent mix with production intent mix.

Root cause: The golden set is static and not fed by production.

Where it breaks: Eval data operations.

Recommended solution

  1. Sample production conversations weekly, label failures and add them as eval cases.
  2. Compare intent distribution of the eval set with production and alert on gaps.
  3. Add eval cases before known launches (new devices, price changes, regulatory changes).

Why it succeeds

Trade-off to manage: Continuous labelling needs a small standing team or vendor budget.

How you prove it worked:

  • Divergence metric between eval and production intent mix.
  • Failure rate per new intent cluster.

Same pattern elsewhere: FinTech: a bank's assistant eval set has no questions about a new instant-payments service, which becomes the top contact reason after launch.

def refresh_eval_set():

11.12

Investment-app assistant tested only on friendly questions

QualityFinTech

Problem statement

A brokerage app launches an assistant tested with 400 questions written by the product team, all about app features. In the first week, users ask "Should I put my emergency fund into this meme stock?", "Give me a guaranteed 20% strategy", and questions in Hindi and Spanish. The assistant gives stock-specific opinions, which the firm is not licensed to give in this channel.

The anti-pattern

Eval data written by the team who built the feature.

Think of it this way: Crash-testing a car only by driving it carefully around the car park.

Why the current design fails

Mechanism: Builders test what they designed for. Real users don't.

  • The eval set reflects how builders expect the product to be used.
  • Out-of-scope, adversarial and regulated-advice questions were never tested.

def paired_eval(a, b, cases, trials=5):
    sa = np.array([[score(a(c)) for _ in range(trials)] for c in cases]).mean(1)
    sb = np.array([[score(b(c)) for _ in range(trials)] for c in cases]).mean(1)
