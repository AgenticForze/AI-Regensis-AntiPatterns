15.1

LLM credit-memo tool deployed outside model risk management

ComplianceFinTech

Problem statement

A US bank's commercial-lending team deploys an LLM that drafts credit memos and suggests risk ratings. Because it was bought as a "productivity tool", it never went through model risk management. Examiners find it influences credit decisions and treat it as an unvalidated model.

The anti-pattern

AI tool bypasses model risk.

Think of it this way: Using a new set of scales in a pharmacy without having them calibrated.

Why the current design fails

  • The tool influences decisions but isn't classified as a model.
  • No validation, monitoring or documentation.
  • Ownership is unclear.

Root cause: AI uses not routed through the model-risk framework.

Where it breaks: Governance process.

Recommended solution

  1. Classify AI uses by impact; anything influencing credit, pricing or compliance decisions enters model risk management (inventory, validation, ongoing monitoring).
  2. Document intended use, limitations, evals and controls in a model card.
  3. Define human accountability for decisions the tool informs.

Why it succeeds

Trade-off to manage: Validation slows deployment; scale effort by risk tier.

How you prove it worked:

  • Inventory coverage audits against gateway usage.

Same pattern elsewhere: Telco: an AI that sets device-financing credit limits is deployed without review by the credit risk function.

Reference implementation

def classify_ai_use(uc) -> str:
    if uc.influences & {"credit", "pricing", "compliance"}:
        return "model_risk_managed"                       # enters MRM: validation, monitoring, review
    return "standard"

model_card = {
    "intended_use": "draft credit memos for analyst review", "out_of_scope": ["final credit decision"],
    "limitations": ["no access to bureau data"], "evals": "evals/credit_memo_v4.html",
    "controls": ["analyst sign-off", "numeric recompute check"], "accountable_owner": "Head of Credit Risk"}
Key takeaway

If it influences a decision, it's a model. Govern it like one.

15.2

Disconnect and port-out executed with no human gate

ComplianceTelcoCritical

Problem statement

A carrier's agent can disconnect lines and approve port-out requests autonomously. A misread request ("cancel my roaming pass") leads to a full line disconnect, and the customer's number is lost to recycling rules before anyone notices.

The anti-pattern

Irreversible actions are autonomous.

Think of it this way: A demolition crew that starts work from a phone message without checking the address.

Why the current design fails

  • Irreversible actions run without confirmation or approval.
  • No risk tiers for actions.
  • No cooling-off or undo window.

Root cause: Human-in-the-loop not designed around reversibility and impact.

Where it breaks: Action policy.

Recommended solution

  1. Classify actions by reversibility and impact (read, reversible write, irreversible).
  2. Require explicit customer confirmation for reversible writes and human or out-of-band approval for irreversible ones.
  3. Add soft-delete or cooling-off windows (number quarantine) wherever possible.

Why it succeeds

Trade-off to manage: Slower completion for rare high-impact actions.

How you prove it worked:

  • Irreversible actions without approval records.

Same pattern elsewhere: FinTech: an agent closes accounts and sends balances by cheque without approval.

Reference implementation

ACTION_CLASS = {"get_usage": "read", "change_plan": "reversible_write",
                "disconnect_line": "irreversible", "port_out": "irreversible"}

def execute(action, args, ctx):
    cls = ACTION_CLASS[action]
    if cls == "reversible_write" and not ctx.customer_confirmed(action):
        return ask_confirmation(action, args)
    if cls == "irreversible":
        approval = out_of_band.approve(ctx.customer_id, action) or human_queue.approve(action, args)
        if not approval: return {"status": "PENDING_APPROVAL"}
        return quarantine_then_execute(action, args, days=30)     # number quarantine / cooling-off
    return TOOLS[action](**args)
Key takeaway

The less reversible the action, the more human the decision.

15.4

Customers trapped in a chatbot doom loop

ComplianceFinTech

Problem statement

A bank's assistant handles disputes but has no clear way to reach a person. Customers with unusual problems loop through the same answers. Regulators have specifically raised concerns about banking chatbots that block access to human help, and complaint volumes rise.

The anti-pattern

No way out of the bot.

Think of it this way: A phone menu with no option to speak to anyone.

Why the current design fails

  • No escalation path or triggers.
  • Bot keeps trying when it's failing.
  • Containment is the main KPI.

Root cause: Automation optimised for containment over resolution.

Where it breaks: Product design and KPIs.

Recommended solution

  1. Always offer a path to a human, and escalate automatically on triggers (repeated failure, frustration, disputes, vulnerability, legal threats).
  2. Pass full context to the human agent.
  3. Balance containment with resolution and complaint metrics.

Why it succeeds

Trade-off to manage: More human contacts; fewer complaints and better outcomes.

How you prove it worked:

  • Loop detection; requests for a human not honoured.

Same pattern elsewhere: Telco: customers can't reach an agent to dispute a bill because the bot keeps re-explaining it.

Reference implementation

TRIGGERS = {"failed_turns": 2, "frustration": 0.7, "intents": {"complaint", "bereavement", "vulnerability"}}

def should_escalate(session):
    return (session.consecutive_failures >= TRIGGERS["failed_turns"]
            or sentiment(session.last_user_msg) <= -TRIGGERS["frustration"]
            or session.intent in TRIGGERS["intents"]
            or wants_human(session.last_user_msg))

if should_escalate(session):
    handoff(session, context=summary(session))           # full context to the human agent
Key takeaway

Never trap a customer with a bot.

LLM-assisted credit decline can't give specific reasons

ComplianceFinTechCritical

Problem statement

A lender lets an LLM review applications and recommend approve or decline, which underwriters mostly follow. When declining, the lender must give applicants the specific principal reasons. The LLM's narrative reasons are vague, inconsistent and can't be tied to the actual factors behind the recommendation.

The anti-pattern

LLM recommends credit decisions.

Think of it this way: A referee who can't say which rule was broken.

Why the current design fails

  • An opaque model drives credit decisions.
  • Reasons are generated text, not the factors used.
  • Legal requirements for specific reasons can't be met.

Root cause: LLM used as a decision-maker where explainable decisions are required.

Where it breaks: Decision architecture.

Recommended solution

  1. Keep credit decisions in validated, explainable models and rules; use the LLM to gather and summarise information, not to decide.
  2. Generate adverse-action reasons from the decision model's factors, with the LLM only drafting the letter from them.
  3. Test reasons for accuracy and consistency.

Why it succeeds

Trade-off to manage: Less use of LLM judgement in decisions.

How you prove it worked:

  • Mismatch between stated reasons and decision factors.

Same pattern elsewhere: Telco: a postpaid credit check declines applicants with AI-written reasons that don't match the actual credit policy.

Reference implementation

decision = credit_model.decide(application)              # validated, explainable model + rules
reasons = [REASON_TEXT[f] for f in decision.top_adverse_factors(n=4)]   # from the model's factors

letter = llm.draft(template="adverse_action_letter", reasons=reasons,
                   instructions="Use the reasons exactly as given. Do not add or infer reasons.")
assert all(r in letter for r in reasons), "letter must contain the decision model's reasons"
Key takeaway

The LLM can write the letter. It can't be the decision.

Retention offers differ by customer name and dialect

ComplianceTelco

Problem statement

A carrier's retention agent uses conversation tone and wording to decide offer generosity. An internal audit finds customers writing in certain dialects or with certain names receive smaller offers on average, even with the same tenure and value.

The anti-pattern

Model discretion over offers.

Think of it this way: A shop assistant who gives discounts based on accent.

Why the current design fails

  • Model judgement affects outcomes for customers.
  • Inputs carry proxies for protected characteristics.
  • No fairness testing.

Root cause: Unconstrained model discretion over customer outcomes.

Where it breaks: Decision design and testing.

Recommended solution

  1. Determine offers from an offer engine using business attributes (tenure, value, churn risk), not conversational style.
  2. Test for disparities with counterfactual evals (same case, different name or dialect).
  3. Monitor outcome distributions across segments.

Why it succeeds

Trade-off to manage: Less personalisation from conversation.

How you prove it worked:

  • Counterfactual eval gaps; outcome disparity reports.

Same pattern elsewhere: FinTech: a collections agent offers better repayment plans to customers who write in formal English.

Reference implementation

def offer_for(account):
    return offer_engine.best(tenure=account.tenure, value=account.arpu, churn=churn_model.score(account.id))

def counterfactual_test(cases):
    gaps = []
    for c in cases:
        base = run_retention_flow(c)
        for variant in name_and_dialect_variants(c):           # same case, different name/dialect
            if run_retention_flow(variant).offer_id != base.offer_id:
                gaps.append((c.id, variant.variant))
    return gaps
Key takeaway

Same facts, same outcome, whatever the name or accent.

ComplianceTelco

Problem statement

A carrier's bot gives wrong porting advice for a week. The AI platform team, the care product owner, the knowledge team and the vendor each think another group owns the fix. Nobody leads the incident, and the issue continues.

The anti-pattern

Shared, undefined ownership.

Think of it this way: Four people watching a pot boil over, each assuming someone else will turn off the heat.

Why the current design fails

  • No RACI for AI behaviour and content.
  • Incident process doesn't name AI owners.
  • Vendors' responsibilities unclear.

Root cause: Undefined ownership.

Where it breaks: Operating model.

Recommended solution

  1. Define a RACI per AI use case (product owner accountable; platform, content and vendor responsibilities).
  2. Include AI in incident management with named on-call owners.
  3. Review ownership when teams or vendors change.

Why it succeeds

Trade-off to manage: None significant.

How you prove it worked:

  • Time to assign ownership in incidents.

Same pattern elsewhere: FinTech: a bank's AI disclosure error goes unfixed because compliance, product and IT each wait for the others.

Reference implementation

RACI = {
    "care_bot": {"accountable": "VP Digital Care", "responsible": {"platform": "AI Platform", "content": "Knowledge Team",
                 "vendor": "Vendor Mgmt"}, "on_call": "pagerduty:care-ai"},
}

def open_incident(use_case, summary):
    r = RACI[use_case]
    return incidents.create(summary, owner=r["accountable"], page=r["on_call"])

Call records used to fine-tune a model without a legal basis

ComplianceTelco

Problem statement

A carrier's data-science team fine-tunes a model on two years of care transcripts and call-detail data to improve churn conversations. No one checked whether customer consent and CPNI rules allow this use. The privacy team halts the project and the model must be deleted.

The anti-pattern

Training on customer data unreviewed.

Think of it this way: Using customers' letters to train new staff without asking whether that's allowed.

Why the current design fails

  • Data reused for a new purpose without assessment.
  • No consent or legal-basis check.
  • No data lineage for training sets.

Root cause: Training-data governance missing.

Where it breaks: Data governance.

Recommended solution

  1. Require a privacy and legal review (purpose, legal basis, consent, CPNI) before using customer data for training.
  2. Minimise and de-identify training data.
  3. Record lineage so models can be traced and retrained if data must be removed.

Why it succeeds

Trade-off to manage: Slower experimentation.

How you prove it worked:

  • Training datasets without approval records.

Same pattern elsewhere: FinTech: a bank trains on customer emails without checking GLBA and privacy notices.

Reference implementation

TRAINING_USE_REVIEW = ["purpose", "legal_basis", "consent", "cpni_rules", "dpia_ref"]

def approve_training_dataset(ds):
    missing = [k for k in TRAINING_USE_REVIEW if not ds.review.get(k)]
    if missing: raise PermissionError(f"privacy/legal review incomplete: {missing}")
    ds = deidentify(minimise(ds, fields=["transcript_text", "intent"]))
    lineage.record(dataset=ds.id, sources=ds.source_ids, model_targets=[])   # traceable for removal
    return ds
Key takeaway

Training is a new purpose. Check you're allowed.

Problem statement

A European carrier adds an AI feature that infers its care agents' emotions from their voice during calls and feeds it into performance dashboards. The EU AI Act prohibits emotion-recognition systems in the workplace (with narrow exceptions), and the works council challenges it.

The anti-pattern

Deploy vendor AI features unclassified.

Think of it this way: Fitting a lie detector to every employee's chair.

Why the current design fails

  • The use case wasn't classified against AI Act risk categories.
  • Vendor features enabled by default.
  • No legal or employee-representative review.

Root cause: No AI risk classification before deployment.

Where it breaks: Governance.

Recommended solution

  1. Classify every AI use case against the AI Act categories (prohibited, high-risk, limited, minimal) before deployment.
  2. Disable prohibited features in vendor products.
  3. Involve legal, privacy and employee representatives for workplace AI.

Why it succeeds

Trade-off to manage: None significant.

How you prove it worked:

  • Inventory entries without risk classification.

Same pattern elsewhere: FinTech: a bank uses AI to infer customers' emotions to adjust collections strategies without assessing legal risk.

Reference implementation

AI_ACT_CATEGORY = {
    "workplace_emotion_recognition": "prohibited",
    "credit_scoring": "high_risk",
    "customer_chatbot": "limited",       # transparency obligations
    "spam_filter": "minimal"}

def register_use_case(uc):
    cat = AI_ACT_CATEGORY.get(uc.function) or legal.classify(uc)
    if cat == "prohibited":
        vendor_config.disable(uc.vendor, feature=uc.feature)
        raise PermissionError("prohibited AI practice")
    return inventory.add(uc, ai_act_category=cat, reviewers=["legal", "privacy", "works_council"])
Key takeaway

ComplianceTelco

Problem statement

A carrier's AI policy says "AI must not make account changes without customer confirmation." An audit finds three agents that change plans without confirmation, because the policy lives in a PDF and isn't enforced in any system.

The anti-pattern

Policy only in a PDF.

Think of it this way: A speed limit sign on a road with no speed cameras and no police.

Recommended solution

  1. Map each policy statement to a technical control (tool preconditions, pipeline checks, monitoring).

Why it succeeds

How you prove it worked:

  • Policy statements without mapped controls.

Reference implementation

POLICY_CONTROLS = {
    "AI-POL-3.1 No credit decisions by AI":      "tool: credit_decision not exposed to agents",
    "AI-POL-4.2 Human approval > $500 refunds":  "tool precondition in issue_refund",
    "AI-POL-5.1 PII redacted in logs":           "collector redaction processor",
}

def control_coverage():
    tested = {p: controls_test(p) for p in POLICY_CONTROLS}

            "passing": mean(tested.values()), "failing": [p for p, ok in tested.items() if not ok]}

class Override(BaseModel):
    case_id: str; ai_recommendation: str; human_decision: str

@schedule(cron="0 8 1 * *")
def monthly_override_review():

Human review queue with no SLA or capacity plan

ComplianceFinTech

Problem statement

A bank routes high-risk AI fraud decisions to human analysts. Volume grows faster than the team, and the queue reaches 4 days. Legitimate customers' cards stay blocked, and complaints surge.

The anti-pattern

Review step without capacity planning.

Think of it this way: A checkpoint with one guard and a growing queue of cars.

Why the current design fails

  • Review step without capacity planning.
  • No SLA or prioritisation.
  • Automation volume changes without staffing changes.

Root cause: Human-in-the-loop designed as a step, not as a service.

Where it breaks: Operations design.

Recommended solution

  1. Set SLAs for review queues and plan capacity from forecast volumes.
  2. Prioritise by risk and customer impact; auto-resolve low-risk cases with safeguards.
  3. Monitor queue age and alert before SLA breaches.

Why it succeeds

Trade-off to manage: Staffing costs, or accepting more automation risk at the margin.

How you prove it worked:

  • Queue age, throughput and SLA compliance.
