20AI Leadership Anti-Patterns

Most enterprise AI value is lost in operating models, not architectures. These are the organizational patterns that keep good technology from reaching production.

20.1

Proof-of-concept purgatory

AdoptionCost

Problem statement

A bank has run 60 GenAI proofs of concept in 18 months. Four reached production. Each PoC had its own stack, no production owner, and success criteria of "the demo worked".

The anti-pattern

PoCs are funded as innovation theatre: easy to start, no path to production, no exit criteria, and no production-grade requirements (security, data, evals) in scope.

Why the current design fails

  • Demos skip the hard 80%: data access, security review, evaluation, integration and change management.
  • No owner or budget for production. PoCs end and nothing happens.
  • Fragmented stacks make each success a one-off.

Recommended solution

Replace PoCs with production-intent pilots:

  • Entry: business owner, value hypothesis with a KPI baseline, data access confirmed, risk tier assigned.
  • Build on the shared platform (gateway, guardrails, evals, observability) from day one.
  • Exit criteria agreed upfront: eval thresholds, KPI movement in a controlled pilot, security and risk sign-off.
  • Stage gates with a scale/stop decision at 8–12 weeks, and production budget pre-allocated for winners.

Why it succeeds

Every pilot exercises the real path to production, so successes can scale immediately. Clear exit criteria kill weak ideas early and free capacity, and the shared platform makes each new pilot cheaper than the last.

Reference implementation

PILOT_GATES = {
    "entry":   ["business_owner", "kpi_baseline", "data_access_approved", "risk_tier"],
    "week_6":  ["eval_suite_passing", "security_review_started", "pilot_users_onboarded"],
    "week_12": ["kpi_delta >= target", "risk_signoff", "run_cost_per_unit <= budget"],
}
decision = "scale" if all(check(g) for g in PILOT_GATES["week_12"]) else "stop_or_pivot"
Key takeaway

Run pilots that are designed to graduate: production platform, agreed exit criteria, and a scale-or-stop decision on a fixed date.

Follow-up to expect

How would you triage a portfolio of 60 stalled PoCs?

20.2

Technology-first use-case selection

AdoptionCost

Problem statement

An executive asks "Where can we use agents?" Teams respond with agent ideas for low-value, low-volume processes, and the portfolio produces impressive demos with negligible financial impact.

The anti-pattern

Starting from a technology ("we need an agent strategy") and searching for problems, rather than starting from value pools and constraints.

Why the current design fails

  • Low business impact: use cases chosen for novelty, not value.
  • Feasibility blind spots: data readiness and risk are discovered late.
  • Loss of sponsor confidence when results don't move P&L metrics.

Recommended solution

Run a value-led portfolio process:

  • Map value pools by function (process volumes, cost per transaction, error costs, revenue levers).
  • Score candidates on value, feasibility (data readiness, integration, skills) and risk (regulatory tier, reversibility).
  • Choose the simplest effective technique for each: rules, classical ML, RAG, workflow plus LLM, or agent.
  • Balance the portfolio between quick wins and strategic bets, and review quarterly.

Why it succeeds

Investment flows to measurable value, and feasibility and risk are known before build. Matching technique to problem avoids over-engineering, which keeps sponsors confident and funding flowing.

Reference implementation

def priority(uc):
    value = uc.annual_volume * uc.unit_cost_saved + uc.revenue_uplift
    feasibility = mean([uc.data_readiness, uc.integration_ease, uc.team_skill])        # 0–1
    risk_penalty = {"low": 1.0, "medium": 0.8, "high": 0.6}[uc.risk_tier]
    return value * feasibility * risk_penalty

roadmap = sorted(candidates, key=priority, reverse=True)[:12]
Key takeaway

Start from value pools, not technology. Score by value, feasibility and risk, then use the simplest technique that works.

20.3

Every team builds its own AI stack

CostScaleSecurity

Problem statement

Twelve product teams each build their own RAG pipeline, prompt management, guardrails and logging. Security reviews take months because every stack is different, and a vulnerability fix has to be applied twelve times.

The anti-pattern

No shared AI platform. Each team re-solves the same infrastructure problems, with inconsistent quality and controls.

Why the current design fails

  • Duplicated cost and effort on undifferentiated plumbing.
  • Inconsistent controls and slow, bespoke security reviews.
  • No economies of scale in evaluation, observability, vendor commitments or skills.

Recommended solution

Establish an AI platform team and a "paved road":

  • Platform capabilities: model gateway (routing, metering, guardrails), retrieval and ingestion services, prompt registry, evaluation harness, tracing, agent runtime, MCP registry, identity integration.
  • Pre-approved patterns with security sign-off already done, so teams using the paved road get fast-track reviews.
  • A center of excellence for standards, reusable assets, training and architecture review.
  • Measure platform success by time-to-production and adoption, not by features shipped.

Why it succeeds

Teams ship faster because the hard, common parts are solved once. Security and risk review the platform once and the patterns many times. Costs fall through shared capacity and vendor leverage.

Reference implementation

# Paved road: a new use case is mostly configuration on shared services
app = PlatformApp(
    name="claims-summary", owner="claims-ops", risk_tier="medium",
    model_policy="mid-tier-default", guardrails="baseline+pii",
    retrieval=platform.retrieval(index="claims-kb", acl=True),
    evals=platform.evals(suite="claims_summary_v1", gate=0.9),
    tracing=True, budget_usd_month=4000)
app.deploy(env="pilot")
Key takeaway

Build the paved road once. A shared AI platform turns every new use case into configuration plus domain work, and makes security reviews fast.

Follow-up to expect

20.4

Measuring success by model accuracy instead of business KPIs

Adoption

Problem statement

A document-processing program reports 96% extraction accuracy to the board. Finance asks how much processing cost fell, and nobody knows. The manual team is the same size because exceptions still go to humans.

The anti-pattern

Success is defined by technical metrics (accuracy, F1, latency) without connecting them to business outcomes, baselines or process change.

Why the current design fails

  • Technical success, business failure: accuracy gains don't automatically change cost or revenue.
  • No baseline, so impact can't be shown.
  • Process unchanged: humans still do the same work around the AI.

Recommended solution

Build a value tree:

  • Business KPI: cost per case, cycle time, revenue per rep, loss ratio, CSAT.
  • Operational drivers: straight-through-processing rate, handling time, exception rate.
  • AI metrics: accuracy, confidence calibration, latency, cost per call.

Baseline the KPIs before launch. Redesign the process so AI changes work allocation (for example, auto-approve high-confidence cases and route only exceptions). Report all three levels together.

Why it succeeds

Leadership sees AI performance in financial terms, and technical teams see which model improvements actually move the business. Process redesign is where the value is realized.

Reference implementation

value_tree = {
    "cost_per_invoice":      {"baseline": 4.10, "target": 1.80},
    "straight_through_rate": {"baseline": 0.00, "target": 0.70},     # driver
    "field_accuracy":        {"baseline": None, "target": 0.97},     # AI metric
    "confidence_calibration_ece": {"target": "< 0.05"},              # enables auto-approval
}
auto_approve = lambda doc: doc.min_field_confidence >= 0.95 and doc.vendor in TRUSTED_VENDORS
Key takeaway

Accuracy is an input, not an outcome. Tie model metrics to business KPIs through a value tree, and redesign the process to capture the value.

20.5

Ignoring change management and workforce impact

Adoption

Problem statement

A contact center deploys an excellent agent-assist tool. Agents distrust it, fear it's monitoring them for headcount cuts, and ignore suggestions. Usage falls to 20% within two months.

The anti-pattern

AI deployment is treated as a technology project. Users aren't involved in design, roles and incentives aren't updated, and concerns aren't addressed.

Why the current design fails

  • Distrust and passive resistance regardless of tool quality.
  • Misaligned incentives: metrics still reward old behaviours.
  • Missed design insight from frontline users.

Recommended solution

  • Co-design with frontline users, using their workflows and their language.
  • Communicate a clear narrative: what changes, what doesn't, how roles evolve, and how data is (and isn't) used.
  • Training and champions in each team, with feedback loops into the product backlog.
  • Update KPIs and incentives to reward effective AI-assisted work.
  • Engage HR, works councils and unions early where relevant.

Why it succeeds

Users trust tools they helped shape and understand. Aligned incentives make usage rational, and feedback loops keep improving the tool, which increases trust further.

Reference implementation

adoption_dashboard = {
    "suggestion_acceptance_rate": by_team(accepted / shown),
    "trust_score_survey": quarterly_survey("I trust the assistant's suggestions"),
    "feedback_items_closed": backlog.closed(label="user-feedback", period="month"),
    "handle_time_delta": compare(handle_time, cohort="assisted", control="unassisted"),
}
Key takeaway

AI adoption is a people change. Co-design, communicate, train, and realign incentives, or the best tool goes unused.

Follow-up to expect

How would you address workforce concerns in a unionized environment?

20.6

Building everything, or buying everything

LeadershipCost

Problem statement

The steering committee asks whether to build an in-house RAG platform or buy a vendor product. Two camps argue "always build for control" versus "always buy for speed".

The anti-pattern

A blanket build-or-buy preference applied to the whole AI stack.

Why the current design fails

  • Build-vs-buy is a portfolio decision per layer, not one decision.
  • Building commodity layers wastes scarce engineers on undifferentiated work.
  • Buying the differentiating layer hands the advantage to a vendor and creates lock-in.

Recommended solution

Decide per layer using differentiation, time-to-value, total cost of ownership (TCO), control and risk:

  • Buy or use managed for commodity infrastructure: foundation models, vector DB, observability.
  • Build what encodes proprietary advantage: domain data pipelines, retrieval tuned to your corpus, evals that define quality for your business, workflow integration.
  • Partner where speed matters but customization is needed.
  • Protect optionality with abstraction layers and data portability, and revisit annually.

Why it succeeds

Engineers spend their time on what differentiates the business, while commodity layers improve with the market. In one example, the team bought a managed vector DB and observability tool, and built the ingestion pipeline, permission-aware retrieval service and eval suite because those encoded the company's data and quality definitions.

Reference implementation

CRITERIA = {"differentiation": .3, "time_to_value": .2, "tco": .2, "control": .15, "risk": .15}

def decide(layer_scores):                  # scores 1–5; high differentiation favours build
    build = sum(CRITERIA[c] * s["build"] for c, s in layer_scores.items())
    buy = sum(CRITERIA[c] * s["buy"] for c, s in layer_scores.items())
    return "build" if build - buy > 0.5 else "buy" if buy - build > 0.5 else "partner"

decisions = {layer: decide(scores) for layer, scores in workshop_scores.items()}
Key takeaway

Build what differentiates, buy what's commodity, and keep the seams portable. Decide per layer, not once for the stack.

Follow-up to expect

Should we build our own RAG platform or buy a vendor product?

20.7

Chasing leaderboards and model churn

LeadershipQualityCost

Problem statement

A new model just topped the public benchmarks. The team wants to switch every workload to it this sprint.

The anti-pattern

Model choice driven by headlines: either switch everything immediately, or refuse to switch at all.

Why the current design fails

  • Public benchmarks rarely match your task, data or constraints.
  • Switching on headlines causes regressions in formats, refusals and tool-calling behaviour, and constant churn.
  • Refusing to switch leaves cost and quality on the table.

Recommended solution

Make model choice an evidence-based, low-cost decision:

  • Put all calls behind an LLM gateway so models are swappable by configuration.
  • Run every candidate through your own task-specific eval suite, comparing quality, latency, cost and safety per use case.
  • Roll out winners per route via canary; pin versions in production; track deprecations; keep a fallback model.

Why it succeeds

Gains are captured where they're real and regressions are avoided where they aren't. In one example, the new model won on reasoning-heavy analysis (+6 points) but regressed JSON compliance for extraction; the team switched one route, kept the other, and saved 30% on a third by moving it to a smaller model with equal scores.

Reference implementation

def evaluate_candidate(candidate, routes):
    decisions = {}
    for route in routes:
        cur, new = run_evals(route, ROUTE_MODEL[route]), run_evals(route, candidate)
        better = new.quality >= cur.quality + 0.02 and new.safety >= cur.safety and new.format_ok >= cur.format_ok
        cheaper = new.quality >= cur.quality - 0.005 and new.cost < cur.cost * 0.8
        decisions[route] = "canary" if better or cheaper else "keep"
    return decisions
Key takeaway

Treat new models as candidates, not upgrades. A gateway plus your own evals turns model churn into routine, per-route decisions.

Follow-up to expect

A new model just topped the benchmarks. The team wants to switch everything. Your call?

20.8

Governance bolted on at the end

LeadershipCompliance

Problem statement

Legal blocked a customer-facing AI launch two weeks before go-live over data and safety concerns. The team had never engaged them during the build.

The anti-pattern

Risk review is a single gate at the end of delivery, after design decisions are locked in.

Why the current design fails

  • Late surprises cause rework and adversarial relationships between delivery and risk teams.
  • Real risks (prompt injection, data leakage, biased outcomes, IP, regulatory duties) go unmanaged during pilots.
  • Every use case gets the same heavy review, so low-risk work queues behind high-risk work.

Recommended solution

Make governance part of delivery, scaled to risk:

  • Risk tiering at intake (internal productivity vs customer-facing vs consequential decisions about people), with proportionate controls per tier.
  • Bake controls into the paved road: data classification and PII redaction, approved models with agreed data terms, guardrails, logging and audit trails.
  • For higher tiers: a system card, red-team results against the OWASP LLM Top 10, an impact assessment, human-oversight design and incident playbooks.
  • Align to a framework (NIST AI RMF, ISO/IEC 42001) and map EU AI Act obligations with Legal.
  • Run an AI governance council (Legal, Security, Privacy, business) that approves within an SLA.

Why it succeeds

Most use cases clear quickly through standard controls, freeing review capacity for the few high-risk ones. In one example, 70% of use cases (internal, low-risk) were cleared in days.

Reference implementation

TIERS = {
    "internal_productivity": {"controls": ["pii_redaction", "approved_models", "logging"], "review_days": 3},
    "customer_facing":       {"controls": ["+guardrails", "+red_team", "+system_card"], "review_days": 10},
    "consequential":         {"controls": ["+impact_assessment", "+human_oversight", "+incident_playbook"], "review_days": 20},
}

def intake(use_case):
    tier = classify_tier(use_case)       # at intake, not at launch
    return governance.open(use_case, tier=tier, required=TIERS[tier]["controls"], sla_days=TIERS[tier]["review_days"])
Key takeaway

Governance that arrives at the end blocks launches. Tier risk at intake and build the controls into the paved road.

Follow-up to expect

Legal blocked your launch two weeks before go-live. How do you prevent that next time?

20.9

The wrong team shape for applied AI

LeadershipAdoption

Problem statement

You have headcount for 10 people to build applied AI products. One proposal is ten ML PhDs; another is ten full-stack engineers who know prompting.

The anti-pattern

Staffing an applied AI team as either a research lab or a pure app team.

Why the current design fails

  • Applied AI value comes mostly from data, integration, evaluation and product judgment, not model research.
  • A research-heavy team builds impressive prototypes nobody ships.
  • A team with no ML depth can't debug quality or design evaluations.

Recommended solution

Hire for the full delivery loop:

  • AI/ML engineers who build LLM systems end to end (retrieval, agents, evals).
  • A data engineer for pipelines, connectors and quality; a platform engineer for the gateway, reliability and scale.
  • An AI product manager who owns outcomes; an evaluation lead who owns golden sets and error analysis.
  • Access to domain experts for rubrics and labeling, and a design partner for trust-building UX.
  • Hire T-shaped people with shipping records, set up a career ladder, and upskill existing engineers through pairing.

Why it succeeds

Every stage from data to adoption has an owner, so prototypes become products. Example shape: 4 AI engineers, 2 platform, 1 data engineer, 1 AI PM, 1 eval lead, 1 designer at 50%, plus 3 SME hours a week from each business unit served.

Reference implementation

TEAM = {"ai_engineer": 4, "platform_engineer": 2, "data_engineer": 1,
        "ai_product_manager": 1, "eval_lead": 1, "designer": 0.5}
SME_HOURS_PER_WEEK = {bu: 3 for bu in BUSINESS_UNITS_SERVED}

LOOP = ["data", "retrieval/agents", "evaluation", "platform/reliability", "product/outcomes", "ux/adoption"]
coverage = {stage: [r for r, owns in ROLE_OWNS.items() if stage in owns and TEAM.get(r)] for stage in LOOP}
assert all(coverage.values()), f"unowned stages: {[s for s, r in coverage.items() if not r]}"
Key takeaway

Applied AI is a delivery loop, not a research problem. Staff every stage, from data and evals to product and adoption.

Follow-up to expect

You have headcount for 10. Who do you hire to build applied AI products?

20.10

Launch and leave

LeadershipQualityReliability

Problem statement

Six months after launch, usage dropped and answers got worse. Nobody changed any code. The proposed fix is to retrain the model.

The anti-pattern

The AI feature is treated as a finished project after launch, with no owner, monitoring or feedback loop.

Why the current design fails

  • AI systems drift even when code doesn't: content changes, user behaviour shifts, providers update models, new edge cases appear.
  • Without ownership and online monitoring, quality decays silently and trust erodes.
  • Retraining is proposed without any evidence of what changed.

Recommended solution

Treat AI features as living products with LLMOps:

  • A named owner and on-call rotation.
  • Online monitoring of quality (sampled judge scores, feedback, escalation and reformulation rates), freshness, latency and cost, with SLOs and alerts.
  • A feedback loop: weekly failure triage into the eval set, monthly metric reviews with business owners, re-evaluation whenever providers update models.
  • Change management: training, champions, in-product guidance and release notes.

Why it succeeds

Drift is detected and fixed continuously instead of discovered by users. In one example, a weekly 30-minute failure review fed 40 new cases a month into the golden set; online quality recovered from 81% to 90% and usage regained its peak within a quarter.

Reference implementation

@schedule(cron="0 10 * * MON")
def weekly_failure_review():
    failures = traces.sample(feedback="down", days=7, n=40) + traces.sample(escalated=True, days=7, n=20)
    for f in triage_session(failures, owner=OWNER):
        golden.add(f.as_eval_case())
    report.post(channel="#ai-assistant", metrics=online_quality(days=7), new_cases=len(failures))

provider.on_model_update(lambda m: run_full_evals(model=m))      # re-evaluate on provider changes
Key takeaway

AI quality decays without ownership. Run AI features as products with SLOs, a weekly failure review and change management.

Follow-up to expect

Six months after launch, usage dropped and answers got worse. Nobody changed anything. Why?

20.11

Overpromising to executives

LeadershipAdoption

Problem statement

The CEO announced that the AI assistant will handle 80% of customer queries by Q2. Your data says 45% is realistic at the current quality bar.

The anti-pattern

Committing to deterministic targets for a probabilistic system, either by trying to hit the number anyway or by telling the CEO they're wrong.

Why the current design fails

  • Pressure to hit the target leads to cutting corners on quality and safety.
  • When the target slips, the AI program loses credibility and budget.
  • A flat "you're wrong" damages trust without offering a path.

Recommended solution

Reset expectations early, with evidence and a path:

  • Show containment by query type, error rate at each automation level and the customer impact of wrong answers.
  • Offer scenarios with trade-offs: 45% at today's quality bar by Q2; 60% by Q3 with listed investments; 80% only with a higher error rate or narrower scope.
  • Agree an error budget and guardrail metrics (CSAT, compliance) that can't be traded away.
  • Report progress on a regular cadence with the same metrics.

Why it succeeds

Leadership gets a choice instead of a surprise, and quality guardrails are protected. In one example, the executive team agreed to "50% by Q2, 70% by Q4, CSAT ≥ 4.3"; the team beat the Q2 number, which built the credibility to win budget for the next phase.

Reference implementation

def scenarios(by_query_type):
    out = []
    for target_quality in (0.95, 0.92, 0.88):            # stricter → lower containment
        contained = sum(v.volume for v in by_query_type if v.accuracy >= target_quality)
        out.append({"quality_bar": target_quality, "containment": contained / total_volume(by_query_type),
                    "investments": investments_needed(target_quality)})
    return out

GUARDRAILS = {"csat_min": 4.3, "compliance_violations": 0}   # not tradeable for containment
Key takeaway

Probabilistic systems need scenario-based commitments. Offer trade-offs with evidence, agree guardrail metrics, and report against them.

Follow-up to expect

Your CEO announced 80% automation by Q2; your data says 45%. What do you do?

20.12

System design that starts with the model

LeadershipQuality

Problem statement

In an architecture review (or a design interview), the first sentence is "I'd use a frontier model with LangChain", before anyone has asked about users, scale, data or risk.

The anti-pattern

The design starts from a model and framework choice instead of requirements and constraints.

Why the current design fails

  • Requirements such as latency, cost, permissions and risk end up retrofitted around an early tool choice.
  • Model and framework choices are the most volatile part of the stack, so the design ages fastest where it began.
  • Reviewers and interviewers read it as a lack of systems thinking.

Recommended solution

Use a six-step design template:

  1. Clarify users, scale (documents, QPS), latency and cost targets, and risk level.
  2. Data: sources, ingestion, chunking, metadata, freshness, permissions.
  3. Retrieval: hybrid + rerank + compression, and why each.
  4. Generation or agent: workflow vs agent, tools, guardrails, human approval.
  5. Evaluation: golden set, offline metrics, online feedback, tracing.
  6. Operations: latency and cost budget, caching, monitoring, failure modes, rollout.

Why it succeeds

The design is anchored in durable requirements, so model and framework become replaceable details chosen last. Tracing every requirement to a component makes gaps visible during review rather than in production.

Reference implementation

DESIGN_TEMPLATE = ["requirements", "data", "retrieval", "generation_or_agent", "evaluation", "operations"]

def review(design):
    missing = [s for s in DESIGN_TEMPLATE if not design.sections.get(s)]
    untraced = [r for r in design.requirements if not any(r.id in c.satisfies for c in design.components)]
    return {"missing_sections": missing, "untraced_requirements": untraced,
            "model_chosen_before_requirements": design.first_decision == "model"}
Key takeaway

Start from requirements and risk, and choose the model last. A design should trace every requirement to a component.

Follow-up to expect

Walk me through how you'd design an enterprise document Q&A system over 5 million documents with strict permissions.
