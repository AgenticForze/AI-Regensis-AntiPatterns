10Tool Design, MCP & A2A

The Model Context Protocol (MCP) standardizes how agents reach tools and data. Agent-to-agent (A2A) protocols standardize how agents reach each other. Both widen the attack surface if they're adopted without identity and governance.

10.1

Custom tool integrations per agent instead of a shared protocol

CostScale

Problem statement

Eight teams build agents that need Salesforce, ServiceNow and SharePoint. Each writes its own connector with its own auth, error handling and schemas. Twenty-four integrations do roughly the same job, all maintained separately.

The anti-pattern

Tool integrations are hand-coded inside each agent codebase and tied to one framework or vendor SDK.

Why the current design fails

  • N×M integration cost. Every agent × system pair is built and maintained separately.
  • Inconsistent security. Each connector handles credentials and permissions differently.
  • Lock-in. Integrations written for one framework can't be reused by another.

Recommended solution

Standardize on MCP servers for tools and data:

  • Build or adopt one MCP server per system of record, owned by the platform or system team.
  • Expose servers through an MCP gateway or registry that handles authentication, authorization, rate limits and audit. All three hyperscalers now offer managed gateways or toolboxes for this.
  • Publish a catalog of approved servers. Agents discover and connect instead of re-implementing.
  • Version server interfaces and test them like APIs.

Why it succeeds

Integration cost drops from N×M to N+M. Security controls are implemented once at the gateway and applied consistently. Any MCP-capable framework or model can reuse the same integrations, which reduces lock-in.

Reference implementation

# One MCP server per system of record, owned by the platform team
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("servicenow")

@mcp.tool()
def create_incident(short_description: str, urgency: Literal["1", "2", "3"], ci: str) -> dict:
    """Create a ServiceNow incident. Use for confirmed outages only."""
    return snow.incidents.create(short_description=short_description, urgency=urgency, cmdb_ci=ci)

# Any agent, any framework: connect through the governed gateway
tools = mcp_client.connect("https://mcp-gateway.corp/servicenow", auth=user_obo_token).list_tools()
Key takeaway

Integrate each system once as an MCP server, govern access at a gateway, and let every agent reuse it.

10.2

MCP servers and A2A endpoints without authentication or trust boundaries

Security

Problem statement

A developer installs a community MCP server that claims to summarize GitHub issues. Its tool description contains hidden instructions telling the agent to read ~/.aws/credentials and include them in a "diagnostic" call.

The anti-pattern

Any MCP server or remote agent can be connected. Tool descriptions and agent responses are trusted implicitly. Remote endpoints have no authentication, or use shared static keys.

Why the current design fails

  • Tool poisoning. Malicious instructions hidden in tool metadata or results steer the agent.
  • Rug pulls. A server's tools change after approval.
  • Impersonation. Without mutual authentication, a rogue agent can pose as a trusted one in A2A exchanges.
  • Data exfiltration through tools that send data to external endpoints.

Recommended solution

Apply zero trust to tools and agents:

  • Only allow servers from an internal registry. Review them and pin versions with hashes of tool definitions, and alert on any change.
  • Authenticate with OAuth 2.1 / OIDC (as the MCP authorization spec describes) or mTLS. Give each agent its own workload identity, and verify signed agent cards for A2A.
  • Run local servers in sandboxes with no access to secrets. Restrict network egress to declared domains.
  • Treat tool descriptions and outputs as untrusted input: scan them for injection patterns, and never let them change the agent's permissions.

Why it succeeds

Only reviewed, pinned code reaches agents. Strong identity prevents impersonation, and sandboxing plus egress limits stop exfiltration even if a tool is compromised. Change detection closes the rug-pull gap.

Reference implementation

APPROVED = registry.load("mcp-allowlist.yaml")      # name, url, version, sha256(tool_defs)

def connect_tool_server(name, agent_identity):
    entry = APPROVED[name]
    client = MCPClient(entry.url, auth=oauth.client_credentials(agent_identity, scope=entry.scope),
                       mtls=True)
    defs = client.list_tools()
    if sha256(canonical(defs)) != entry.defs_hash:
        security.alert("mcp_definition_changed", server=name); raise UntrustedServer(name)
    return [wrap_untrusted_output(t) for t in defs]      # outputs scanned before reaching the model
Key takeaway

MCP and A2A make integration easy, including for attackers. Allow-list, pin, authenticate, sandbox, and treat tool metadata as untrusted input.

Follow-up to expect

10.3

Over-privileged service accounts for agents

SecurityCompliance

Problem statement

A sales-assistant agent runs under a service account with admin rights to the CRM "to avoid permission errors". A prompt-injected email causes it to export the full customer list.

The anti-pattern

Agents run as one broad service identity, not as the user they act for, with standing access to everything they might ever need.

Why the current design fails

  • Confused-deputy attacks. Agents act with more privilege than the requesting user.
  • Maximum blast radius for any injection or bug.
  • Audit gaps. Logs show "service account" rather than who actually triggered the action.

Recommended solution

Apply least privilege with delegated identity:

  • Give each agent its own workload identity (Entra Agent ID, AWS IAM roles with AgentCore Identity, Google service identities).
  • Use on-behalf-of (OBO) delegation, so actions run with the intersection of the user's and the agent's permissions.
  • Use narrow, task-scoped OAuth scopes and short-lived tokens. Grant elevation just in time, with approval.
  • Log both the user and the agent identity on every action.

Why it succeeds

An agent can never do more than the user it serves, which neutralizes confused-deputy attacks. Short-lived scoped tokens shrink blast radius, and dual-identity logs give auditors a complete chain of accountability.

Reference implementation

def call_crm(action, args, user_token, agent):
    token = idp.on_behalf_of(user_assertion=user_token, client=agent.identity,
                             scopes=SCOPES_FOR[action])            # e.g. crm.contacts.read
    if action in HIGH_RISK:
        approvals.require(user=token.sub, agent=agent.id, action=action)
    resp = crm.request(action, args, bearer=token.access_token)    # expires in minutes
    audit.log(user=token.sub, agent=agent.id, action=action, resource=args.get("id"))
    return resp
Key takeaway

An agent should never be more powerful than the person it serves. Give agents their own identity, delegate with OBO, and keep scopes narrow and short-lived.

10.4

Provider-specific tool code in every app

CostScale

Problem statement

The document-search and ticketing tools were written inside one assistant using one provider's function-calling format. Moving them to a second app means rewriting them, along with their auth and audit.

The anti-pattern

Tools are implemented inside each application, in each model provider's tool-calling format, with their own credentials and logging.

Why the current design fails

  • Every new app or model provider means rewriting the same tools.
  • Auth, rate limits and audit logic are duplicated and drift apart.
  • Nobody owns the tool as a product, so quality depends on which app copy you use.

Recommended solution

  • Package shared tools as MCP servers owned by the platform team, so any MCP-capable app or agent reuses them.
  • Centralize authentication, authorization and audit in the server or an MCP gateway.
  • Write thin clients per host application instead of re-implementing tools.
  • Track reuse: number of apps using each server and time to add a tool to a new app.

Why it succeeds

A tool is built and secured once and reused by every app and model, so adding a new channel takes hours instead of a rewrite. One owner keeps descriptions, schemas and controls consistent.

Reference implementation

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("support-tools")

@mcp.tool()
def search_docs(query: str, k: int = 5) -> list[dict]:
    """Search the support knowledge base. Returns titles, snippets and doc ids."""
    return [{"id": h.id, "title": h.title, "snippet": h.text[:300]} for h in kb.search(query, k=k)]

@mcp.tool()
def create_ticket(summary: str, priority: str = "P3") -> dict:
    """Open a support ticket for the signed-in user."""
    return tickets.create(summary=summary, priority=priority, requester=current_user())

if __name__ == "__main__":
    mcp.run()            # any MCP-capable assistant or agent can now connect
Key takeaway

Build a tool once, as an MCP server with its own owner, auth and audit. Don't rewrite it inside every app.

10.5

Agent given a raw SQL tool on the billing database

ReliabilityLatencySecurityTelcoCritical

Problem statement

To move fast, a carrier gives its care agent a run_sql tool on a read replica of the billing database. The agent writes queries that scan entire tables at peak (slowing the replica used by billing reports), and a prompt injection gets it to return other customers' invoices.

The anti-pattern

Raw SQL tool on the billing DB.

Think of it this way: Handing a visitor the keys to the archive room instead of fetching the file they need.

Why the current design fails

  • Generic power with no business boundaries.
  • No object-level authorisation.
  • Unpredictable load on shared systems.

Root cause: Exposing raw data access instead of task-shaped tools.

Where it breaks: Tool design.

Recommended solution

  1. Replace raw SQL with task-shaped tools (get_invoice_summary(account_id, period)) that enforce ownership and limits.
  2. If analytics needs SQL, use parameterised templates on a dedicated store with row-level security and query limits.
  3. Rate-limit and time-box tools that hit shared systems.

Why it succeeds

Trade-off to manage: Less flexibility; more tools to build.

How you prove it worked:

  • Query cost and cross-account access per tool.

Same pattern elsewhere: FinTech: an agent with SQL access to the core-banking reporting database exposes balances of other customers.

Reference implementation

@tool(rate_limit="10/min", timeout_s=3)
def get_invoice_summary(period: str, ctx: Session) -> dict:
    """Invoice totals and line categories for the caller's own account and one billing period."""
    account_id = ctx.verified_account_id                      # ownership from the session
    row = billing_ro.execute(
        "SELECT total, tax, line_category, amount FROM invoice_lines "
        "WHERE account_id = :a AND period = :p LIMIT 200", a=account_id, p=period)
    return summarize(row)
Key takeaway

Give agents verbs for the business, not a shell into the database.

10.6

Wire value date in the wrong time zone

ReliabilityFinTech

Problem statement

A corporate-banking agent schedules a wire "for tomorrow" for a client in Singapore. The tool takes value_date as a date with no time zone, and the agent computes "tomorrow" in UTC. The wire is scheduled a day late and misses a supplier deadline, incurring penalties.

The anti-pattern

Relative dates resolved by the model.

Think of it this way: Booking a meeting "at 9" without saying whose 9.

Why the current design fails

  • Relative dates resolved by the model.
  • No time-zone context in the tool.
  • Cut-off times and business days ignored.

Root cause: Ambiguous temporal parameters.

Where it breaks: Tool interface.

Recommended solution

  1. Provide a date-resolution tool or resolve relative dates in code using the client's time zone and calendar.
  2. Require explicit dates with time zone, and validate against cut-off times and holidays.
  3. Echo the resolved date in confirmation.

Why it succeeds

Trade-off to manage: None significant.

How you prove it worked:

  • Mismatches between requested and executed dates.

Same pattern elsewhere: Telco: a technician visit "tomorrow morning" is booked in the data centre's time zone.

Reference implementation

@tool
def resolve_value_date(expression: str, ctx: Session) -> dict:
    tz = ZoneInfo(ctx.client.timezone)                        # client's zone, not the server's
    d = dateparser.parse(expression, settings={"TIMEZONE": str(tz), "RETURN_AS_TIMEZONE_AWARE": True}).date()
    cal = holiday_calendar(ctx.wire.currency)
    if not cal.is_business_day(d) or past_cutoff(d, ctx.wire.currency, tz):
        d = cal.next_business_day(d)
    return {"value_date": d.isoformat(), "timezone": str(tz), "echo": f"Value date {d:%a %d %b %Y} ({tz})"}
Key takeaway

Never let the model guess what tomorrow means.

10.7

get_bill, get_invoice and get_statement all exist

ReliabilityTelco

Problem statement

A carrier's agent has three tools that return billing information from different systems: get_bill (legacy), get_invoice (new billing) and get_statement (finance). The agent picks inconsistently and gives customers numbers from the legacy system for accounts already migrated.

The anti-pattern

Overlapping tools from different systems.

Think of it this way: Three phone numbers for the same department, one of which goes to an empty office.

Why the current design fails

  • Overlapping tools with vague differences.
  • Legacy tools never retired.
  • The model can't tell which is current.

Root cause: Tool set mirrors system history, not tasks.

Where it breaks: Tool catalogue design.

Recommended solution

  1. Expose one tool per task (get_bill_summary) that routes internally to the right system based on migration status.
  2. Retire or hide legacy tools.
  3. Name and describe tools by what they're for and when not to use them.

Why it succeeds

Trade-off to manage: Routing logic moves into the tool layer.

How you prove it worked:

  • Tool-selection confusion in traces.

Same pattern elsewhere: FinTech: transfer, payment and send_money tools overlap, and the agent picks a slower rail.

Reference implementation

@tool
def get_bill_summary(period: str, ctx: Session) -> dict:
    """Use for any question about a customer's bill, invoice or statement. Not for payment history."""
    acct = ctx.verified_account_id
    if migration.status(acct) == "migrated":
        return new_billing.summary(acct, period)
    return legacy_billing.statement(acct, period)              # routing is internal, one tool for the task

# get_bill / get_invoice / get_statement removed from the agent's tool list
Key takeaway

One task, one tool. Hide the plumbing.

10.8

Transaction tool returns 10,000 rows

ReliabilityFinTech

Problem statement

A business-banking agent calls get_transactions(account) for a corporate account. The tool returns 10,000 transactions for the year. The response exceeds the context limit and the call fails, or is truncated and the agent analyses partial data.

The anti-pattern

Unbounded list tool.

Think of it this way: Asking for a book and being handed the whole library.

Why the current design fails

  • No filtering or pagination parameters.
  • Output size is unbounded.
  • Truncation is silent.

Root cause: Tools without size controls.

Where it breaks: Tool design.

Recommended solution

  1. Add filters (date range, amount, counterparty, category) and pagination with a sensible default page size.
  2. Return totals and counts with each page, and say when more pages exist.
  3. Provide aggregate tools for summary questions.

Why it succeeds

Trade-off to manage: More parameters to document.

How you prove it worked:

  • Response sizes and truncation events per tool.

Same pattern elsewhere: Telco: get_usage returns every data session for a month on an IoT account with thousands of SIMs.

Reference implementation

@tool
def list_transactions(start: date, end: date, min_amount: float | None = None,
                      counterparty: str | None = None, category: str | None = None,
                      page: int = 1, page_size: int = 25) -> dict:
    q = txns.query(start=start, end=end, min_amount=min_amount, counterparty=counterparty, category=category)
    items = q.page(page, page_size)
    return {"items": items, "total_count": q.count(), "total_amount": q.sum(),
            "page": page, "has_more": page * page_size < q.count()}

@tool
def spending_by_category(start: date, end: date) -> dict: return txns.aggregate(start, end, by="category")
Key takeaway

Every list tool needs filters, pages and totals.

10.9

Plan change executed without a preview

ReliabilityTelco

Problem statement

A carrier's agent has a change_plan tool that executes immediately. Customers don't see the prorated charges, lost promotions or device-installment effects until the next bill. Plan-change complaints and reversals rise.

The anti-pattern

Change executes immediately.

Think of it this way: A checkout that charges your card before showing the basket total.

Why the current design fails

  • No dry-run or quote mode.
  • Side effects aren't shown before execution.
  • Confirmation is based on the model's description.

Root cause: Write tools without a preview step.

Where it breaks: Tool design.

Recommended solution

  1. Split into preview_plan_change (returns prorated charges, promotions lost, effective date) and execute_plan_change (requires the preview id).
  2. Show the preview to the customer and require explicit confirmation.
  3. Use TMF679 product offering qualification or a quote API for eligibility and effects.

Why it succeeds

Trade-off to manage: One more step in the flow.

How you prove it worked:

  • Reversal and complaint rates after plan changes.

Same pattern elsewhere: FinTech: a loan-restructure tool executes without showing the new payment schedule and total interest.

Reference implementation

@tool
def preview_plan_change(subscription_id: str, new_offering_id: str) -> dict:
    q = tmf679.qualify(subscription_id, new_offering_id)
    return {"preview_id": q.id, "prorated_charge": q.proration, "promotions_lost": q.lost_promotions,
            "effective_date": q.effective_date, "eligible": q.eligible}

@tool
def execute_plan_change(preview_id: str, customer_confirmed: bool) -> dict:
    if not customer_confirmed:
        return {"status": "REFUSED", "why": "show the preview and get explicit confirmation first"}
    return orders.submit_from_preview(preview_id)
Key takeaway

Preview before you commit.

10.10

Bulk suspension reports success when 3 of 50 lines failed

ReliabilityCostTelco

Problem statement

An enterprise customer asks the agent to suspend 50 lines reported stolen in an office burglary. The bulk tool returns "success" because the batch was accepted. Three lines failed provisioning and stayed active. Fraudulent international calls on those lines cost $8,000.

The anti-pattern

Batch accepted reported as success.

Think of it this way: A courier reporting "all delivered" when three parcels were returned.

Why the current design fails

  • Bulk tools report batch acceptance, not per-item outcomes.
  • The agent tells the customer everything is done.
  • No follow-up on failures.

Root cause: Coarse success semantics for bulk operations.

Where it breaks: Tool response design.

Recommended solution

  1. Return per-item results (succeeded, failed with reason, pending) and overall counts.
  2. Make the agent report failures explicitly and retry or escalate them.
  3. Track asynchronous completion to the final state.

Why it succeeds

Trade-off to manage: Larger responses for bulk calls; summarise counts plus failures only.

How you prove it worked:

  • Items still active after bulk suspension requests.

Same pattern elsewhere: FinTech: a bulk card-block request reports success while two cards remain active.

Reference implementation

@tool
def suspend_lines(line_ids: list[str], reason: str) -> dict:
    results = [{"line_id": l, **oss.suspend(l, reason)} for l in line_ids]   # per-item status
    counts = Counter(r["status"] for r in results)
    return {"succeeded": counts["OK"], "failed": counts["FAILED"], "pending": counts["PENDING"],
            "failures": [r for r in results if r["status"] == "FAILED"],
            "track": [r["job_id"] for r in results if r["status"] == "PENDING"]}
# agent instructions: report failures explicitly; retry or escalate each failed line
Key takeaway

Bulk tools must report per-item truth.

Statement tool trusts the account id the model supplies

ReliabilityFinTechCritical

Problem statement

A bank's get_statement tool takes account_id as a parameter and returns the statement. The agent normally passes the customer's own account, but a user asks "show me the statement for account 4471-2208" and the agent passes it through. The tool returns another customer's statement.

The anti-pattern

Tool trusts model-supplied ids.

Think of it this way: A post office that hands over any parcel if you can read out the tracking number.

Why the current design fails

  • The tool trusts identifiers from the model.
  • No check that the account belongs to the authenticated user.
  • Classic insecure direct object reference.

Root cause: Missing object-level authorisation in tools.

Where it breaks: Tool authorisation.

Recommended solution

  1. Derive the user's identity from the session, not from tool arguments.
  2. Check that every requested object belongs to (or is delegated to) that identity.
  3. Prefer tools that take no account id for "my account" questions.

Why it succeeds

Trade-off to manage: None significant.

How you prove it worked:

  • Authorisation failures per tool; cross-account attempts.

Same pattern elsewhere: Telco: a get_call_records tool returns records for any phone number passed (see sec-04).

Reference implementation

@tool
def get_statement(month: str, ctx: Session) -> dict:
    """Statement for the signed-in customer. Takes no account id."""
    account_id = ctx.identity.primary_account_id               # derived from the session
    return statements.get(account_id, month)

@tool
def get_statement_for(account_id: str, month: str, ctx: Session) -> dict:
    if account_id not in ctx.identity.accounts_and_delegations():
        return {"status": "REFUSED", "why": "account not owned or delegated"}
    return statements.get(account_id, month)
Key takeaway

Identity comes from the session, never from the prompt.

Legacy OSS call with no timeout hangs the conversation

ReliabilityLatencyTelco

Problem statement

A carrier's agent calls a legacy OSS for line-test results. Sometimes the OSS takes 90 seconds or never responds. The tool has no timeout, so the customer's chat hangs and eventually the session expires.

The anti-pattern

Tool calls with no timeout.

Think of it this way: Waiting on hold forever because nobody set a limit.

Why the current design fails

  • No timeouts on tool calls.
  • No async pattern for slow operations.

Where it breaks: Tool implementation.

Recommended solution

  1. Set timeouts per tool based on its SLA, and return a structured timeout error.
  2. For slow operations, start the job and return a job id; notify or let the agent check status later.
  3. Tell the customer what's happening and offer a callback.

Why it succeeds

Trade-off to manage: Async flows need status tracking.

How you prove it worked:

  • Tool latency percentiles and timeout rates.

Same pattern elsewhere: FinTech: a credit-bureau call without a timeout stalls loan applications.

Reference implementation

TOOL_TIMEOUTS = {"oss_line_test": 8, "get_balance": 2}

@tool
async def run_line_test(line_id: str) -> dict:
    try:

Every tool call needs a deadline.

10.13

Tool schema changed in place breaks deployed agents

ReliabilityFinTech

Problem statement

A bank's platform team renames a parameter in the shared transfer tool from "amount" to "amount_minor" and changes units, in place. Three agents built by other teams keep sending "amount" in major units; the tool fills defaults, and transfers are created for the wrong amounts until someone notices.

The anti-pattern

Change tool schema in place.

Think of it this way: Changing the shape of a plug socket overnight across the whole building.

Why the current design fails

  • Tool interfaces change without versioning.
  • Consumers aren't notified or tested.
  • Defaults hide errors.

Root cause: No versioning or compatibility policy for tools.

Where it breaks: Tool lifecycle.

Recommended solution

  1. Version tools (transfer_v2) and keep v1 until consumers migrate.
  2. Reject unknown or missing parameters instead of defaulting.
  3. Run consumer contract tests in the tool's CI.

Why it succeeds

Trade-off to manage: Maintaining two versions temporarily.

How you prove it worked:

  • Calls with unknown parameters; usage by version.

Same pattern elsewhere: Telco: a shared provisioning tool changes its product-code format and breaks three agents.

Reference implementation

class TransferV2Args(BaseModel):
    model_config = ConfigDict(extra="forbid")                  # unknown params rejected, no defaults
    from_account: str; to_account: str; amount: Decimal; currency: str; reference: str

@tool(name="transfer_v2")
def transfer_v2(args: TransferV2Args): ...

@tool(name="transfer", deprecated="use transfer_v2; removal 2027-01-31")
def transfer_v1(args: TransferV1Args): ...                       # kept until consumers migrate
# CI: consumer contract tests for every agent that calls transfer*
Key takeaway

Tools are APIs. Version them like APIs.

10.14

MCP server exposes the whole BSS API with an admin token

ReliabilitySecurityTelcoCritical

Problem statement

A carrier team wraps its entire BSS API (300 endpoints) as an MCP server using an admin token, so any internal agent can connect. A sales-assistant agent gains the ability to terminate subscriptions and change billing accounts, far beyond its purpose.

The anti-pattern

Whole API as one MCP server, admin token.

Think of it this way: Publishing the master key so any department can open any door.

Why the current design fails

  • The MCP server exposes everything to everyone.
  • One powerful credential sits behind all tools.
  • Clients get capabilities they don't need.

Root cause: MCP used as a pass-through instead of a scoped capability boundary.

Where it breaks: MCP server design.

Recommended solution

  1. Build purpose-specific MCP servers (sales read-only catalog and quotes; care with scoped writes).

def instrumented(tool):
    def run(*a, ctx, **kw):
        t0 = monotonic()
        try:
            return tool(*a, ctx=ctx, **kw)
        except Exception:
            tool_errors.labels(tool=tool.__name__, caller=ctx.agent_id).inc(); raise
        finally:
            tool_calls.labels(tool=tool.__name__, caller=ctx.agent_id).inc()
            tool_latency.labels(tool=tool.__name__).observe(monotonic() - t0)
    return run
