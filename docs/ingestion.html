1.1

Fixed-size chunking that ignores document structure

Quality

Problem statement

An insurer indexes 40,000 policy documents for a claims-adjuster assistant. Adjusters ask "Is water damage from a burst pipe covered under the HO-3 endorsement?" The answer is often wrong or incomplete, even though the clause is in the corpus.

The anti-pattern

Every document is split into 512-token windows with a 50-token overlap, regardless of headings, clauses, tables or lists. The same splitter is used for contracts, FAQs, spreadsheets and emails.

Why the current design fails

  • Semantic units are cut in half. A coverage clause and its exclusion end up in different chunks, so the retriever returns the clause without the exception.
  • Headings are lost. A chunk that says "This does not apply" has no anchor to which section "this" refers to.
  • Embedding dilution. Chunks that straddle two topics produce vectors that sit between both, so they rank poorly for either.
  • Blind tuning. Teams adjust chunk size by trial and error with no evaluation set, which trades one failure for another.

Recommended solution

Use structure-aware chunking driven by the document layout:

  1. Parse into a document tree (title → section → clause → paragraph/table) with a layout-aware parser.
  2. Split on semantic boundaries (sections, clauses, list items). Merge small siblings and recursively split oversized nodes.
  3. Prepend a contextual header to each chunk: document title, section breadcrumb, effective date. Optionally add a one-sentence LLM summary of where the chunk sits in the document ("contextual retrieval").
  4. Store a parent-child relationship. Retrieve on small child chunks for precision, then expand to the parent section for generation.
  5. Pick a chunking strategy per document type (contracts, FAQs, tables, transcripts) and validate it against a labeled retrieval set.

Why it succeeds

Chunks now line up with how meaning is actually organized, so each embedding represents one idea. The breadcrumb restores the context that splitting removes, which raises recall on queries that reference section names. The parent-child expansion delivers complete clauses, exceptions included, to the generator. Because the strategy is chosen per document type and measured, changes are evidence-based rather than guesswork.

Reference implementation

def chunk_document(doc_tree, max_tokens=400):
    chunks = []
    for node in doc_tree.walk(levels=("section", "clause")):
        breadcrumb = " > ".join(node.path_titles())          # Policy > Coverage A > Water damage
        for piece in split_on_boundaries(node.text, max_tokens):
            header = f"[{doc_tree.title} | {breadcrumb} | eff. {doc_tree.effective_date}]"
            chunks.append({
                "id": f"{doc_tree.id}:{node.id}:{piece.idx}",
                "text": f"{header}\n{piece.text}",
                "parent_id": node.id,          # expand to full clause at generation time
                "doc_type": doc_tree.doc_type,
            })
    return chunks

# Retrieval: match on children, generate on parents
hits = index.search(query, k=20)
context = dedupe(store.get_parent(h.parent_id) for h in rerank(query, hits)[:5])
Key takeaway

Chunking is a modelling decision, not a preprocessing default. Chunk along document structure, carry the heading path into every chunk, and prove the choice with a retrieval eval.

1.2

No metadata or lineage on chunks

ComplianceQuality

Problem statement

A pharmaceutical company's regulatory assistant cites an SOP. An auditor asks which version, which approval date, and which source system the answer came from. Nobody can tell.

The anti-pattern

Chunks are stored as {id, text, vector}. Source system, version, owner, effective date, classification and ingestion run are discarded during ingestion.

Why the current design fails

  • No filtering. Retrieval can't be restricted to current, approved or region-specific documents, so superseded SOPs compete with live ones.
  • No auditability. In regulated industries, an answer without provenance is unusable however accurate it is.
  • No targeted fixes. When a source document is wrong or withdrawn, nobody can find and purge its chunks.
  • No freshness signals. The ranker can't prefer newer content.

Recommended solution

Define a chunk metadata contract and enforce it at ingestion:

Field Purpose
source_uri, source_system, doc_id, version Citation and lineage
effective_from, effective_to, status Freshness and supersession filtering
classification, acl_groups, region Security trimming and residency
owner, doc_type, language Routing, ranking and stewardship
ingest_run_id, parser_version, embed_model Reproducibility and rollback

Reject chunks that fail the contract. Register every ingestion run in a lineage store (OpenLineage, a data catalog, or a simple run table) so you can trace any answer back to raw bytes.

Why it succeeds

Metadata turns the vector index from a bag of text into a governed data product. Filters keep superseded and unauthorized content out before ranking. Citations carry version and date, which satisfies auditors. A withdrawn document can be purged by doc_id in seconds, and a bad parser release can be rolled back by ingest_run_id.

Reference implementation

from pydantic import BaseModel, Field
from datetime import date

class ChunkMeta(BaseModel):
    doc_id: str; version: str; source_uri: str; source_system: str
    status: str = Field(pattern="^(approved|draft|superseded)$")
    effective_from: date; effective_to: date | None = None
    classification: str; acl_groups: list[str]; region: str
    ingest_run_id: str; parser_version: str; embed_model: str

def ingest(chunk_text, raw_meta, run):
    meta = ChunkMeta(**raw_meta, ingest_run_id=run.id,
                     parser_version=run.parser, embed_model=run.embedder)  # raises if invalid
    index.upsert(id=chunk_id(meta), vector=embed(chunk_text), text=chunk_text, metadata=meta.model_dump())

# Retrieval only sees approved, in-force, permitted content
index.search(q, filter={"status": "approved", "effective_to": {"$gte": today()},
                        "acl_groups": {"$in": user.groups}})
Key takeaway

If you can't answer "where did this answer come from, which version, and who approved it", the system isn't production-ready for a regulated client.

1.3

Parsing PDFs, tables and scans as flat text

Quality

Problem statement

A bank's credit-risk assistant answers questions from annual reports and rate sheets. Asked for "the Tier 1 capital ratio for 2025", it returns a number from the wrong column or the wrong year.

The anti-pattern

A basic text extractor flattens PDFs. Tables become whitespace-separated number soup, multi-column layouts interleave, headers and footers repeat on every chunk, and scanned pages are skipped silently.

Why the current design fails

  • Row and column relationships are destroyed. "12.4 13.1 11.8" no longer says which number belongs to which year or metric.
  • Reading order breaks on two-column layouts, so sentences are stitched across columns.
  • Boilerplate pollution. Repeated headers and footers dominate embeddings and crowd out real hits.
  • Silent gaps. Scanned or image-only pages produce no text and no error, so the knowledge isn't there and nobody knows.

Recommended solution

Treat parsing as a multimodal extraction pipeline:

  • Use a layout-aware parser or document-intelligence service (for example Azure Document Intelligence, Amazon Textract, Google Document AI, or open-source Docling/Unstructured) that returns blocks, reading order and table cells.
  • Serialize tables as Markdown or HTML, and for large tables also emit row-level chunks that repeat the column headers ("2025 · Tier 1 capital ratio · 13.1%").
  • Run OCR on image-only pages. For charts and diagrams, generate captions with a vision model and index those.
  • Strip repeated headers and footers by detecting text that recurs across pages.
  • Add quality gates: text-per-page thresholds, OCR confidence, table-detection counts. Route failures to a review queue.

Why it succeeds

Numbers stay attached to their row and column labels, so retrieval and generation see "2025 Tier 1 ratio = 13.1%" instead of an ambiguous string. Row-level chunks make single facts directly retrievable. Quality gates turn silent data loss into a visible operational metric, which matters most in finance, where one wrong figure destroys trust.

Reference implementation

def parse(pdf):
    doc = layout_parser.analyze(pdf)                 # blocks, reading order, tables, confidence
    out = []
    for page in doc.pages:
        if page.text_chars < 50:                     # image-only page
            page = ocr.run(page)
            if page.confidence < 0.85: review_queue.put(pdf.id, page.no)
        for t in page.tables:
            out.append(chunk(t.to_markdown(), kind="table", page=page.no))
            for row in t.rows:                       # row-level facts with headers repeated
                out.append(chunk(" · ".join(f"{h}: {v}" for h, v in zip(t.headers, row)),
                                 kind="table_row", page=page.no))
        for fig in page.figures:
            out.append(chunk(vision_caption(fig.image), kind="figure", page=page.no))
        out += text_chunks(strip_boilerplate(page.blocks, doc.repeated_lines))
    return out
Key takeaway

In document-heavy industries the parser is the most underrated component. Bad parsing produces confident wrong numbers that no prompt can fix.

1.4

One-time ingestion with no incremental refresh or deletes

ReliabilityCompliance

Problem statement

An HR policy assistant was loaded once at launch. Six months later it still quotes the old parental-leave policy, and documents that were deleted from SharePoint for legal reasons are still being cited.

The anti-pattern

Ingestion is a notebook someone ran once. Updates mean re-running everything by hand. Deletions in the source system never reach the index.

Why the current design fails

  • Stale answers. The index drifts from the source of truth, and users get confident answers based on outdated policy.
  • Zombie documents. Content removed for legal, privacy or confidentiality reasons stays retrievable, which is a compliance incident waiting to happen.
  • Full re-index cost. Rebuilding everything to pick up a handful of changes is slow and expensive, so it happens rarely.
  • No freshness SLA. Nobody owns how stale the index is allowed to be.

Recommended solution

Build ingestion as a continuously synchronized pipeline:

  • Subscribe to change events (Graph API delta queries, S3 events, Confluence webhooks, database CDC) instead of polling everything.
  • Hash content at document and chunk level. Re-embed only chunks whose hash changed.
  • Propagate deletes as tombstones keyed by doc_id. Never rely on "we'll overwrite it next time".
  • Run a periodic reconciliation job that compares source inventory with index inventory and fixes drift.
  • Publish freshness metrics (p95 lag from source change to searchable) and alert when the SLA is breached.

Why it succeeds

Event-driven sync keeps the index within minutes of the source, at a fraction of the cost of full rebuilds, because only changed chunks are re-embedded. Tombstones and reconciliation close the compliance gap for deleted content. A measured freshness SLA turns "is the bot up to date?" into an operational metric with an owner.

Reference implementation

def on_change(event):
    if event.type == "deleted":
        index.delete(filter={"doc_id": event.doc_id}); audit.log("purge", event.doc_id); return
    doc = fetch(event.uri)
    new_chunks = {c.id: c for c in chunk_document(parse(doc))}
    old_hashes = index.get_hashes(doc_id=event.doc_id)
    changed = [c for cid, c in new_chunks.items() if old_hashes.get(cid) != sha256(c.text)]
    stale   = set(old_hashes) - set(new_chunks)
    index.upsert([embed_chunk(c) for c in changed]); index.delete(ids=list(stale))
    metrics.observe("freshness_lag_s", now() - event.modified_at)

def reconcile():                                    # nightly safety net
    drift = set(index.doc_ids()) ^ set(source.doc_ids())
    for d in drift: on_change(source.event_for(d))
Key takeaway

A RAG index is a replica of the enterprise's knowledge. Treat it like any replica, with change data capture, delete propagation and a freshness SLA.

1.5

Ingesting PII and secrets without redaction

SecurityCompliance

Problem statement

A support assistant is trained on five years of ticket history. A user asks how a refund was handled and gets back another customer's full name, phone number and partial card number.

The anti-pattern

Raw tickets, emails and chat logs are embedded as-is. PII, PHI, credentials and API keys pasted into tickets all become retrievable context.

Why the current design fails

  • Cross-user leakage. Any user who can query the assistant can surface any other customer's personal data.
  • Regulatory exposure. GDPR, HIPAA, PCI-DSS and similar rules apply to the vector store, logs and caches as much as to the source system.
  • Secrets exposure. Credentials pasted into tickets become retrievable by anyone.
  • Irreversible spread. Once PII is in embeddings, prompt logs and caches, deleting it means finding every copy.

Recommended solution

Apply privacy by design at ingestion and again at output:

  • Run PII/PHI and secret detectors (Microsoft Presidio, Amazon Comprehend PII, Google Cloud DLP, or Sensitive Data Protection) before chunking.
  • Redact what the use case doesn't need. Pseudonymize what it does (reversible tokens in a vault, so authorized workflows can re-identify).
  • Classify every document and set classification metadata. Restricted classes go into separate, tightly scoped indexes or are excluded.
  • Add an output filter as defense in depth, and apply the same redaction to prompt and response logs.
  • Record a data-protection impact assessment (DPIA) for the use case.

Why it succeeds

Sensitive values never become retrievable context, so leakage can't happen through retrieval no matter what the user asks. Tokenization keeps analytical value ("same customer across tickets") without exposing identity. Redacted logs prevent the observability stack from becoming a second copy of the PII. The design is explainable to a privacy officer.

Reference implementation

from presidio_analyzer import AnalyzerEngine
from presidio_anonymizer import AnonymizerEngine

analyzer, anonymizer = AnalyzerEngine(), AnonymizerEngine()
ENTITIES = ["PERSON", "PHONE_NUMBER", "EMAIL_ADDRESS", "CREDIT_CARD", "US_SSN", "IBAN_CODE"]

def sanitize(text, doc_id):
    if secret_scanner.find(text):                     # API keys, passwords, tokens
        quarantine(doc_id); return None
    results = analyzer.analyze(text=text, entities=ENTITIES, language="en")
    return anonymizer.anonymize(text=text, analyzer_results=results,
                                operators={"DEFAULT": vault_tokenize_operator()}).text

clean = sanitize(ticket.body, ticket.id)
if clean: ingest(clean, meta | {"classification": "internal-redacted"})
Key takeaway

Data protection has to happen before embedding. Once PII is in the vector store, the logs and the caches, it can no longer be cleaned up reliably.

1.6

Rebuilding the whole index every night

CostReliabilityScale

Problem statement

The nightly index job now takes 30 hours, so it overlaps itself. Embedding bills spike, and documents edited at 9 am aren't searchable until the next day.

The anti-pattern

Full rebuilds instead of incremental updates. Fine at 10K documents; at 50M chunks it re-embeds 25B tokens to pick up a 0.1% change.

Why the current design fails

  • Cost and runtime scale with the whole corpus, not with what changed.
  • Freshness is capped at once a day, and slips further as the job grows.
  • Overlapping runs compete for the same resources and can corrupt or double-write the index.

Recommended solution

Use change data capture:

  1. Consume change events (or poll updated_at).
  2. Hash each chunk's normalized text and re-embed only chunks whose hash changed.
  3. Upsert by stable chunk ID; tombstone removed chunks.
  4. Keep a periodic full reconciliation (weekly) to catch drift, not as the main path.

Why it succeeds

Embedding cost tracks the rate of change rather than corpus size, and edits become searchable in minutes. The trade-off is more moving parts (queue, hash registry). Catch regressions with an index-lag SLO ("95% of edits searchable within 15 minutes") and embedding tokens per day.

Reference implementation

def on_doc_changed(doc):
    new = {chunk_id(doc.id, c.section, i): c for i, c in enumerate(chunk_doc(doc))}
    old = registry.chunk_hashes(doc.id)             # {chunk_id: hash}
    changed = [cid for cid, c in new.items() if old.get(cid) != sha256(normalize(c.text))]
    removed = set(old) - set(new)
    if changed:
        vecs = embed([new[c].text for c in changed])  # only what changed
        store.upsert(ids=changed, vectors=vecs, meta=[new[c].meta for c in changed])
    if removed:
        store.delete(ids=list(removed))
    registry.save(doc.id, {cid: sha256(normalize(c.text)) for cid, c in new.items()})
Key takeaway

Re-embed what changed, not what exists. Change data capture plus a weekly reconciliation beats nightly rebuilds on cost and freshness.

1.7

CRM export column renamed, plan names vanish from the index

QualityTelco

Problem statement

A carrier's knowledge pipeline ingests a nightly CRM export to build customer-context documents for agent assist. The CRM team renames plan_name to product_offering_name. The pipeline doesn't fail; it fills the field with blanks. For two weeks, agent assist shows customers with no plan, and suggestions are generic.

The anti-pattern

No contract with the upstream export.

Think of it this way: A supplier changing the label on a box, and your warehouse quietly filing it as empty.

Why the current design fails

  • No contract between producer and consumer.
  • Missing fields default to blank instead of failing.
  • No data-quality checks on outputs.

Root cause: No data contracts or schema validation.

Where it breaks: Ingestion pipeline.

Recommended solution

  1. Define data contracts (schema, required fields, semantics, owner) with upstream teams, and test them in the producer's CI.
  2. Validate schemas at ingestion and fail loudly on missing required fields.
  3. Add quality checks (null rates, distributions) with alerts.

Why it succeeds

Trade-off to manage: Contracts need cross-team agreement.

How you prove it worked:

  • Null-rate alerts per field.

Same pattern elsewhere: FinTech: a core-banking extract renames a balance field, and the assistant shows zero balances.

Reference implementation

class CrmPlanRecord(BaseModel):          # data contract with the CRM team
    account_id: str; plan_code: str; plan_name: constr(min_length=1); effective_from: date

def ingest(batch):
    try:
        rows = [CrmPlanRecord.model_validate(r) for r in batch]
    except ValidationError as e:
        raise IngestionHalted(f"contract violation: {e.errors()[:3]}")      # fail loudly
    if null_rate(batch, "plan_name") > 0.01: alert("plan_name null rate spike")
    return rows
Key takeaway

Data you depend on needs a contract.

1.8

OCR misreads income documents with no confidence check

QualityFinTech

Problem statement

A mortgage lender's pipeline OCRs payslips and bank statements for an underwriting assistant. Low-quality phone photos produce digit errors (8 read as 3). The pipeline passes all text on, and the assistant summarises incomes that are off by thousands.

The anti-pattern

Pass all OCR text downstream.

Think of it this way: Copying numbers from a smudged fax without saying it was smudged.

Why the current design fails

  • OCR confidence is ignored.
  • No validation against document totals.
  • Low-quality inputs flow downstream silently.

Root cause: No quality gates on extracted data.

Where it breaks: Document ingestion.

Recommended solution

  1. Capture OCR confidence per field and route low-confidence fields to human verification or re-upload requests.
  2. Cross-check totals (gross minus deductions equals net) and year-to-date figures.
  3. Mark extracted values with confidence in downstream context.

Why it succeeds

Trade-off to manage: More manual verification for bad images.

How you prove it worked:

  • Share of low-confidence fields; underwriting corrections.

Same pattern elsewhere: Telco: OCR on ID documents for postpaid sign-up misreads dates of birth.

Reference implementation

def extract_income(doc):
    fields = ocr.extract(doc, fields=["gross", "deductions", "net", "ytd_gross"])
    low = [f for f in fields.values() if f.confidence < 0.9]
    if low:
        return request_verification(doc, fields=[f.name for f in low])
    if abs(fields["gross"].value - fields["deductions"].value - fields["net"].value) > 1:
        return request_reupload(doc, reason="totals don't reconcile")
    return {k: {"value": f.value, "confidence": f.confidence} for k, f in fields.items()}
Key takeaway

Extracted data needs a confidence score and a cross-check.

1.9

No freshness SLO for promotion pages

QualityTelco

Problem statement

A carrier's marketing team updates promotion pages daily. The knowledge pipeline crawls the website weekly. The bot regularly quotes expired promotions, and store staff have to honour or explain them.

The anti-pattern

Weekly crawl for daily-changing content.

Think of it this way: A newspaper delivered once a week for a market that changes daily.

Why the current design fails

  • Update frequency of sources isn't matched by the pipeline.
  • No freshness targets per source.
  • Expired content isn't removed promptly.

Root cause: No freshness SLOs.

Where it breaks: Knowledge pipeline.

Recommended solution

  1. Set freshness SLOs per source based on change frequency and risk (promotions within hours).
  2. Use CMS events to update, and expiry dates on promotional content that the index enforces.
  3. Monitor lag per source.

Why it succeeds

Trade-off to manage: Event-driven ingestion is more complex.

How you prove it worked:

  • Lag between source publish and index update.

Same pattern elsewhere: FinTech: a bank's rate pages update instantly but the assistant's index refreshes weekly (see rag-05).

Reference implementation

FRESHNESS_SLO = {"promotions": timedelta(hours=2), "help_articles": timedelta(days=1), "legal": timedelta(days=1)}

@cms.webhook
def on_publish(evt):
    index.upsert(evt.doc, meta={"expires_at": evt.doc.promo_end, "source": evt.source})

def search(q):
    return index.search(q, filter={"$or": [{"expires_at": None}, {"expires_at": {"$gt": now()}}]})

for src, slo in FRESHNESS_SLO.items():
    if index_lag(src) > slo: alert(f"{src} freshness SLO breached")
Key takeaway

Every source needs a freshness target.

1.10

After a bank merger, customer ids collide across systems

QualityFinTechCritical

Problem statement

After a merger, a bank's assistant combines data from both banks' systems. Customer ids overlap, and the integration layer joins on id alone. Some customers see another person's accounts in the assistant's summary.

The anti-pattern

Join merged systems on overlapping ids.

Think of it this way: Two schools merging and seating students by roll number, so two different "number 14"s share a desk.

Why the current design fails

  • Identifiers aren't globally unique across sources.
  • No master data management or entity resolution.
  • Joins aren't validated.

Root cause: Missing master data management.

Where it breaks: Data integration.

Recommended solution

  1. Use a master customer index with globally unique ids and source-system mappings.
  2. Validate joins (name, date of birth, address) and quarantine conflicts.
  3. Test data integration with known collision cases before exposing it to AI.

Why it succeeds

Trade-off to manage: MDM is a substantial programme.

How you prove it worked:

  • Join conflict rates; customer reports of unknown accounts.

Same pattern elsewhere: Telco: after acquiring a regional carrier, account numbers overlap and the bot shows the wrong bills.

Reference implementation

def resolve_customer(source_system, source_id):
    gid = mci.lookup(source_system, source_id)            # master customer index, globally unique id
    if gid: return gid
    candidates = mci.match(name=..., dob=..., address=...)
    if len(candidates) != 1:
        quarantine.put(source_system, source_id, candidates)   # conflicts never reach the AI
        return None
    return mci.link(candidates[0], source_system, source_id)
Key takeaway

Join on identity you can trust, not on ids that happen to match.

1.11

Can't tell which version of a document produced an answer

QualityTelco

Problem statement

A customer disputes a bot answer about device trade-in terms from last month. The knowledge base article has since been edited twice. The vector store keeps only the latest chunks with no version info, so the carrier can't show what the bot actually relied on.

The anti-pattern

Chunks without versions.

Think of it this way: A contract where pages get replaced and no one keeps the old ones.

Why the current design fails

  • Chunks have no document version.
  • Old versions aren't retained.
  • Traces store chunk ids without versions.

Root cause: No lineage from answer to source version.

Where it breaks: Ingestion and tracing.

Recommended solution

  1. Store document id, version and content hash on every chunk, and record them in traces.
  2. Retain historical versions in the content store (not necessarily in the live index).
  3. Make "what did the bot rely on" a supported query for complaints teams.

Why it succeeds

Trade-off to manage: Storage for history.

How you prove it worked:

  • Traces with complete source versions.

Same pattern elsewhere: FinTech: a bank can't prove which fee schedule version its assistant quoted.

Reference implementation

def chunk_meta(doc, i, text):
    return {"doc_id": doc.id, "version": doc.version, "content_hash": sha256(text), "chunk_index": i}

span.set_attribute("retrieval.sources", [f"{h.meta['doc_id']}@{h.meta['version']}" for h in hits])

1.12

Intent labels from three vendors disagree

QualityTelco

Problem statement

A carrier outsources intent labelling to three vendors. Each interprets "billing dispute" versus "billing question" differently. The trained router is inconsistent, and evals built on the labels can't be trusted.

The anti-pattern

Labels without shared guidelines.

Think of it this way: Three referees using slightly different rulebooks.
