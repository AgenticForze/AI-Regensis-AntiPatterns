14.1

Last week's bad answer can't be reproduced

ReliabilityFinTech

Problem statement

A complaint arrives about a wrong answer the bank's assistant gave about early repayment charges eight days ago. Engineering tries to reproduce it. Since then, the prompt changed twice, the index was rebuilt, and the model was upgraded. Git has the code, but nothing records which prompt, index snapshot and model produced the answer.

The anti-pattern

Git for code only.

Think of it this way: Trying to bake the same cake again when the recipe, oven and flour have all changed and nobody wrote down which were used.

Why the current design fails

Mechanism: Behavior depends on prompt, model version, index snapshot, embeddings, and parameters.

  • Behaviour depends on more than code.
  • Prompts, indexes and models change on different schedules.
  • No single record ties them together.

Root cause: Only code is versioned.

Where it breaks: Release engineering.

Recommended solution

  1. Version every component (prompt, model id, index snapshot, embedding model, tool versions, guardrail config).
  2. Record each production configuration as a release manifest with an id, stamped on every trace.
  3. Keep index snapshots long enough to replay recent incidents.

Why it succeeds

Trade-off to manage: Snapshots cost storage; keep them on a rolling window.

How you prove it worked:

  • Ability to rebuild any release from its manifest, tested quarterly.

Same pattern elsewhere: Telco: a regulator asks a carrier to explain an AI answer about contract terms, and the configuration that produced it can't be reconstructed.

Reference implementation

manifest = {
    "release": "care-bot-2026.11.07",
    "prompt": "care.main@31", "model": "provider/model-2026-08-14",
    "index": "kb_2026_11_05_snapshot", "embedder": "bge-m3@rev3",
    "tools": {"billing": "2.4.1", "orders": "1.9.0"}, "guardrails": "baseline@12",
}
release_store.save(manifest)
span.set_attribute("release.id", manifest["release"])           # stamped on every trace
# replay: load manifest by trace → same prompt/model/index snapshot
Key takeaway

Reproducibility needs the whole bundle versioned.

14.3

Fine-tuning a model on monthly price plans

ReliabilityCostLatencyTelco

Problem statement

A carrier spends three months and $40k fine-tuning a model on its price plans and promotions so the bot "knows the catalog". The catalog changes monthly. Two weeks after deployment, the model confidently quotes last month's prices, and retraining each month is too slow and expensive.

The anti-pattern

Fine-tuning for knowledge.

Think of it this way: Tattooing the menu on the waiter's arm when the menu changes every month.

Why the current design fails

Mechanism: Fine-tuning is good for style, format, and behavior, but poor for fresh, factual knowledge. Retraining for each update is costly.

  • Fine-tuning bakes knowledge into weights.
  • Knowledge goes stale as soon as the catalog changes.
  • The model can't cite where a price came from.

Root cause: Fine-tuning used for fresh, factual knowledge.

Where it breaks: Approach selection.

Recommended solution

  1. Use a ladder (prompting, then RAG or tools for knowledge, then fine-tuning for behaviour, format or cost).
  2. Get prices from the catalog (TMF620) as a tool.
  3. Fine-tune only for stable behaviour (tone, format, classification) once evals and data exist.

Why it succeeds

Trade-off to manage: Tools add latency, but prices are always current and citable.

How you prove it worked:

  • Price accuracy against the live catalog.

Same pattern elsewhere: FinTech: a bank fine-tunes on its rate sheet, and the model quotes old mortgage rates after a rate change.

Reference implementation

LADDER = ["prompting", "rag_or_tools", "fine_tune"]

@tool
def get_plan_price(offering_id: str) -> dict:
    return tmf620.product_offering_price(offering_id)      # monthly prices from the catalog

# fine-tune only for stable behaviour (tone, format, classification), with evals + data in place
Key takeaway

RAG for knowledge, fine-tuning for behaviour.

Problem statement

The anti-pattern

Training on raw historical transcripts.

Think of it this way: Teaching an apprentice by having them shadow everyone, including the staff who were later disciplined.

Why the current design fails

Mechanism: The model learns everything in the data, including mistakes.

  • The model learns everything in the data, including bad behaviour.
  • Transcripts were never filtered by QA outcome.
  • PII is also embedded in training data.

Root cause: Unvetted training data.

Where it breaks: Data curation.

Recommended solution

  1. Filter training data by QA scores and compliance reviews; remove non-compliant calls.
  2. Remove PII, deduplicate, and label examples.
  3. Hold out a test set and run compliance evals on the fine-tuned model before deployment.
  4. Track data lineage (which calls, which filters).

Why it succeeds

Trade-off to manage: Filtering reduces data volume; quality matters more than quantity.

How you prove it worked:

  • Compliance phrase scans of model outputs.

Same pattern elsewhere: Telco: a care model fine-tuned on old chats learns to quote retired policies and sarcastic replies.

14.6

All traffic switched to a new model at once

ReliabilityTelco

Problem statement

A carrier switches 100% of its care bot to a new model version on Monday morning. Offline evals passed. In production, the new model handles abbreviations and prepaid-brand slang differently, and transfers to agents rise 35% before the team rolls back two hours later.

The anti-pattern

No gradual rollout.

Think of it this way: Changing every traffic light in a city to a new system at once instead of testing one junction.

Why the current design fails

Mechanism: Offline evals don't catch everything.

  • Offline evals don't catch everything.
  • No gradual exposure.
  • Rollback is manual and slow.

Root cause: Big-bang rollout.

Where it breaks: Deployment strategy.

Recommended solution

  1. Shadow first (new model runs silently, outputs compared), then canary (1-5%), then progressive ramp.
  2. Define automatic rollback triggers on key metrics (transfer rate, errors, quality score).
  3. Avoid Monday peaks for changes.

Why it succeeds

Trade-off to manage: Slower rollouts; far fewer incidents.

How you prove it worked:

  • Canary vs control metric comparison.

Same pattern elsewhere: FinTech: a bank switches its fraud-alert explanations to a new model and complaint volume jumps.

Reference implementation

ROLLOUT = [("shadow", 0), ("canary", 0.02), ("ramp", 0.25), ("ramp", 0.5), ("full", 1.0)]
ROLLBACK_IF = {"transfer_rate": +0.03, "error_rate": +0.01, "quality_score": -0.02}

for stage, pct in ROLLOUT:
    gateway.set_traffic("new_model", pct, shadow=(stage == "shadow"))
    wait(hours=24, avoid=["MON 08:00-12:00"])
    if any(delta(m) * (1 if d > 0 else -1) > abs(d) for m, d in ROLLBACK_IF.items()):
        gateway.set_traffic("new_model", 0); alert("auto-rollback"); break
Key takeaway

Shadow, canary, then ramp.

def cost_per_resolved_dispute(month):
    llm = ledger.sum(use_case="disputes", month=month)

How you prove it worked:

  • Cache hit rates and cost per conversation.
