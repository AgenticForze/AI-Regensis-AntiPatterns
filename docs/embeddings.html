2.1

One embedding model for every domain and language

Quality

Problem statement

A global manufacturer's engineering assistant serves English, German and Japanese plants. German queries for "Drehmomentspezifikation" (torque specification) rarely retrieve the right maintenance manuals, and part numbers like "XJ-4471-B" never match.

The anti-pattern

A general-purpose English embedding model was chosen from a leaderboard and applied to every corpus, language and content type. It was never evaluated on the company's own queries.

Why the current design fails

  • Leaderboards measure someone else's data. Public benchmark rankings say little about part numbers, internal jargon or regulatory language.
  • Cross-lingual gaps. English-centric models place German and Japanese text poorly, so retrieval recall drops sharply for non-English users.
  • Lexical identifiers. Dense vectors blur exact codes (SKUs, ticket IDs, clause numbers) that users expect to match exactly.
  • No baseline. Without a domain eval set, nobody can tell whether a model change helps or hurts.

Recommended solution

Select embeddings empirically against the client's own data:

  1. Build a labeled evaluation set of 200–500 real queries with known relevant documents, stratified by language, department and query type (conceptual, identifier, how-to).
  2. Shortlist 3–5 candidates (multilingual and domain-tuned commercial or open models) and compare recall@k, MRR and nDCG.
  3. Pair dense vectors with sparse/lexical retrieval (BM25, SPLADE) for codes and rare terms.
  4. Consider fine-tuning the embedder on in-domain query–document pairs when the gap stays large. Synthetic queries generated from the corpus work well for this.
  5. Re-run the eval on every candidate model change.

Why it succeeds

The selection criterion becomes recall on the client's real workload rather than a public benchmark. Multilingual models put "Drehmomentspezifikation" and "torque specification" in the same region of vector space. Hybrid lexical retrieval catches exact identifiers that dense vectors smear. The eval set becomes a lasting asset for every future model decision.

Reference implementation

def evaluate_embedder(model, eval_set, corpus, k=10):
    index = build_index(corpus, embed_fn=model.embed)
    recalls, rr = [], []
    for q in eval_set:                                  # {"query","lang","relevant_ids"}
        hits = [h.id for h in index.search(model.embed(q["query"]), k=k)]
        recalls.append(len(set(hits) & set(q["relevant_ids"])) / len(q["relevant_ids"]))
        rr.append(next((1 / (i + 1) for i, h in enumerate(hits) if h in q["relevant_ids"]), 0))
    return {"recall@k": mean(recalls), "mrr": mean(rr),
            "by_lang": group_mean(eval_set, recalls, key="lang")}

results = {m.name: evaluate_embedder(m, eval_set, corpus) for m in CANDIDATES}
best = max(results, key=lambda m: results[m]["recall@k"])
Key takeaway

Choose embeddings the way you'd choose a database index, by measuring them on the real workload. A leaderboard tells you nothing about the client's part numbers.

2.2

No versioning when the embedding model changes

ReliabilityCost

Problem statement

A team upgrades to a newer embedding model to improve recall. Half the corpus is re-embedded overnight before the job fails. Retrieval quality collapses the next morning and nobody can explain why.

The anti-pattern

Vectors from different models (or model versions) are written into the same index. Upgrades are an in-place overwrite with no record of which model produced which vector, and no way back.

Why the current design fails

  • Incompatible vector spaces. Vectors from different models aren't comparable. Mixing them makes similarity scores meaningless.
  • No rollback. When the new model underperforms, the old vectors are gone.
  • Downtime and big-bang cost. Re-embedding a large corpus in place blocks queries or leaves the index half-migrated.
  • Query/document mismatch. The query path may be upgraded before or after the document path.

Recommended solution

Treat the embedding model as part of the index schema and migrate with blue/green:

  • Record embed_model and embed_version on every vector and in the index name (kb_v2_e5large_2026_10).
  • Build the new index in parallel (shadow), backfilling from the canonical chunk store rather than from the old index.
  • Run the retrieval eval and a shadow-traffic comparison. Promote only if metrics improve.
  • Switch via an alias, so queries move atomically and the query embedder flips at the same moment.
  • Keep the previous index until the rollback window closes.

Why it succeeds

Each index is internally consistent, so similarity scores stay meaningful. The alias switch makes cutover atomic and reversible. Evidence from the eval gates the change, which turns a risky upgrade into a routine release. Keeping chunks in a canonical store (not only the vector DB) makes rebuilds reproducible.

Reference implementation

def migrate_embeddings(new_model, alias="kb_current"):
    new_index = f"kb_{new_model.slug}_{today():%Y%m%d}"
    vdb.create_index(new_index, dim=new_model.dim)
    for batch in chunk_store.iter_batches(1000):              # canonical source, not the old index
        vdb.upsert(new_index, [(c.id, new_model.embed(c.text), c.meta | {"embed_model": new_model.slug})
                               for c in batch])
    old = vdb.resolve_alias(alias)
    if evaluate(new_index, new_model) < evaluate(old, current_model) + MIN_GAIN:
        raise PromotionBlocked("new embedder did not beat baseline")
    vdb.swap_alias(alias, new_index); config.set("query_embedder", new_model.slug)  # atomic pair
    schedule_drop(old, after_days=14)
Key takeaway

Vectors are only comparable inside one model's space. Version the embedder with the index, migrate blue/green, and let the eval decide promotion.

2.3

Using the vector database as the system of record

ReliabilityCompliance

Problem statement

A legal-tech platform stores contract clauses only in its vector database. When it needs to switch vendors, change chunking or answer a legal-hold request, it discovers the original text and metadata exist nowhere else.

The anti-pattern

Documents are parsed, chunked and written straight into the vector store. Raw files and processed chunks aren't kept elsewhere. The vector DB is treated as the database.

Why the current design fails

  • Lock-in. Switching vector database, embedder or chunking strategy means re-ingesting from sources that may have changed or disappeared.
  • Weak data management. Vector stores are optimized for ANN search, not for transactions, backups, legal hold or complex queries.
  • No reprocessing. Parser improvements can't be applied retroactively.
  • Governance gaps. Retention, lineage and access reviews are hard when content lives only in a search index.

Recommended solution

Adopt a medallion-style knowledge pipeline:

  • Raw (bronze): immutable original files with checksums in object storage (S3, GCS, ADLS).
  • Processed (silver): parsed and chunked records with full metadata in a lakehouse table or relational DB, versioned by parser_version.
  • Serving (gold): vector indexes and keyword indexes treated as derived, rebuildable projections.

Retention, legal hold and deletion policies apply at the raw and processed tiers and propagate to indexes.

Why it succeeds

The vector store becomes replaceable infrastructure. Changing vendor, embedder or chunker is a rebuild job rather than a re-ingestion project. Governance tools (catalogs, retention policies, access reviews) work on the tables they were designed for. Reprocessing history with a better parser costs compute, not archaeology.

Reference implementation

# Bronze → Silver → Gold, each step idempotent and keyed by content hash
raw_uri = object_store.put(f"raw/{src}/{doc_id}/{sha}.pdf", bytes_)      # immutable
chunks  = chunk_document(parse(raw_uri))
lake.merge("silver.chunks", chunks, keys=["chunk_id"],
           extra={"parser_version": PARSER_V, "raw_uri": raw_uri})

def rebuild_gold(index_name, embedder):                   # any time, any vendor
    for batch in lake.read("silver.chunks", where="status='approved'").batches(2000):
        vector_index(index_name).upsert(embed_batch(batch, embedder))
        keyword_index(index_name).upsert(batch)
Key takeaway

The vector index should be the cheapest thing to throw away. Keep raw and processed knowledge in governed storage and treat indexes as derived views.

2.4

No access control at retrieval time

SecurityCompliance

Problem statement

An enterprise knowledge assistant indexes SharePoint for the whole company. A junior analyst asks about "upcoming restructuring" and receives excerpts from a board-only M&A memo.

The anti-pattern

Everything is ingested into one shared index with a service account that can read everything. Permissions are "handled" by a system-prompt instruction not to reveal confidential information.

Why the current design fails

  • The LLM is not a security boundary. Once confidential text is in the context window, prompt instructions can't reliably stop it leaking, and prompt injection can extract it on purpose.
  • Permission flattening. A service account with global read rights collapses the source system's ACLs.
  • Stale permissions. Even when ACLs are copied, they drift if they aren't re-synced when group membership changes.
  • Multi-tenant leakage. In SaaS platforms, one client's data can be retrieved for another.

Recommended solution

Enforce document-level security trimming in the retrieval layer:

  • Ingest ACLs (allowed users and groups) with each chunk and keep them in sync via change feeds, as you do content.
  • At query time, resolve the caller's identity and group memberships from the IdP (Entra ID, Okta) using the user's token (on-behalf-of flow), not a service account.
  • Apply ACLs as a pre-filter in the vector or hybrid query. Post-filtering after top-k leaks through ranking and harms recall.
  • For hard isolation (tenants, classification levels), use separate indexes or namespaces.
  • Log every retrieval with user, query and returned doc_ids for audit.

Why it succeeds

Authorization happens deterministically, before the model sees anything. A user can only ever be shown content they could open in the source system, whatever the prompt says. Identity propagation keeps entitlements current, and audit logs prove it to security reviewers. This is the control CISOs ask for first.

Reference implementation

def secure_search(query, user_token, k=8):
    user = idp.validate(user_token)                         # OBO flow, not a service principal
    groups = idp.transitive_groups(user.oid)                 # cached with short TTL
    flt = {"$or": [{"acl_users": {"$in": [user.oid]}},
                   {"acl_groups": {"$in": groups}}],
           "tenant_id": user.tenant_id,
           "classification": {"$in": user.clearances}}
    hits = index.hybrid_search(query, filter=flt, k=k)       # PRE-filter, not post-filter
    audit.log(user=user.oid, query_hash=h(query), doc_ids=[h.doc_id for h in hits])
    return hits
Key takeaway

Never ask the model to keep secrets. Authorization belongs in the retrieval layer, enforced with the user's own identity before anything enters the prompt.

2.5

Index and query encoded differently (silent recall loss)

QualityReliability

Problem statement

Retrieval recall was 0.84 in the notebook and 0.62 in production. Same embedding model, same data, no errors anywhere.

The anti-pattern

The ingestion job and the query service each embed text their own way. One drops the model's required query prefix, one normalizes vectors and the other doesn't, or they pin different model revisions or truncation lengths.

Why the current design fails

  • Small encoding mismatches don't throw errors; they quietly move query vectors away from the document vectors they should match.
  • Typical causes: the query:/passage: prefix or query instruction dropped in one service; normalization at index time but not at query time (or a cosine index fed unnormalized vectors); a different tokenizer, model revision or truncation length.
  • Teams blame "production data" and start tuning the wrong layer.

Recommended solution

Treat embedding as a contract between two services, not a model detail:

  1. Put embedding behind one shared library or service used by both indexing and querying, with a pinned model revision, prefix rules and normalization.
  2. Add a parity test in CI that embeds fixed strings through both paths and asserts identical vectors.
  3. Store the embedder version with every vector.
  4. Monitor live recall on a canary query set hourly, so drift shows up within hours.

Why it succeeds

There is only one place where encoding rules live, so they can't diverge. The parity test catches regressions before deployment, and the canary set catches anything that slips through (for example a dependency upgrade) in hours rather than after users complain.

Reference implementation

class Embedder:
    """Single source of truth for both ingestion and query paths."""
    def __init__(self, name="BAAI/bge-small-en-v1.5", revision="<pinned-commit>"):
        self.m = SentenceTransformer(name, revision=revision)
        self.q_prefix = "Represent this sentence for searching relevant passages: "
        self.version = f"{name}@{revision}"
    def docs(self, texts):  return self.m.encode(texts, normalize_embeddings=True)
    def query(self, text):  return self.m.encode([self.q_prefix + text], normalize_embeddings=True)[0]

def test_parity(ingest_embedder, query_embedder):
    for s in CANARY_STRINGS:
        assert np.allclose(ingest_embedder.query(s), query_embedder.query(s), atol=1e-6)
Key takeaway

A recall drop with no error is usually an encoding contract mismatch. Share one embedder, test parity in CI, and monitor canary recall.

2.6

Chunks longer than the embedder's input limit

Quality

Problem statement

Long policy sections are never retrieved, even when the answer is in them. The team concludes "embeddings aren't good with long text" and starts evaluating bigger models.

The anti-pattern

Chunk sizes are set without checking the embedding model's maximum input length. Many models silently truncate beyond their limit (often 512 tokens).

Why the current design fails

  • Everything after the cutoff is invisible to retrieval, and no error is raised.
  • The failure looks like a model-quality problem, so money goes to a bigger model instead of a one-line fix.
  • Character-based chunk sizes hide the problem further, because token counts vary by language and content.

Recommended solution

Add data-quality gates to ingestion:

  1. Measure every chunk in tokens with the embedder's own tokenizer.
  2. Reject or re-split any chunk over the model's limit (minus a small margin for prefixes).
  3. Log and alert on the over-limit rate, and add a chunk-token distribution chart to the ingestion dashboard.

Why it succeeds

Content beyond the limit gets its own vectors, so it becomes retrievable. The over-limit metric turns a silent class of failure into a visible one, and the fix costs nothing compared with switching models.

Reference implementation

MAX_IN = embedder.m.max_seq_length            # e.g. 512 for many models

def validate(chunks, tokenizer=embedder.m.tokenizer):
    over = [c for c in chunks if len(tokenizer.encode(c.text)) > MAX_IN]
    metrics.gauge("ingest.chunks_over_limit_pct", 100 * len(over) / max(len(chunks), 1))
    if over:
        chunks = [x for c in chunks for x in (resplit(c, MAX_IN - 16) if c in over else [c])]
    return chunks
Key takeaway

Size chunks in tokens against the embedder's limit, and gate ingestion on it. Silent truncation is a data-quality bug, not a model problem.

2.7

Choosing the vector store by hype

CostReliability

Problem statement

The team wants to adopt a new dedicated vector database. The company already runs Postgres, has 3 million chunks, and simple metadata filters.

The anti-pattern

The vector store is picked by popularity rather than requirements. Either a new system is added that the team can't operate, or a library such as FAISS is used as if it were a database.

Why the current design fails

  • Vector stores are long-lived infrastructure with operational cost, security reviews and migration pain.
  • A new system adds on-call load, backups, access control and another vendor review.
  • A bare library lacks persistence, filtering, replication and access control, which surface later as outages or leaks.

Recommended solution

Decide with requirements and capacity math, recorded in an architecture decision record (ADR):

  • Requirements: corpus size and growth, write rate, metadata filtering (especially ACLs), hybrid search, latency SLO, multi-tenancy, availability, team skills, existing stack, cost.
  • Rule of thumb: under roughly 5–10M vectors with simple filters, Postgres + pgvector is often enough and adds no new system. Dedicated stores earn their place with large scale, heavy filtering, hybrid search or multi-tenant isolation.
  • Run a two-week spike on real data before committing.

Why it succeeds

The choice matches the workload and the team's operating capacity. Capacity math exposes when quantization or sharding is needed, and the ADR makes the decision revisitable when scale changes, instead of being re-argued every quarter.

Reference implementation

def vector_memory_gb(n_vectors, dims, bytes_per_dim=4, index_overhead=0.3, replicas=2):
    raw = n_vectors * dims * bytes_per_dim / 1e9
    return round(raw * (1 + index_overhead) * replicas, 1)

vector_memory_gb(5_000_000, 768)                    # ~40 GB   float32, HNSW, 2 replicas
vector_memory_gb(5_000_000, 768, bytes_per_dim=1)   # ~10 GB   with int8 quantization
vector_memory_gb(200_000_000, 1024)                 # ~2,130 GB -> needs sharding / quantization
Key takeaway

Pick the vector store from requirements, capacity math and a spike on real data. Often the database you already run is enough.

2.8

ANN index defaults never measured

QualityLatency

Problem statement

Search got faster after moving from exact search to HNSW, but answer quality dropped a little. Nobody can say why.

The anti-pattern

Approximate nearest-neighbour parameters (M, ef_search, nprobe) are left at library defaults, and ANN recall is never compared with exact search.

Why the current design fails

  • ANN parameters set a recall/latency trade-off, and defaults weren't chosen for this corpus or SLO.
  • Without an exact-search baseline, the team trades quality for speed blindly.
  • As the corpus grows, recall can degrade further with no alert.

Recommended solution

Make ANN recall a tracked service-level indicator:

  1. Nightly, sample around 1,000 queries and compare ANN top-k with exact top-k.
  2. Alert if recall falls below an agreed level (for example 0.95).
  3. Tune ef_search or nprobe to the latency SLO using the measured curve.
  4. Re-check whenever the corpus grows significantly.

Why it succeeds

The speed/quality trade-off becomes an explicit, measured choice. The nightly SLI catches degradation as the index grows, before users notice quality loss.

Reference implementation

import faiss, numpy as np, time

def ann_recall(vectors, queries, k=10, ef_values=(16, 32, 64, 128)):
    d = vectors.shape[1]
    exact = faiss.IndexFlatIP(d); exact.add(vectors)
    _, truth = exact.search(queries, k)
    hnsw = faiss.IndexHNSWFlat(d, 32, faiss.METRIC_INNER_PRODUCT); hnsw.add(vectors)
    for ef in ef_values:
        hnsw.hnsw.efSearch = ef
        t0 = time.perf_counter(); _, approx = hnsw.search(queries, k)
        ms = (time.perf_counter() - t0) / len(queries) * 1000
        rec = np.mean([len(set(a) & set(t)) / k for a, t in zip(approx, truth)])
        print(f"ef_search={ef:>4}  recall@{k}={rec:.3f}  {ms:.2f} ms/query")
Key takeaway

Approximate search is a trade-off you should measure. Track ANN recall against exact search and tune to the latency SLO.

Follow-up to expect

2.9

One giant in-memory HNSW index

ReliabilityCostScale

Problem statement

The vector database node runs out of memory, index rebuilds take a day, and p99 latency spikes during compaction. The corpus has grown to 200 million chunks.

The anti-pattern

200 million float32 vectors held in one in-memory index on one node, as if it were a demo. 200M × 768 × 4 bytes is about 615 GB before graph overhead, with a single failure domain.

Why the current design fails

  • Memory, rebuild time and compaction all scale with the whole corpus, so every operation is slow and risky.
  • One node means one failure domain: any outage takes retrieval down entirely.
  • Most queries only need a slice of the corpus but pay for searching all of it.

Recommended solution

Shrink and split the index:

  • Quantize: int8 is about 4× smaller; binary or product quantization for candidates, then rescore the top few hundred with full-precision vectors.
  • Reduce dimensions if the model supports it (Matryoshka-style truncation).
  • Shard by a natural key (tenant, region, document type) so most queries hit one shard.
  • Consider disk-based ANN for cold data, and replicate shards for availability.

Why it succeeds

Memory per node drops by an order of magnitude, rebuilds are per shard, and most queries touch one small shard. Rescoring recovers most of the recall lost to quantization, and replicas remove the single failure domain.

Reference implementation

def plan_index(n_vectors, dims, shards, bytes_per_dim=1, overhead=0.3, replicas=2):
    per_shard_gb = n_vectors / shards * dims * bytes_per_dim * (1 + overhead) / 1e9
    return {"per_shard_gb": round(per_shard_gb, 1), "total_gb": round(per_shard_gb * shards * replicas, 1)}

plan_index(200_000_000, 768, shards=16)          # int8: ~12.5 GB per shard

def search(q, tenant):
    shard = router.shard_for(tenant)              # most queries hit one shard
    cands = shard.search_quantized(embed(q), k=300)
    return rescore_full_precision(q, cands)[:10]  # recover recall lost to quantization
Key takeaway

At hundreds of millions of vectors, quantize, shard by a natural key and replicate. One giant in-memory index is a single point of failure.

2.10

Post-filtering highly selective metadata filters

QualitySecurity

Problem statement

A user in a small department gets 0–2 results, or irrelevant ones, even though the answer exists in documents they're allowed to see.

The anti-pattern

ANN search returns the top 100 across all 100M chunks, and only then drops what the user can't see or what doesn't match the filter.

Why the current design fails

  • If the filter keeps 0.01% of the corpus, almost all 100 candidates are discarded.
  • Users with narrow permissions or rare filters systematically get worse answers.
  • Raising k to compensate makes every query slower without fixing the root cause.

Recommended solution

Filter during search:

  • Use a store with filter-aware ANN (filtered HNSW, payload indexes).
  • Partition or shard on high-selectivity keys (tenant, region).
  • For very selective filters, fall back to exact search over the filtered subset, which is small by definition.

Why it succeeds

Every user gets a full candidate set from the documents they can actually see. Exact search on small subsets is both accurate and fast, and partitioning keeps large tenants from crowding out small ones.

Reference implementation

def filtered_search(q, flt, k=10):
    n = index.count(filter=flt)
    if n < 20_000:
        return exact_search(embed(q), ids=index.ids(filter=flt), k=k)   # tiny subset: exact is cheap
    return index.search(embed(q), k=k, filter=flt)                       # filter-aware ANN

metrics.inc("results_below_k", filter=flt_name) if len(hits) < k else None   # catch it per filter
Key takeaway

Post-filtering starves users with narrow permissions. Filter inside the search, partition on selective keys, and use exact search for tiny subsets.

2.11

ACLs copied once at ingest, plus a shared answer cache

SecurityCompliance

Problem statement

An employee who moved out of Finance still gets answers from Finance documents. Worse, user B receives user A's cached answer containing a salary figure.

The anti-pattern

Permissions are snapshotted at index time and never synced, and a semantic or answer cache is keyed only on the query text and shared across users with different access.

Why the current design fails

  • Revocations never reach the index, so former entitlements live on indefinitely.
  • A shared cache bypasses retrieval-time security entirely: the first user's answer is served to everyone who asks a similar question.
  • Storing per-user ACLs on chunks explodes index size, so teams avoid syncing at all.

Recommended solution

  • Store group-level ACLs on chunks (not individual users) and resolve the user's current groups from the identity provider on every request.
  • Sync permission changes as their own event stream, which is far cheaper than re-embedding.
  • Scope every cache key by tenant and a hash of the permission set, and invalidate on permission changes.
  • For hard multi-tenant isolation, use a separate namespace or index per large tenant.

Why it succeeds

Revocations take effect within minutes, and no cached answer can cross a permission boundary. An automated access test suite ("user X must never see doc Y") and a canary document per tenant prove it on every deploy.

Reference implementation

def cache_key(q, user):
    perm = sha256(",".join(sorted(user.groups)))[:16]
    return f"{user.tenant}:{perm}:{normalize(q)}"

@idp.on("group_membership_changed")
def on_membership(evt):
    cache.invalidate(prefix=f"{evt.tenant}:")             # permission-scoped invalidation

def test_access(user="finance-leaver", doc="FIN-SALARY-2026"):
    assert doc not in [h.doc_id for h in secure_search("salary bands", token_for(user))]
Key takeaway

Permissions change after ingestion and caches cross users. Sync ACLs as events, resolve groups per request, and scope every cache by permission set.

2.12

Noisy neighbours in a shared retrieval cluster

ReliabilityLatencyScale

Problem statement

One enterprise tenant starts a 30-million-document backfill, and every other tenant's retrieval latency triples.

The anti-pattern

Ingestion and queries share one compute pool with no isolation or quotas.

Why the current design fails

  • Bulk ingestion competes with interactive queries for CPU, memory and I/O.
  • One tenant's activity sets everyone else's latency, which breaks SLAs for all tenants.
  • Without per-tenant metrics, the cause isn't visible.

Recommended solution

  • Separate ingestion and query compute.
  • Apply per-tenant rate limits and quotas.
  • Give the largest tenants dedicated shards or namespaces.
  • Schedule backfills off-peak with throttling, and autoscale query replicas on p95 latency.

Why it succeeds

Interactive latency no longer depends on other tenants' bulk work. Dedicated resources cost more and run at lower utilization, which is the price of predictable SLOs. Per-tenant p95 and error-rate alerts make any remaining contention visible.

Reference implementation

ingest_limiter = TokenBucket(rate_per_tenant={"default": 50, "enterprise-a": 200})   # docs/s

def submit_backfill(tenant, docs):
    job = ingest_queue.enqueue(tenant, docs, window="off_peak", throttle=ingest_limiter.rate(tenant))
    return job.id

# query pool autoscaling (KEDA): trigger on per-pool p95 latency, separate from ingestion workers
metrics.histogram("retrieval_p95_ms", labels={"tenant": tenant})   # alert per tenant
Key takeaway

Isolate ingestion from queries and tenants from each other. Without quotas, one backfill sets everyone's latency.
