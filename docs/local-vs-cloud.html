17Local LLMs vs Hyperscaler Hosting (Cost Management)

Self-hosting open-weight models can cut costs dramatically or burn money quietly. The difference is usage level, utilization and operational maturity.

6 anti-patterns

The deployment spectrum

Option Examples You pay for You operate
Managed API (pay per token) Bedrock, Foundry Models, Agent Platform, first-party model APIs Tokens Nothing below the API
Reserved / provisioned capacity Provisioned Throughput, PTUs Committed capacity Capacity planning
Self-hosted on cloud GPUs vLLM / SGLang / TGI on EKS, GKE, AKS; SageMaker; NVIDIA NIM GPU hours (busy or idle) Serving stack, scaling, patching, model lifecycle
On-prem / edge Ollama, llama.cpp, NIM on owned hardware, AI PCs Capex + power + staff Everything

What a real TCO comparison includes

  • GPU cost at realistic utilization. Interactive workloads often run at 20–40% average utilization because of peaks and redundancy.
  • People: platform and MLOps engineers to run serving, autoscaling, upgrades, security patching and on-call.
  • Quality gap: an open model that's 5 points worse on your eval may need more human review, which costs more than the tokens saved.
  • Model refresh: re-evaluating and redeploying as new open models ship every few months.
  • Hidden infrastructure: load balancers, storage for weights, observability, redundancy across zones.

17.1

Self-hosting "to save money" at low or spiky usage

Cost

Problem statement

A mid-size insurer moves its claims-summary workload (~40M tokens a month) from a managed API to two dedicated GPU nodes running an open model. The monthly bill rises fivefold, mostly for GPUs idling overnight and at weekends.

The anti-pattern

Comparing the per-token API price with a theoretical per-token cost at 100% GPU utilization, then deploying always-on GPUs for a small or bursty workload.

Why the current design fails

  • Fixed costs dominate at low usage. A GPU costs the same whether it serves one request or a thousand.
  • Redundancy doubles the floor. Production needs at least two replicas across zones.
  • Bursty traffic forces provisioning for peak.

Recommended solution

  • Measure monthly tokens, peak-to-average ratio and latency needs per workload.
  • Build a TCO model that includes GPU hours at realistic utilization, redundancy, engineering FTEs and the quality-adjusted cost (human review).
  • Self-host only when steady usage is well above break-even, or when another driver (sovereignty, air-gap, latency, customization) justifies it.
  • For bursty self-hosted workloads, use scale-to-zero serverless GPU options or batch scheduling.

Why it succeeds

The decision rests on real numbers. Low-usage workloads stay on pay-per-token pricing, where cost follows demand, and high-usage, steady workloads move to self-hosting where the fixed cost is spread across enough work to win.

Reference implementation

def monthly_tco_selfhost(tokens_m, gpu_hr_usd, tokens_per_gpu_hr_m, util=0.35, replicas_min=2, fte=0.5,
                         fte_cost=18_000, infra_overhead=0.15):
    gpu_hours = max(replicas_min * 730, tokens_m / (tokens_per_gpu_hr_m * util))
    return gpu_hours * gpu_hr_usd * (1 + infra_overhead) + fte * fte_cost

def monthly_tco_api(tokens_m, usd_per_m_blended, cache_hit=0.3, cache_discount=0.9):
    return tokens_m * usd_per_m_blended * (1 - cache_hit * cache_discount)

decision = "self-host" if monthly_tco_selfhost(T, ...) < 0.7 * monthly_tco_api(T, ...) else "managed API"
Key takeaway

Self-hosting trades variable cost for fixed cost. It only pays off when steady usage is high enough to keep GPUs busy, and people are counted in the TCO.

17.2

Comparing token prices while ignoring operations and quality

CostQuality

Problem statement

A business case shows a 70% saving from switching to a self-hosted open model. After launch, the model's lower accuracy on complex claims raises manual-review rates from 8% to 19%, wiping out the saving.

The anti-pattern

The cost comparison stops at infrastructure. Quality differences, the cost of errors and the operating team aren't in the model.

Why the current design fails

  • Errors cost more than tokens. One extra human review can cost far more than thousands of model calls.
  • The ops team is real. Serving, scaling, upgrades, security and on-call need people.
  • Upgrades aren't free. Each new open model needs evaluation, quantization testing and redeployment.

Recommended solution

Compare on cost per correct business outcome:

cost per outcome = (inference + infra + ops) / successful outcomes + error rate × cost of an error

  • Run both models on the same eval suite. Measure accuracy per segment and downstream effects (escalations, rework).
  • Price the error cost with the business (review minutes, customer impact, regulatory exposure).
  • Include operating headcount and an upgrade cadence in the model.

Why it succeeds

The metric captures what the business actually pays for. It often shows a hybrid answer: open models for easy, high-volume segments, frontier models for complex ones. It also gives finance a defensible business case.

Reference implementation

def cost_per_outcome(model, segment, volume, error_cost_usd):
    acc = evals[model][segment]["accuracy"]
    infra = infra_cost(model, volume[segment])
    return (infra + ops_cost(model)) / (volume[segment] * acc) + (1 - acc) * error_cost_usd

plan = {seg: min(MODELS, key=lambda m: cost_per_outcome(m, seg, volume, ERROR_COST[seg]))
        for seg in SEGMENTS}         # often: open model for simple segments, frontier for complex
Key takeaway

The right unit is cost per correct outcome, not cost per token. Price the errors and the operating team before claiming savings.

17.3

Unoptimized self-hosted serving (no batching, quantization or KV cache reuse)

CostLatency

Problem statement

A team serves an open 70B model with a basic Python inference server, one request at a time at full precision. They need eight GPUs to handle a load that an optimized stack serves on two.

The anti-pattern

Self-hosting with naive serving: static batching or none, unquantized weights, no prefix caching, and default autoscaling based on CPU.

Why the current design fails

  • Low throughput per GPU multiplies hardware cost.
  • Memory waste from unmanaged KV cache limits concurrency.
  • Wrong scaling signals. CPU metrics don't reflect GPU queue depth.

Recommended solution

  • Use a modern inference engine (vLLM, SGLang, TensorRT-LLM or NVIDIA NIM) with continuous batching and paged KV-cache management.
  • Enable prefix caching for shared system prompts and RAG templates.
  • Quantize (FP8, AWQ/GPTQ INT4) after validating accuracy on your evals.
  • Consider speculative decoding for latency-sensitive paths.
  • Autoscale on queue depth and time-to-first-token, not CPU.
  • Right-size the model: a fine-tuned 8B model often beats a generic 70B on a narrow task.

Why it succeeds

These techniques commonly raise throughput per GPU severalfold, which directly divides hardware cost. Validating quantization on evals protects quality, and queue-based autoscaling matches capacity to real demand.

Reference implementation

# vLLM: continuous batching is on by default; enable prefix caching + FP8
# vllm serve <open-model> --quantization fp8 --enable-prefix-caching \
#   --max-num-seqs 256 --gpu-memory-utilization 0.92 --tensor-parallel-size 2

# Kubernetes HPA on custom metric (queue depth) instead of CPU
# metrics:
# - type: Pods
#   pods: {metric: {name: vllm_num_requests_waiting}, target: {type: AverageValue, averageValue: "8"}}
Key takeaway

If you self-host, the serving stack is the cost lever. Continuous batching, prefix caching and validated quantization decide how many GPUs you need.

17.4

All-or-nothing hosting with no hybrid routing

CostQuality

Problem statement

A company debates for months whether to go "all open-source on-prem" or "all managed frontier API". Both options are bad for parts of their workload.

The anti-pattern

Hosting is treated as a single binary decision for the whole AI estate, not a per-workload routing choice.

Why the current design fails

  • All-frontier overpays for simple, high-volume tasks.
  • All-local under-serves complex reasoning and agentic tasks.
  • Analysis paralysis delays value.

Recommended solution

Build a hybrid model mesh behind one gateway:

  • Local or self-hosted small models for high-volume simple tasks, highly sensitive data, or offline/edge needs.
  • Managed frontier models for complex reasoning, coding and agentic planning.
  • A router that considers task type, data classification, required quality and cost, with confidence-based escalation.
  • One evaluation framework and one observability stack across both.

Why it succeeds

The estate gets the low unit cost of local models where they suffice and frontier quality where it matters. Sensitive data can stay local by policy, and teams start delivering value instead of debating the architecture.

Reference implementation

def route(req):
    if req.data_class == "restricted" and not req.allow_external:
        return local_models.pick(req.task)                  # sovereignty first
    if req.task in SIMPLE_TASKS and volume_high(req.task):
        out = local_models.pick(req.task).generate(req)
        return out if out.confidence >= 0.75 else frontier.generate(req)   # escalate
    return frontier.generate(req)
Key takeaway

Local versus cloud is a routing decision, not a religion. Send each request to the cheapest compliant model that meets its quality bar.

17.5

Assuming "local" automatically means secure and compliant

SecurityCompliance

Problem statement

A government agency runs open models on-prem "for security". An audit finds unpatched inference servers, model weights downloaded from an unverified mirror, a license that restricts their use case, and no logging.

The anti-pattern

Equating physical location with security. Self-hosted models skip supply-chain checks, licensing review, patching and monitoring that a managed service would have provided.

Why the current design fails

  • Model supply-chain risk: tampered weights and unsafe serialization formats can execute code on load.
  • License non-compliance: open-weight licenses vary (acceptable-use policies, user thresholds, field-of-use limits).
  • Operational security debt: unpatched CUDA drivers, inference servers and containers.
  • Missing controls: no guardrails, no audit logs, no evals.

Recommended solution

  • Source models from verified publishers, verify hashes and signatures, prefer safetensors formats, and scan artifacts.
  • Run license review in the intake process.
  • Run serving on hardened, patched images with vulnerability scanning and network isolation.
  • Route local models through the same AI gateway, guardrails, tracing and eval gates as cloud models.
  • Keep an AI bill of materials (model, version, source, license, fine-tune data).

Why it succeeds

Local deployment then delivers the sovereignty it promised, without new supply-chain or compliance holes. One control framework across local and cloud keeps governance consistent and auditable.

Reference implementation

def register_local_model(artifact, meta):
    assert meta["format"] == "safetensors", "no pickle-based formats"
    assert sha256(artifact) == meta["publisher_sha256"], "hash mismatch"
    assert sigstore.verify(artifact, meta["signature"]), "signature invalid"
    assert license_review.approved(meta["license"], use_case=meta["use_case"])
    scan = model_scanner.scan(artifact)
    assert not scan.findings, scan.findings
    aibom.record(meta | {"scan": scan.id})
    return model_registry.add(artifact, meta)
Key takeaway

On-prem isn't automatically secure. Verify the model supply chain, review licenses, patch the stack, and hold local models to the same controls as cloud.

17.6

No caching layer in front of any model

CostLatency

Problem statement

An HR assistant answers "How many vacation days do I get?" 9,000 times a month. Each time it runs full retrieval and generation.

The anti-pattern

Every request runs the full pipeline, whatever the model hosting. There's no exact, semantic or prompt-prefix caching.

Why the current design fails

  • Repeated identical work for frequent questions.
  • Higher latency for answers that could be instant.
  • Wasted capacity on reserved or self-hosted GPUs.

Recommended solution

Use layered caching:

  1. Prompt or prefix caching at the model layer for stable system prompts and documents (available on the managed APIs; prefix caching in vLLM).
  2. Exact-match cache on normalized query plus user scope.
  3. Semantic cache for paraphrases above a high similarity threshold. Scope it by permission group and language, and invalidate it when source documents change.
  4. Never cache across permission boundaries, and never cache personalized answers globally.

Why it succeeds

High-frequency questions are answered in milliseconds at near-zero marginal cost. Prefix caching cuts the cost of the misses too. Scoping and invalidation keep caching from creating leakage or staleness.

Reference implementation

def cached_answer(q, user):
    scope = f"{user.permission_hash}:{user.lang}"
    if (hit := exact_cache.get(scope, normalize(q))): return hit
    if (hit := semantic_cache.nearest(scope, embed(q), min_sim=0.95)) and not hit.stale():
        return hit.answer
    ans = rag_answer(q, user)
    semantic_cache.put(scope, embed(q), ans, doc_ids=ans.source_doc_ids, ttl=86400)
    return ans

on_document_change(lambda doc_id: semantic_cache.invalidate(doc_ids=[doc_id]))
Key takeaway

The cheapest model call is the one you don't make. Layer prefix, exact and semantic caches, scoped by permissions and invalidated by source changes.
