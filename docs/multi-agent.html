8Multi-Agent Systems

Multiple agents can parallelize work and isolate context. They also multiply cost, latency and failure modes. These anti-patterns show the difference.

8.1

Multi-agent for its own sake ("the org chart in code")

CostReliability

Problem statement

A marketing team builds a "CMO agent" that manages a "copywriter agent", an "SEO agent", a "brand agent" and a "legal agent" to write a product description. It takes 3 minutes, costs 40× a single call, and the output is worse than one good prompt.

The anti-pattern

Agents are created to mirror human job titles. Each hand-off is a conversation, and the topology is chosen for the demo narrative.

Why the current design fails

  • Information loss at every hand-off. Each agent sees a summary of a summary.
  • Cost and latency multiply with the number of agents and rounds of conversation.
  • Coordination failures. Agents disagree, repeat work, or wait on each other.
  • Harder evaluation. Responsibility for a bad output is spread across agents.

Recommended solution

Use multiple agents only for specific, measurable reasons:

  • Parallelism: independent subtasks such as researching ten competitors at once.
  • Context isolation: subtasks that would otherwise flood one context window, such as reading many large documents.
  • Separation of privilege: different tools or data permissions per agent.

Otherwise, use one capable agent with good tools, plus deterministic checks (a legal-term linter, SEO rules) instead of LLM "reviewer" agents. Benchmark the multi-agent design against the single-agent baseline on quality, cost and latency.

Why it succeeds

Each additional agent has to justify itself in throughput, context capacity or security. Deterministic checks are cheaper and more reliable than agent debates. The simpler architecture is easier to evaluate, and multi-agent designs remain available when evidence supports them.

Reference implementation

# Orchestrator–worker only where subtasks are independent and context-heavy
async def competitive_research(companies):
    briefs = await asyncio.gather(*[
        sub_agent(f"Research {c}: pricing, launches, hiring signals",
                  tools=[web_search, fetch], budget=Budget(steps=12)) for c in companies])
    return lead_agent.synthesize(briefs)       # sub-agents return condensed findings, not transcripts

# Product copy: single agent + deterministic checks, no agent "committee"
draft = llm.generate(COPY_PROMPT, product=p)
issues = legal_linter(draft) + seo_rules(draft) + brand_terms(draft)
final = llm.revise(draft, issues) if issues else draft
Key takeaway

Agents aren't headcount. Add one only for parallelism, context isolation or privilege separation, and prove it beats the single-agent baseline.

8.2

Chatty agents passing full transcripts

CostLatency

Problem statement

In a supply-chain planning system, each agent forwards its entire conversation history to the next. By the fourth agent, the context is 180K tokens and most of it is irrelevant intermediate reasoning.

The anti-pattern

Agents communicate through free-form natural-language chat, passing complete transcripts and intermediate tool outputs to each other.

Why the current design fails

  • Token cost grows with every hop.
  • Signal drowns in noise. Downstream agents struggle to find the facts they need.
  • No contract. Nobody knows what an agent is required to provide or can rely on receiving.

Recommended solution

Use typed hand-off contracts:

  • Define the output schema for each agent (findings, decisions, open questions, artifact references).
  • Pass large artifacts by reference (file or blob IDs), not inline.
  • Summarize or compress before hand-off. Discard raw tool output and scratch reasoning.
  • Validate hand-offs, and reject or repair malformed ones.

Why it succeeds

Context stays small and relevant, so cost and latency stay roughly flat as the pipeline grows. Contracts make each agent independently testable and replaceable, and references keep heavy data out of prompts while staying accessible when needed.

Reference implementation

class DemandForecastHandoff(BaseModel):
    sku_forecasts: list[SkuForecast]          # compact, typed
    assumptions: list[str]
    risks: list[str]
    artifact_refs: dict[str, str]             # {"model_run": "s3://.../run-8812.parquet"}

fc = forecaster.run(task, output_schema=DemandForecastHandoff)
plan = supply_planner.run(goal="build replenishment plan", inputs=fc.model_dump())   # no transcript
Key takeaway

Agents should exchange contracts, not conversations. Use typed hand-offs, pass artifacts by reference, and throw away scratch work.

8.3

No supervisor, contract or termination condition

Reliability

Problem statement

A peer-to-peer group of "researcher", "critic" and "writer" agents debates a market-entry memo. The critic always finds something to improve, so the conversation never converges and is cut off by a timeout.

The anti-pattern

Agents talk freely in a group chat with no orchestrator, no defined completion criteria and no authority to decide when the work is done.

Why the current design fails

  • No convergence. Critique loops can run forever.
  • No accountability. No single component owns the final result or the decision to stop.
  • Unpredictable control flow that can't be tested.

Recommended solution

Use an explicit orchestration topology:

  • Supervisor/orchestrator owns the plan, assigns bounded tasks, and decides completion.
  • Acceptance criteria as a rubric (sections present, sources cited, numbers reconciled), checked by code where possible.
  • Revision limits: at most N critique rounds, then escalate to a human with the open issues.
  • Express the topology as a graph with explicit edges and conditions, not as free chat.

Why it succeeds

There's always one owner of "done". Rubric-based acceptance makes quality objective and testable. Revision limits bound cost and guarantee termination, and the graph topology is reviewable and testable like any other code.

Reference implementation

def supervise(goal):
    plan = supervisor.plan(goal)                       # bounded tasks with owners
    results = {t.id: workers[t.role].run(t) for t in plan.tasks}
    draft = writer.run(goal, results)
    for attempt in range(2):                           # revision limit
        gaps = rubric.check(draft)                     # deterministic + judge criteria
        if not gaps: return draft
        draft = writer.revise(draft, gaps)
    return escalate_to_human(draft, open_issues=rubric.check(draft))
Key takeaway

Every multi-agent system needs an owner of "done": a supervisor, acceptance criteria and a revision limit.

8.4

Shared mutable memory without concurrency control

Reliability

Problem statement

Parallel agents processing insurance claims all read and write a shared "case notes" scratchpad. Two agents overwrite each other's updates, and one claim is approved on the basis of another claim's notes.

The anti-pattern

Agents share one global blackboard (a dict, document or memory store) with unrestricted read/write access and no keys, versions or locks.

Why the current design fails

  • Race conditions and lost updates when agents run in parallel.
  • Cross-contamination between unrelated tasks or customers.
  • Unattributable state. Nobody knows which agent wrote what, or when.

Recommended solution

Treat shared agent state as a concurrent data structure:

  • Scope state by task, case or tenant. Agents get only the keys they need.
  • Prefer append-only event logs with reducers that merge updates deterministically (the pattern LangGraph state reducers use).
  • Use optimistic concurrency (version numbers, compare-and-swap) for mutable records.
  • Record writer_agent, timestamp and step for every write.

Why it succeeds

Scoping prevents cross-contamination by construction. Append-only logs plus reducers remove lost updates and give a full history. Optimistic locking surfaces conflicts instead of hiding them, and attribution makes debugging and audit straightforward.

Reference implementation

from typing import Annotated
import operator

class ClaimState(TypedDict):
    claim_id: str
    findings: Annotated[list[Finding], operator.add]     # append-only; parallel writes merge
    decision: Decision | None

def write_decision(store, claim_id, decision, expected_version, agent):
    ok = store.compare_and_set(key=f"claim:{claim_id}:decision", value=decision,
                               version=expected_version, meta={"writer": agent, "ts": now()})
    if not ok: raise ConflictError("decision changed by another agent; re-read and retry")
Key takeaway

Shared agent memory is a concurrency problem. Scope it, append rather than overwrite, version mutable records, and attribute every write.

8.5

Cascading failures with no circuit breakers

ReliabilityCost

Problem statement

A data-extraction agent starts returning malformed results after an upstream API change. Three downstream agents keep consuming its output, compounding errors, and 4,000 incorrect records are written to the ERP before anyone notices.

The anti-pattern

Agents trust each other's outputs implicitly. There's no validation between stages, no health tracking per agent, and no automatic stop when error rates spike.

Why the current design fails

  • Errors propagate and amplify through the chain.
  • No blast-radius control. Bad output reaches systems of record.
  • Late detection. Problems are found by downstream users, not by monitoring.

Recommended solution

Apply resilience engineering between agents:

  • Validate every hand-off against its schema and invariants.
  • Track per-agent error and validation-failure rates. Open a circuit breaker when a threshold is crossed, pausing the stage and alerting.
  • Write to systems of record through a staging/quarantine area with reconciliation checks before commit.
  • Use canary releases and anomaly detection on output distributions (volumes, value ranges).

Why it succeeds

Bad output is stopped at the first boundary, not discovered in the ERP. Circuit breakers turn a silent cascade into a visible incident with bounded damage, and staging writes give a final gate that is cheap to roll back.

Reference implementation

class AgentBreaker:
    def __init__(self, name, threshold=0.05, window=200):
        self.name, self.threshold, self.results = name, threshold, deque(maxlen=window)
    def record(self, ok): self.results.append(ok)
    @property
    def open(self): return len(self.results) > 50 and 1 - mean(self.results) > self.threshold

def stage(agent, payload, schema, breaker):
    if breaker.open: raise StagePaused(agent.name)
    out = agent.run(payload)
    ok = schema.validate(out) and invariants_hold(out)
    breaker.record(ok)
    return out if ok else quarantine(out)
Key takeaway

Agent pipelines need the resilience patterns of distributed systems: contract checks, circuit breakers and staged writes.

8.6

Sub-agents with vague briefs

QualityCost

Problem statement

An orchestrator agent sends three research workers the instruction "look into competitor pricing". They duplicate each other's work and return inconsistent prose that the orchestrator can't merge.

The anti-pattern

Workers get one-line, open-ended instructions with no scope boundaries, tools or output format.

Why the current design fails

  • Without scope boundaries, workers overlap and waste tokens on the same sources.
  • Free-text outputs can't be merged, deduplicated or checked automatically.
  • Errors in one worker go unnoticed because nothing defines what "done" looks like.

Recommended solution

  • The orchestrator writes precise briefs: objective, scope boundaries (what not to cover), allowed tools and an output schema.
  • Validate worker outputs against the JSON schema; reject and re-brief on failure.
  • Merge, deduplicate and verify centrally.
  • Track overlap between worker outputs and end-task accuracy.

Why it succeeds

Non-overlapping scopes remove duplicate spend, and structured outputs make merging and verification mechanical. The overlap metric shows immediately when briefs are too loose.

Reference implementation

class Brief(BaseModel):
    objective: str
    in_scope: list[str]; out_of_scope: list[str]
    tools: list[str]
    output_schema: dict

class PricingFinding(BaseModel):
    competitor: str; plan: str; monthly_price: Decimal; source_url: str; as_of: date

briefs = [Brief(objective=f"Collect current consumer plan prices for {c}",
                in_scope=[c], out_of_scope=[x for x in COMPETITORS if x != c],
                tools=["web_search", "fetch"], output_schema=PricingFinding.model_json_schema())
          for c in COMPETITORS]
results = [list_of(PricingFinding).validate(worker.run(b)) for b in briefs]
merged = dedupe(flatten(results), key=lambda f: (f.competitor, f.plan))
Key takeaway

Sub-agents are only as good as their briefs. Give each a scoped objective, tools and an output schema, then merge and verify centrally.

8.7

Supervisor agent becomes the bottleneck for every request

ReliabilityLatencyFinTech

Problem statement

A bank builds a supervisor agent that receives every customer message, decides which of 8 specialist agents should handle it, receives the specialist's answer, and rewrites it before replying. Simple balance questions take 4 LLM calls and 7 seconds, and the supervisor's rewriting sometimes changes amounts.

The anti-pattern

Supervisor handles and rewrites everything.

Think of it this way: A manager who insists on reading and rewording every email the team sends.

Why the current design fails

  • Every request passes through two extra LLM calls.
  • Rewriting adds errors to correct specialist answers.
  • The supervisor's context grows with every specialist's output.

Root cause: A heavyweight supervisor where a router would do.

Where it breaks: Orchestration design.

Recommended solution

  1. Use a lightweight router (small model or classifier) and let the specialist reply directly.
  2. Use a supervisor only for multi-step tasks that need several specialists.
  3. Never let an agent rewrite facts it didn't produce; pass structured data through.

Why it succeeds

Trade-off to manage: Less uniform voice across specialists; enforce style with shared guidelines.

How you prove it worked:

  • LLM calls per simple intent; fact changes between specialist and final answer.

Same pattern elsewhere: Telco: a care supervisor agent paraphrases the billing agent's amounts and rounds them wrongly.

Reference implementation

def handle(msg, ctx):
    intent = router.classify(msg)                          # small model / classifier, ~50 ms
    if intent.kind == "single":
        return SPECIALISTS[intent.domain].reply(msg, ctx)   # specialist answers directly
    plan = supervisor.plan(msg, ctx)                       # only multi-specialist tasks
    results = {s.domain: SPECIALISTS[s.domain].run(s.task) for s in plan.steps}
    return supervisor.compose(results, facts_passthrough=True)   # never rewrites specialists' facts
Key takeaway

Route simple work. Supervise only complex work.

8.8

Planner and critic agents debate for 40 rounds

ReliabilityCostTelco

Problem statement

A carrier's network-planning system pairs a planner agent with a critic agent to improve cell-site upgrade plans. The critic always finds something to improve. They exchange 40 rounds per plan, costing $70 each, and the final plans are no better than round 3.

The anti-pattern

Critic loop until satisfied.

Think of it this way: Two editors passing a draft back and forth forever because each can always find a comma to change.

Why the current design fails

  • No termination condition except "critic satisfied".
  • Critics are prompted to criticise, so they always do.
  • Quality plateaus early.

Root cause: Unbounded reflection loops.

Where it breaks: Multi-agent control flow.

Recommended solution

  1. Cap rounds (2-3), and stop when the critic finds no high-severity issues.
  2. Make the critic check against explicit criteria (budget, coverage targets, constraints) and return structured issues.
  3. Measure quality per round to choose the cap.

Why it succeeds

Trade-off to manage: Caps can stop before a real fix; allow escalation to a human.

How you prove it worked:

  • Rounds per task and quality by round.

Same pattern elsewhere: FinTech: a credit-memo writer and reviewer agent loop on wording for dozens of rounds.

Reference implementation

class Issue(BaseModel):
    criterion: Literal["budget", "coverage_target", "constraint"]; severity: Literal["low", "high"]; detail: str

plan = planner.draft(goal)
for rnd in range(3):                                     # cap rounds
    issues = critic.review(plan, criteria=CRITERIA, schema=list[Issue])
    quality_log.append((rnd, score(plan)))
    if not any(i.severity == "high" for i in issues):
        break
    plan = planner.revise(plan, issues)
Key takeaway

Reflection has diminishing returns. Cap it.

8.9

Two agents update the same fraud case at once

ReliabilityFinTech

Problem statement

In a bank's fraud system, a triage agent and a customer-contact agent both write to the same case record. The triage agent marks a transaction as fraud while the contact agent, reading stale state, records the customer's confirmation that a different transaction was genuine. The case ends with the wrong transaction refunded.

The anti-pattern

Two agents write the same case freely.

Think of it this way: Two people editing the same spreadsheet cell offline and syncing later.

Why the current design fails

  • Shared mutable state without ownership rules.
  • No concurrency control (versions, locks).
  • Agents act on stale reads.

Root cause: No state ownership or concurrency control between agents.

Where it breaks: State design.

Recommended solution

  1. Give each field or record section a single owning agent; others propose changes via events.
  2. Use optimistic concurrency (version numbers) and reject stale writes.
  3. Keep the case as an event log so actions can be reconstructed.

Why it succeeds

Trade-off to manage: Event-based updates are more complex than direct writes.

How you prove it worked:

  • Stale-write rejections; conflicting updates per case.

Same pattern elsewhere: Telco: an order agent and a billing agent both update a customer's product inventory and leave it inconsistent.

Reference implementation

OWNERS = {"risk_assessment": "risk_agent", "customer_contact": "comms_agent", "card_status": "card_agent"}

def write_case(case_id, section, value, agent, expected_version):
    if OWNERS[section] != agent:
        return events.publish("case.change_proposed", case_id=case_id, section=section, value=value, by=agent)
    ok = cases.update_if_version(case_id, section, value, expected_version)   # optimistic concurrency
    if not ok: raise StaleWrite(case_id, section)
    events.append(case_id, {"section": section, "value": value, "by": agent})  # event log
Key takeaway

Shared state needs an owner and a version number.

8.10

Facts lost in a chain of agent summaries

ReliabilityTelco

Problem statement

A B2B complaint flows through four agents: intake, analysis, resolution and communication. Each passes a prose summary to the next. The customer's key detail ("outage affected only the Dallas site, between 2 and 4 pm") becomes "customer had an outage" by the fourth agent, and the credit is calculated for all sites.

The anti-pattern

Prose summaries between agents.

Think of it this way: The telephone game, where a message changes with every whisper.

Why the current design fails

  • Each handoff summarises and loses detail.
  • Facts aren't carried as structured data.
  • The last agent can't see the original.

Root cause: Prose summaries as the handoff format.

Where it breaks: Handoff design.

Recommended solution

  1. Carry key facts as structured fields (sites, times, services, amounts) end to end.
  2. Store original inputs in shared state referenced by id.
  3. Validate that required facts survive each hop.

Why it succeeds

Trade-off to manage: Schemas take design work.

How you prove it worked:

  • Fact-retention tests across the chain.

Same pattern elsewhere: FinTech: a loan application loses the co-applicant's income across three agents and is declined.

Reference implementation

class OutageFacts(BaseModel):
    sites: list[str]; start: datetime; end: datetime | None
    services: list[str]; customers_affected: int; source_refs: list[str]

def hop(agent, facts: OutageFacts, task):
    out = agent.run(task, facts=facts.model_dump())        # structured fields end to end
    new = OutageFacts.model_validate(out["facts"])
    assert set(facts.sites) <= set(new.sites), "facts lost in handoff"
    return new
Key takeaway

Pass facts as data, not as retellings.

8.11

Three agents message the customer at once

ReliabilityFinTech

Problem statement

A bank's dispute system lets the intake agent, the evidence agent and the decision agent each message the customer directly. A customer receives three messages in two minutes with different tones, one asking for documents already provided.

The anti-pattern

Every agent talks to the customer.

Think of it this way: Three departments calling a customer about the same order on the same afternoon.

Why the current design fails

  • No single agent owns the conversation.
  • Messages aren't coordinated or deduplicated.
  • State about what was asked isn't shared.

Root cause: Multiple agents with direct customer access.

Where it breaks: Multi-agent architecture.

Recommended solution

  1. Give one agent ownership of customer communication; others send it requests.
  2. Track outstanding asks in shared state, and deduplicate.
  3. Apply one tone and style guide.

Why it succeeds

Trade-off to manage: The owning agent becomes a dependency; keep it simple.

How you prove it worked:

  • Messages per customer per hour; duplicate asks.

Same pattern elsewhere: Telco: an installation-scheduling agent and a billing agent both text the customer about the same order.

Reference implementation

class CommsOwner:
    def __init__(self): self.pending = {}
    def request(self, from_agent, ask):                     # other agents never message the customer
        key = normalize(ask.question)
        self.pending.setdefault(key, ask)                    # dedupe outstanding asks
    def flush(self, customer):
        if self.pending:
            msg = compose(list(self.pending.values()), style=STYLE_GUIDE)
            channel.send(customer, msg); self.pending.clear()
Key takeaway

One voice per customer.

8.12

Agents delegate a task back and forth

ReliabilityLatencyTelco

Problem statement

A carrier's billing agent delegates a disputed roaming charge to the roaming agent, which decides it's a billing issue and delegates it back. The task bounces 30 times before a timeout, and the customer waits 10 minutes for nothing.

The anti-pattern

Agents delegate without cycle checks.

Think of it this way: Two departments each saying "that's the other team's job".

Why the current design fails

  • Agents can delegate to each other without cycle detection.
  • Responsibilities overlap.
  • No fallback owner.

Root cause: Delegation graph with cycles and unclear ownership.

Where it breaks: Orchestration rules.

Recommended solution

  1. Define clear responsibility boundaries per agent.
  2. Track the delegation path and forbid revisiting an agent for the same task.
  3. Route unresolved tasks to a default owner or a human.

Why it succeeds

Trade-off to manage: None significant.

How you prove it worked:

  • Delegation depth and cycles per task.

Same pattern elsewhere: FinTech: a card agent and a fraud agent pass a suspicious transaction back and forth.

Reference implementation

def delegate(task, to_agent, path=()):
    if to_agent in path:
        return DEFAULT_OWNER.run(task) if DEFAULT_OWNER not in path else human_queue.put(task)
    result = AGENTS[to_agent].run(task)
    if result.status == "delegate":
        return delegate(task, result.target, path + (to_agent,))   # path tracked, no revisits
    return result
Key takeaway

Every task needs an owner when nobody else wants it.

8.13

Maker and checker agents share the same permissions and model

ReliabilitySecurityFinTech

Problem statement

A bank replaces a maker-checker process for payment releases with two agents: one prepares payments, one approves them. Both use the same model, prompt style and credentials. The checker approves 99.7% of what the maker prepares, including a batch with a duplicated supplier invoice.

The anti-pattern

Same-model maker and checker agents.

Think of it this way: The same person signing a cheque twice and calling it dual control.

Why the current design fails

  • The checker shares the maker's blind spots.
  • Both have release permissions.
  • Separation of duties exists only on paper.

Root cause: Agents imitating a control without independence.

Where it breaks: Control design.

Recommended solution

  1. Make the checker independent (deterministic rules such as duplicate detection, limits and payee checks, plus a different model with the source data).
  2. Keep release permission with a human for payments above thresholds.
  3. Audit checker approval rates and disagreements.

Why it succeeds

Trade-off to manage: More human involvement for large payments.

How you prove it worked:

  • Checker approval rate; duplicates found after release.

Same pattern elsewhere: Telco: a change-implementation agent and a change-review agent with the same model approve a faulty router configuration.

Reference implementation

def check_payment(batch):
    rule_hits = duplicate_check(batch) + limit_check(batch) + payee_check(batch)   # deterministic
    narrative = checker_llm(model=DIFFERENT_FAMILY).review(batch.summary)          # independent model
    verdict = "reject" if rule_hits or narrative.issues else "approve"
    audit.log("checker", batch=batch.id, verdict=verdict, maker_agreed=(verdict == batch.maker_verdict))
    if batch.total > RELEASE_THRESHOLD:
        return human_release_queue.put(batch, checker=verdict)   # humans release large payments
    return verdict
Key takeaway

Two copies of the same agent aren't dual control.

8.14

Two parallel agents provision the same line

ReliabilityTelco

Problem statement

To speed up a family-plan change, a carrier runs agents in parallel per line. A shared-data add-on applies to the whole account, and two agents each add it. The account gets two add-ons and double charges.

The anti-pattern

Parallel agents on a shared resource.

Think of it this way: Two waiters taking the same table's order and both sending it to the kitchen.

Why the current design fails

  • Parallel work on shared resources.
  • No locking or idempotency at account level.
  • Task decomposition ignored dependencies.

Root cause: Parallelism without coordination on shared resources.

Where it breaks: Task planning and tools.

Recommended solution

  1. Decompose by resource ownership; account-level actions run once in a coordinator step.
  2. Use idempotency keys at the account level and locks for shared resources.
  3. Check inventory state before adding products.

Why it succeeds

Trade-off to manage: Less parallelism for shared resources.

How you prove it worked:

  • Duplicate products per account after agent runs.

Same pattern elsewhere: FinTech: two parallel agents each pay the same supplier invoice.

Reference implementation

async def provision_order(order):
    async with locks.account(order.account_id):                   # shared resource lock
        if not inventory.has_product(order.account_id, "base_plan"):
            await coordinator.add_base_plan(order.account_id, idempotency_key=f"acct:{order.account_id}:base")
    await asyncio.gather(*[line_agent.provision(l, idempotency_key=f"line:{l.id}") for l in order.lines])
Key takeaway

Parallelise independent work only.

8.15

Each agent has a budget, the system has none

ReliabilityCostFinTech

Problem statement
