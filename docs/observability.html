13.1

All dashboards green while the bot invents outage ETAs

ReliabilityLatencyTelco

Problem statement

During a regional fiber outage, a carrier's chatbot tells thousands of customers "Service will be restored by 6 pm." No such estimate existed; the NOC's restoration time was unknown. APM dashboards show 99.9% availability and normal latency the whole time. Social media catches it before the operations team does.

The anti-pattern

Classic APM only (latency, errors, CPU).

Think of it this way: A smoke detector that only checks its own battery. It reports "working" while the kitchen burns.

Why the current design fails

Mechanism: LLM failures are semantic. A hallucination returns HTTP 200.

  • Monitoring covers availability, latency and errors only.
  • A hallucination returns HTTP 200.
  • No signal measured whether answers were grounded in outage data.

Root cause: Classic APM was used as the only monitoring for a semantic system.

Where it breaks: Production monitoring.

Recommended solution

  1. Add quality signals (sampled online judge for faithfulness to tool data, refusal rate, escalation rate, thumbs-down rate) per intent.
  2. For outage intents, check that any time or credit promise appears in the incident system (TMF642 alarm or incident record) and block it otherwise.
  3. Alert on spikes in specific claims (times, money, promises) during incidents.

Why it succeeds

Trade-off to manage: Online judging costs money; sample, and run cheap rule checks on 100% of risky intents.

How you prove it worked:

  • Online faithfulness score per intent with alerts; claim-pattern monitoring.

Same pattern elsewhere: FinTech: a bank bot tells customers a payment outage will be fixed "within the hour" during a core-banking incident with no ETA.

Reference implementation

CLAIM = re.compile(r"(\b\d{1,2}(:\d{2})?\s?(am|pm)\b|\$\d+|credit|back up by)", re.I)

def guard_outage_reply(reply, account):
    if CLAIM.search(reply):
        inc = tmf642.incident_for(account.service_id)
        if not inc or not claims_match(reply, inc.eta, inc.credit_policy):
            metrics.inc("blocked_unbacked_claim", intent="outage")
            return "We're working on the outage. I'll text you as soon as there's a confirmed restore time."
    return reply
Key takeaway

In LLM systems, 200 OK doesn't mean correct.

13.2

Wrong escrow answer cannot be reconstructed

ReliabilityFinTech

Problem statement

A borrower complains that the mortgage assistant told them their escrow shortage would be spread over 12 months, but their statement demanded a lump sum. The complaints team asks engineering what happened. Logs are split across five services with no shared id; the retrieved documents, the prompt version and the model version can't be determined.

The anti-pattern

Separate logs per service with no shared trace ID.

Think of it this way: An aircraft with no flight recorder. After an incident, everyone has a theory.

Why the current design fails

Mechanism: One answer spans retrieval, reranking, several LLM calls, and tools. Without correlation, debugging is guesswork.

  • One answer spans query rewrite, retrieval, two LLM calls and a servicing API.
  • Each service logs separately, with no correlation id.
  • Prompts and retrieved content weren't recorded.

Root cause: No end-to-end tracing with LLM-specific detail.

Where it breaks: Instrumentation.

Recommended solution

  1. Distributed tracing (OpenTelemetry plus an LLM tracing backend such as Langfuse, LangSmith or Arize Phoenix) with spans for every step.
  2. Record rendered prompt, retrieved document ids, tool inputs and outputs, model and prompt versions per span (with redaction).
  3. Show the trace id in the complaint system so any answer can be replayed.

Why it succeeds

Trade-off to manage: Storing full traces costs money and raises privacy risk; redact and set retention.

How you prove it worked:

  • Percentage of production answers with a complete trace.

Same pattern elsewhere: Telco: a customer disputes what the bot said about a device trade-in value, and the carrier can't show what the bot saw.

Reference implementation

from opentelemetry import trace
tracer = trace.get_tracer("escrow-assistant")

with tracer.start_as_current_span("answer") as root:
    root.set_attribute("prompt.version", P.version); root.set_attribute("gen_ai.request.model", MODEL)
    with tracer.start_as_current_span("retrieve") as s:
        docs = retrieve(q); s.set_attribute("retrieval.doc_ids", [d.id for d in docs])
    with tracer.start_as_current_span("generate") as s:
        out = llm(render(P, docs, q)); s.set_attribute("gen_ai.prompt", redact(render(P, docs, q)))
    complaints.attach_trace_id(case_id, root.get_span_context().trace_id)
Key takeaway

Every answer should be replayable from its trace.

13.3

Two thousand thumbs-down clicks with no trace

ReliabilityTelco

Problem statement

A carrier's app assistant collects thumbs-up and thumbs-down. After a quarter, there are 2,000 negative votes in an analytics table, keyed only by timestamp and app session. None can be linked to the specific answer, prompt or retrieved content, so none can be turned into fixes or eval cases.

The anti-pattern

Feedback stored in a separate table without a trace ID.

Think of it this way: A suggestion box full of notes that say "this was bad" with no indication of what "this" was.

Why the current design fails

Mechanism: Feedback without context can't be diagnosed or turned into eval cases.

  • Feedback and traces live in different systems with no shared key.
  • Triage is impossible without the context.
  • The best source of eval cases is wasted.

Root cause: Feedback events don't carry the trace id.

Where it breaks: Instrumentation and data model.

Recommended solution

  1. Return a trace id with every response and attach it to feedback events.
  2. Build a triage queue of negative-feedback traces, reviewed weekly.
  3. Turn confirmed failures into eval cases.

Why it succeeds

Trade-off to manage: Few users leave feedback; combine explicit votes with implicit signals (rephrasing, escalation).

How you prove it worked:

  • Share of feedback events linked to a trace.

Same pattern elsewhere: FinTech: a bank's thumbs-down data can't be tied to the answer that caused it, so complaints about wrong fee information go unfixed.

Reference implementation

@app.post("/chat")
def chat(req):
    with tracer.start_as_current_span("chat") as span:
        reply = assistant(req.message)
        return {"reply": reply, "trace_id": format(span.get_span_context().trace_id, "032x")}

@app.post("/feedback")
def feedback(f: Feedback):                       # {"trace_id": ..., "rating": "down", "comment": ...}
    store.save(f)
    if f.rating == "down":
        triage_queue.put(f.trace_id)             # weekly review → confirmed failures become eval cases
Key takeaway

Feedback is only useful when it points to a trace.

13.4

Average latency hides 40-second dispute answers

ReliabilityLatencyFinTech

Problem statement

A card issuer's dispute assistant averages 2.1 seconds per answer, well within its target. But 5% of customers, mostly those with several disputed transactions, wait over 40 seconds, and many abandon the chat and call. The team only charts the mean.

The anti-pattern

Mean-based dashboards and alerts.

Think of it this way: A bus company saying the average wait is 5 minutes, ignoring the stop where people wait an hour.

Why the current design fails

Mechanism: LLM latency has long tails (long outputs, retries, agent loops).

  • LLM latency has a long tail (long outputs, retries, multi-tool runs).
  • Means smooth over the tail.
  • Alerts never fire.

Root cause: Mean-based dashboards and alerts.

Where it breaks: Metrics and SLOs.

Recommended solution

  1. Track and alert on p95 and p99, time to first token and per-step latency.
  2. Track output token length distributions, which drive the tail.
  3. Break down latency by intent and complexity (number of transactions).

Why it succeeds

Trade-off to manage: Percentiles need histogram metrics, which cost a bit more to store.

How you prove it worked:

  • SLO on p95 latency per intent, with an error budget.

Same pattern elsewhere: Telco: a bill-explanation bot's average looks fine, but multi-line family accounts wait 30+ seconds.

Reference implementation

13.5

One MVNO tenant burns the monthly LLM budget in a week

ReliabilityCostTelco

Problem statement

A carrier offers its AI care assistant to MVNO partners as a white-label service. One MVNO integrates it into an automated workflow that calls it in a loop. The carrier only sees cost on the provider's monthly invoice. By then the MVNO has used $60k of tokens, against a $15k monthly budget for all tenants.

The anti-pattern

Cost tracked only from the provider's monthly bill.

Think of it this way: A shared office phone with no per-desk billing. You find out who called abroad when the bill arrives.

Why the current design fails

Mechanism: One runaway agent, prompt bug, or abusive tenant can burn the budget in days.

  • Cost is tracked from the invoice, not in real time.
  • No per-tenant quotas or attribution.
  • Automated misuse is invisible until month end.

Root cause: No cost observability at the request level.

Where it breaks: Gateway and metering.

Recommended solution

  1. Meter tokens and cost per request, feature, tenant and user, in real time, via an LLM gateway.
  2. Set per-tenant quotas and rate limits, with budget alerts at 50%, 80% and 100%.
  3. Bill or charge back tenants from the same meter.

Why it succeeds

Trade-off to manage: Hard quotas can block legitimate peaks; use soft limits with alerts plus hard caps.

How you prove it worked:

  • Daily cost per tenant against forecast; anomaly detection on call rates.

Same pattern elsewhere: FinTech: a bank's API partner in an embedded-finance programme triggers runaway calls to the bank's AI document checker.

Reference implementation

@gateway.middleware
def meter(req, call_next):
    if spend.month_to_date(req.tenant) >= quota[req.tenant]:
        raise QuotaExceeded(req.tenant)
    resp = call_next(req)
    usd = price(req.model, resp.usage)
    spend.add(tenant=req.tenant, feature=req.feature, user=req.user, usd=usd)   # same meter drives chargeback
    for pct in (0.5, 0.8, 1.0):
        if crossed(req.tenant, pct): alert(owner(req.tenant), f"{int(pct*100)}% of monthly AI budget")
    return resp
Key takeaway

Tokens are money, so meter them like money.

13.6

Tax-season questions drift outside what the bot knows

ReliabilityFinTech

Problem statement

A bank's assistant was built around everyday banking. Each January to April, questions about tax forms (1099-INT, corrected forms, mortgage interest statements) rise to 20% of traffic. Answer quality drops, but nobody sees it, because outputs are not monitored by topic and the overall score is averaged over the year.

The anti-pattern

Static dashboards, no baselines.

Think of it this way: A shop that doesn't notice its customers have changed from tourists to locals and keeps stocking postcards.

Why the current design fails

Mechanism: Query mix, documents, and model behavior shift gradually.

  • Input mix shifts with seasons, product launches and events.
  • No baseline for topics or retrieval scores.
  • Annual averages hide seasonal problems.

Root cause: No drift detection on inputs or retrieval.

Where it breaks: Monitoring.

Recommended solution

  1. Cluster query embeddings and track cluster shares against a baseline; alert on new or growing clusters.
  2. Track retrieval-score distributions and abstain rates per cluster.
  3. Pre-load seasonal content and eval cases before known seasons.

Why it succeeds

Trade-off to manage: Clustering produces noise; review the top movers only.

How you prove it worked:

  • Weekly drift report of new topic clusters.

Same pattern elsewhere: Telco: each September, a new flagship phone launch shifts traffic to trade-in and pre-order questions.

Reference implementation

def drift_report(window_days=7):
    recent = embed_queries(logs.last(days=window_days))
    labels = kmeans_baseline.predict(recent)
    share = Counter(labels); base = baseline_share
    new_clusters = [c for c in share if share[c] / len(labels) > 2 * base.get(c, 0.005)]
    abstain = {c: abstain_rate(cluster=c) for c in new_clusters}
    if new_clusters:
        alert("query drift", clusters=describe(new_clusters), abstain=abstain)
Key takeaway

Watch the inputs, not just the outputs.

The anti-pattern

Logging tool calls without the reasoning and context that led to them.

Why the current design fails

Mechanism: Post-incident review and compliance need the decision path.

  • Tool calls are logged without inputs, reasoning or context.
  • Customer instructions and the agent's interpretation are lost.
  • Compliance and complaint handling need the decision path.

Root cause: Action logging without decision context.

Where it breaks: Tracing and audit logging.

Recommended solution

  1. Record per step the model input (redacted), the model's stated plan or rationale where available, the tool chosen, arguments and result.
  2. Keep an immutable audit log for every write action, linked to the conversation and customer confirmation.
  3. Require explicit confirmation for destructive actions and record it.

Why it succeeds

Trade-off to manage: Detailed audit logs are sensitive data; restrict access and set retention.

How you prove it worked:

  • Audit completeness checks on write actions.

Same pattern elsewhere: FinTech: a bank agent closes a savings account and the bank cannot show what the customer asked for.

The anti-pattern

Observing only the LLM call.

Why the current design fails

Mechanism: Retrieval is often the root cause.

  • Only the LLM call is observed.
  • Retrieval returned zero or low-score results silently.
  • The model filled the gap from training data.

Where it breaks: Instrumentation.

Recommended solution

  1. Log retrieved doc ids, scores and result counts per request.
  2. Alert on zero-result rate and on drops in top-score distributions per collection.
  3. Health-check each index shard (document count against expected).

Why it succeeds

Trade-off to manage: Per-request retrieval logs add storage; aggregate them to metrics and keep samples.

How you prove it worked:

  • Zero-result and low-score rates by collection.

def logged_retrieve(q, collection):

Problem statement

How you prove it worked:
