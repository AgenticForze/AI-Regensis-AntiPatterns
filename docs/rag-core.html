3.1

Naive top-k vector search with no hybrid retrieval

Quality

Problem statement

A telecom support assistant gets the query "error E-4021 on router model AX3000". Vector search returns generic router-troubleshooting articles, not the one KB article that mentions E-4021.

The anti-pattern

The retrieval stack is one dense vector query with a fixed k=5. No keyword search, no metadata filters, no fallback.

Why the current design fails

  • Dense vectors are bad at exact matching. Error codes, product SKUs, names and acronyms are spread out across embedding space.
  • Recall ceiling. If the right document isn't in the top 5, no prompt engineering can recover it.
  • No structure. Questions with obvious filters ("for AX3000 only", "policies in effect in 2026") ignore that structure entirely.

Recommended solution

Use hybrid retrieval with fusion:

  • Run BM25/keyword and dense retrieval in parallel over the same chunks. Most enterprise search engines (OpenSearch, Elasticsearch, Azure AI Search, Vertex AI Search, pgvector with full-text) support this natively.
  • Merge with Reciprocal Rank Fusion (RRF), which needs no score calibration between the two systems.
  • Extract structured filters from the query (product model, date range, region) with a small LLM call or rules, and apply them as metadata filters.
  • Retrieve wide (k=30–50), then narrow with a reranker (next pattern).

Why it succeeds

Lexical retrieval catches exact identifiers and rare terms, and dense retrieval catches paraphrases and concepts. RRF combines them robustly. Retrieving wide raises the recall ceiling, and filters remove noise before ranking. In published benchmarks and in practice, hybrid retrieval consistently beats either method alone on enterprise corpora.

Reference implementation

def rrf(rank_lists, k=60):
    scores = defaultdict(float)
    for ranks in rank_lists:
        for r, doc_id in enumerate(ranks):
            scores[doc_id] += 1 / (k + r + 1)
    return sorted(scores, key=scores.get, reverse=True)

def hybrid_retrieve(query, user):
    filters = extract_filters(query)                    # {"product": "AX3000"} via small LLM / regex
    flt = acl_filter(user) | filters
    lexical = bm25.search(query, filter=flt, k=50)
    dense   = vectors.search(embed(query), filter=flt, k=50)
    fused   = rrf([[h.id for h in lexical], [h.id for h in dense]])[:50]
    return rerank(query, fetch(fused))[:6]
Key takeaway

Hybrid retrieval is the production baseline. Dense-only search fails on precisely the identifiers enterprise users care about most.

3.2

No reranking stage

QualityCost

Problem statement

A legal research assistant retrieves 20 chunks and passes them all to the LLM. Answers are verbose, sometimes cite marginally related cases, and token costs are three times the forecast.

The anti-pattern

First-stage retrieval scores (cosine similarity) are taken as final relevance. Either everything retrieved is sent to the model, or a small k is used and good results are cut off.

Why the current design fails

  • Bi-encoder similarity is coarse. It compares query and document vectors computed independently, and misses fine-grained relevance.
  • Precision/recall trade-off with no escape. Small k loses recall; large k floods context with noise, raising cost and hallucination risk.
  • Noisy context degrades answers. Irrelevant passages distract the model and dilute citations.

Recommended solution

Add a two-stage retrieve-then-rerank pipeline:

  • Stage 1 (cheap, wide): hybrid retrieval returns 30–100 candidates.
  • Stage 2 (precise, narrow): a cross-encoder reranker (Cohere Rerank, Voyage, BGE-reranker, or the managed rankers in Bedrock, Vertex or Azure AI Search) scores each query–passage pair jointly.
  • Keep the top 3–8, and drop anything under a calibrated relevance threshold even if that leaves fewer.
  • Measure precision@k and answer faithfulness before and after.

Why it succeeds

Cross-encoders read query and passage together, so they capture relevance that vector similarity misses. The pipeline gets recall from the wide stage and precision from the narrow one. Smaller, cleaner context reduces token cost and gives the generator fewer distractors. That shows up as better faithfulness and shorter, better-cited answers.

Reference implementation

def rerank(query, candidates, top_n=6, min_score=0.35):
    scored = reranker.score(query=query, documents=[c.text for c in candidates])  # cross-encoder
    ranked = sorted(zip(candidates, scored), key=lambda x: x[1], reverse=True)
    return [c for c, s in ranked[:top_n] if s >= min_score]

ctx = rerank(q, hybrid_retrieve(q, user, k=60))
if not ctx:
    return abstain(q)              # see "answering when retrieval is empty"
Key takeaway

Retrieve wide and cheap, rerank narrow and precise. A reranker is usually the highest-ROI single upgrade to a RAG system.

3.3

Stuffing the context window ("lost in the middle")

QualityCostLatency

Problem statement

With million-token context windows available, a team skips retrieval and loads an entire 600-page procurement manual into every request. Answers miss details from the middle of the document, latency is high and the monthly bill is a surprise.

The anti-pattern

"Long context replaces RAG." Whole documents, or dozens of chunks, are concatenated into the prompt in arbitrary order, on every turn.

Why the current design fails

  • Position bias. Models attend unevenly across very long inputs and often under-use information buried mid-context.
  • Cost scales with every call. Paying for hundreds of thousands of input tokens per question is rarely justified.
  • Latency. Time-to-first-token grows with input length.
  • Diluted grounding. Citations become vague when everything is in context.

Recommended solution

Engineer the context deliberately:

  • Retrieve and rerank to a small token budget (often 2–8K tokens of evidence).
  • Order evidence: place the most relevant passages at the start and end, and group passages from the same document.
  • Compress: extract only the relevant sentences from long passages, or summarize low-ranked passages.
  • Use long context where it genuinely fits, such as whole-document analysis or contract comparison, and pair it with prompt caching so the stable document prefix isn't re-billed in full on every turn.
  • Track tokens per answer as a cost KPI.

Why it succeeds

Focused context gives the model fewer distractors, so answers are more faithful and citations precise. Token cost and latency fall roughly with input size. Caching makes legitimate long-context use affordable. The design uses long context as a tool for specific jobs rather than a substitute for retrieval.

Reference implementation

def build_context(query, passages, budget_tokens=6000):
    passages = rerank(query, passages, top_n=12)
    passages = [compress(query, p) if tokens(p) > 800 else p for p in passages]   # sentence extraction
    ordered  = passages[0::2] + passages[1::2][::-1]          # strongest at both edges
    ctx, used = [], 0
    for p in ordered:
        if used + tokens(p) > budget_tokens: break
        ctx.append(f"<source id='{p.doc_id}#{p.chunk}'>{p.text}</source>"); used += tokens(p)
    return "\n".join(ctx)

# Long-document analysis path: cache the document prefix, vary only the question
llm.generate(system=[{"text": manual_text, "cache": True}], user=question)
Key takeaway

Context is a budget, not a bucket. Long windows are great for whole-document tasks, but retrieval plus ordering plus caching beats stuffing on cost, latency and accuracy.

3.4

No query rewriting or decomposition for multi-hop questions

Quality

Problem statement

A wealth-management assistant is asked "How did our ESG fund's fees compare to the market average the year after the new SEC rule?" The answer is vague, because no single chunk contains all of that.

The anti-pattern

The user's raw question, conversational context and all, is embedded and searched once. Follow-ups such as "and what about the bond fund?" are searched without the earlier context.

Why the current design fails

  • Multi-hop questions need several facts from different documents (which rule, which year, fund fees, market average). One query embedding can't point at all of them.
  • Conversational references ("it", "that fund", "the year after") carry no meaning without the history.
  • Vocabulary mismatch. Users say "fees", documents say "total expense ratio".

Recommended solution

Insert a query-understanding step before retrieval:

  • Condense: rewrite the latest turn plus history into a standalone question.
  • Decompose: for complex questions, have a small model produce sub-queries with dependencies (find the rule date → find fee data for the next year → find the market benchmark).
  • Expand: add domain synonyms or a hypothetical answer passage (HyDE) to bridge vocabulary gaps.
  • Retrieve per sub-query (in parallel where independent), then synthesize with citations per fact.
  • Route simple questions straight through, so you only pay for decomposition when it's needed.

Why it succeeds

Each sub-query is focused, so it lands on the right evidence. Standalone rewriting fixes conversational reference failures, which are among the most common in chat logs. Routing keeps latency and cost low for the majority of simple questions. Per-fact citations make the composed answer auditable.

Reference implementation

PLAN = """Rewrite the question as standalone using the history, then split it into the
minimal ordered sub-questions needed. Return JSON: {"standalone": str, "steps": [{"q": str, "depends_on": [int]}]}"""

def answer(question, history):
    plan = small_llm.json(PLAN, history=history[-6:], question=question)
    if len(plan["steps"]) <= 1:
        return rag(plan["standalone"])
    facts = {}
    for i, step in enumerate(plan["steps"]):                # resolve dependencies in order
        q = fill(step["q"], {d: facts[d] for d in step["depends_on"]})
        facts[i] = rag(q, return_evidence=True)
    return synthesize(plan["standalone"], facts)            # cites per-fact sources
Key takeaway

Users don't write search queries, they ask compound questions in conversation. Rewrite, decompose and route before you retrieve.

3.5

Answering when retrieval returns nothing relevant

QualityCompliance

Problem statement

A benefits assistant is asked about a dental plan the company doesn't offer. Nothing relevant is retrieved, yet the assistant confidently describes coverage limits, which it invented from general knowledge.

The anti-pattern

Whatever is retrieved, even low-relevance or empty results, goes into the prompt, and the model is always expected to answer. There's no notion of "insufficient evidence".

Why the current design fails

  • Hallucination fills the gap. Models are trained to be helpful, and with weak context they fall back on general knowledge that may not apply to this company.
  • Confident tone. Users can't tell grounded answers from invented ones.
  • Liability. In HR, legal, medical or financial contexts, a fabricated answer can create real obligations or harm.

Recommended solution

Make abstention a first-class path:

  • Gate on evidence: if no passage passes the reranker threshold, don't generate a substantive answer.
  • Instruct and test the generator to answer only from provided sources, and to say what's missing when evidence is partial.
  • Return a helpful fallback, such as clarifying questions, related topics that are covered, or a hand-off to a human or ticket.
  • Run a post-generation groundedness check for high-risk domains.
  • Track abstention rate and "false abstention" as quality KPIs. Spikes reveal content gaps worth filling.

Why it succeeds

The system no longer has to choose between silence and invention. Users learn that answers come with evidence, which builds trust. Abstention logs become a prioritized content backlog. Risk teams get a measurable control rather than a promise that the model will behave.

Reference implementation

def grounded_answer(q, user):
    ev = rerank(q, hybrid_retrieve(q, user), min_score=0.4)
    if not ev:
        metrics.inc("abstain.no_evidence"); gaps.log(q)
        return Answer(text="I couldn't find this in the approved policy documents.",
                      suggestions=related_topics(q), handoff=ticket_link(q))
    draft = llm.generate(SYSTEM_GROUNDED, sources=ev, question=q)
    check = groundedness_judge(draft, ev)                 # claims supported by sources?
    if check.unsupported_claims:
        draft = llm.revise(draft, remove=check.unsupported_claims)
    return Answer(text=draft, citations=cite(ev))
Key takeaway

"I don't know, here's who does" is a feature. Design and measure abstention instead of letting the model improvise.

3.6

Adding a reranker to fix a recall problem

QualityCost

Problem statement

The team added a state-of-the-art reranker, but answer accuracy barely moved. The next proposal is an even bigger reranker.

The anti-pattern

A retrieval upgrade is bought before diagnosing which stage fails. A reranker is applied to a problem that lives in stage 1.

Why the current design fails

  • A reranker can only reorder what stage 1 retrieved. If the right chunk isn't in the candidate pool, reranking can't help.
  • Without recall@50 vs recall@5, nobody knows whether the problem is recall, precision or generation.
  • Money and latency go to the wrong stage, and the real fix (chunking, hybrid search, query rewriting) waits.

Recommended solution

Require a diagnosis before investment. Every retrieval change proposal states which failure it targets:

  • recall@50 low → recall problem: fix chunking, hybrid search or query rewriting.
  • recall@50 high, recall@5 low → precision problem: improve reranking.
  • both high but answers wrong → generation or context problem.

Why it succeeds

Investment goes to the stage that is actually failing. The three-way diagnosis takes minutes on a golden set and prevents expensive changes that can't help.

Reference implementation

def diagnose(golden, retrieve_pool, rerank_top, k_pool=50, k_top=5):
    pool = recall_at_k(retrieve_pool, golden, k_pool)
    top = recall_at_k(lambda q, k: rerank_top(q, retrieve_pool(q, k_pool), k), golden, k_top)
    if pool < 0.85:
        return f"RECALL problem (recall@{k_pool}={pool:.2f}): fix chunking/hybrid/query rewriting"
    if top < pool - 0.10:
        return f"PRECISION problem ({top:.2f} vs pool {pool:.2f}): improve reranking"
    return "Retrieval OK: look at context shaping and the generation prompt"
Key takeaway

A reranker can't promote a chunk that never arrived. Diagnose recall vs precision vs generation before buying a fix.

3.7

Hand-tuned score fusion for hybrid search

QualityReliability

Problem statement

Search quality drifts every few weeks, and someone re-tunes the weights that combine BM25 and vector scores.

The anti-pattern

Raw cosine and BM25 scores are combined linearly with hand-picked weights (0.7 × dense + 0.3 × bm25).

Why the current design fails

  • The two score scales shift as the corpus, document lengths and query mix change.
  • The weights encode one moment's data and silently go stale.
  • Re-tuning is a recurring manual chore that depends on one engineer's intuition.

Recommended solution

  • Standardize on Reciprocal Rank Fusion (RRF) as the platform default, because it uses ranks and needs no calibration.
  • Allow weighted fusion only when an ablation shows a durable gain, with weights re-validated automatically in the nightly eval.
  • Make fusion a measured platform setting rather than a per-engineer tweak.

Why it succeeds

Rank-based fusion is robust to score drift, so quality no longer degrades between tuning sessions. The nightly comparison flags the rare case where weighted fusion is worth it.

Reference implementation

def rrf(rankings: list[list[str]], k: int = 60, weights=None) -> list[str]:
    weights = weights or [1.0] * len(rankings)
    scores = {}
    for w, ranking in zip(weights, rankings):
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + w / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

@schedule(cron="0 3 * * *")
def fusion_check():
    gap = evaluate(fusion="weighted") - evaluate(fusion="rrf")
    if gap > 0.02: alert(f"weighted fusion beats RRF by {gap:.3f}; review weights")
Key takeaway

Fuse rankings, not raw scores. RRF needs no calibration and doesn't go stale as the corpus changes.

Follow-up to expect

3.8

Reranking without a latency budget

LatencyQuality

Problem statement

After adding reranking, p95 latency went from 1.2 s to 3.8 s and users complain. The proposal is to remove the reranker.

The anti-pattern

A new stage is added with no latency budget, so there's no agreed point at which quality gains stop being worth the wait.

Why the current design fails

  • Removing the stage throws away the quality gain; keeping it unchanged hurts adoption.
  • Every stage expands to fill the time it's given, with no owner for the end-to-end number.
  • The reranker runs on every query, even where stage 1 is already confident.

Recommended solution

Set an end-to-end latency SLO with the product owner (for example p95 under 2 s to first token) and give each stage a budget. Then optimize the reranker inside its budget:

  • Fewer candidates (find the knee on the eval curve).
  • A smaller or distilled model, GPU batching and score caching.
  • Adaptive reranking that skips the step when stage-1 results are already confident.
  • Stream the answer to cut perceived latency.

Why it succeeds

The quality gain stays, and latency fits the SLO. Adaptive skipping removes reranking cost from the easy majority of queries, and per-stage budgets give every component an owner and a limit.

Reference implementation

def adaptive_rerank(query, cands, scores, gap=0.15, keep=8):
    # skip reranking when stage 1 is already confident: top-1 clearly ahead of top-2
    if len(scores) > 1 and scores[0] - scores[1] > gap:
        metrics.incr("rerank.skipped")
        return cands[:keep]
    with timer("rerank_ms", budget_ms=250):
        return rerank(query, cands[:40], keep=keep)      # 40 = knee from the eval curve
Key takeaway

Every stage needs a latency budget. Optimize the reranker inside its budget instead of choosing between quality and speed.

Follow-up to expect

3.9

Every query gets every query transformation

CostLatency

Problem statement

Each query now runs a rewrite, four multi-query variants and HyDE. Quality rose 3 points; cost rose 5×.

The anti-pattern

The heaviest retrieval pipeline is applied uniformly to every query, including the many that were already easy.

Why the current design fails

  • Most of the gain usually comes from a minority of hard queries, but every query pays full price.
  • Latency rises for simple questions that needed none of it.
  • Cost per query hides that cost per correct answer barely improved for most traffic.

Recommended solution

Route by difficulty:

  • Always do the cheap, high-value step (standalone rewrite in chat).
  • Trigger multi-query, HyDE or decomposition only when a cheap signal says retrieval is weak: low top rerank score, short or vague query, multiple entities.
  • Measure quality and cost per route, and report cost per correctly answered question rather than cost per query.

Why it succeeds

Hard queries still get the full treatment, so most of the quality gain is kept, while the easy majority runs at baseline cost and latency.

Reference implementation

def smart_retrieve(q, history):
    q1 = standalone_rewrite(q, history) if history else q          # always, cheap
    cands = hybrid(q1, k=50)
    top = rerank(q1, cands, keep=8)
    if top[0].score >= 0.5 and len(q1.split()) > 3:
        return top                                                   # easy path (most traffic)
    metrics.incr("retrieval.escalated")
    variants = multi_query(q1, n=3) + [hyde(q1)]
    pool = rrf([ids(cands)] + [ids(hybrid(v, k=50)) for v in variants])[:80]
    return rerank(q1, [chunk(i) for i in pool], keep=8)
Key takeaway

Spend retrieval effort where it changes the answer. Route by difficulty and report cost per correct answer.

Follow-up to expect

Quality rose 3 points, cost rose 5×. Is that a good trade?

3.10

Shipping bundled retrieval upgrades with no ablation

QualityCost

Problem statement

In one release the team added contextual chunks, multi-query, a new reranker and compression. Quality went up 6 points. Nobody can say which change mattered.

The anti-pattern

Several retrieval changes ship together and are evaluated only as a bundle.

Why the current design fails

  • Bundled changes can't be attributed, so you can't remove the ones that only add cost.
  • When one later regresses, there's no baseline to isolate it.
  • The team learns nothing reusable for the next project.

Recommended solution

Make ablation studies part of the definition of done for retrieval changes:

  • One change per experiment, or a leave-one-out matrix for bundles.
  • All on the same golden set, reporting quality, latency and cost.
  • Publish results in a shared experiment log so other teams reuse findings.

Why it succeeds

Each component has to justify its latency and cost, so dead weight is removed. The experiment log turns one team's results into platform knowledge.

Reference implementation

STAGES = ["contextual_chunks", "multi_query", "reranker_v2", "compression"]

def leave_one_out(build_pipeline, golden):
    full = evaluate(build_pipeline(set(STAGES)), golden)
    print("full", full)
    for s in STAGES:
        r = evaluate(build_pipeline(set(STAGES) - {s}), golden)
        print(f"without {s:<18} quality {r['quality'] - full['quality']:+.3f}  "
              f"p95 {r['p95_ms'] - full['p95_ms']:+.0f} ms  cost {r['cost'] - full['cost']:+.4f}")
Key takeaway

If you can't say which change mattered, you can't keep the good ones and drop the expensive ones. Ablate every retrieval change.

Follow-up to expect

Quality went up 6 points after four changes shipped together. Which change mattered?

3.11

Fixed-size chunking splits the roaming tariff table

QualityComplianceTelco

Problem statement

A mobile operator launches a GenAI care assistant in its app and IVR that answers from rate-plan guides and roaming tariff PDFs. A customer on the Unlimited Elite plan asks "How much is data in Mexico?" and is told it is included. Mexico is Zone 2 for that plan, billed at $2/MB after 5 GB. The customer returns from a week in Cancun to a $1,400 bill, opens a dispute, and the case ends up in a regulator complaint queue.

The anti-pattern

Every document is cut into 512-token chunks regardless of structure.

Think of it this way: A roaming tariff is an airline fare grid: cities down the side, fare classes across the top. Cut the grid into strips every few inches, hand someone the strip that says "$2/MB, 5 GB, $10/day" and ask about Mexico on Elite. They cannot know which row or column they are holding, so they guess. The LLM does the same.

Why the current design fails

Mechanism: A table row lands in one chunk and its column headers in another. The retrieved chunk has numbers with no labels, so the LLM guesses.

  • The roaming guide is a matrix of zones (rows) x plans (columns) x allowance, overage and day-pass price.
  • The splitter cuts every 512 tokens, so the plan-name header row lands in chunk 13 and the Zone 2 rates in chunk 14.
  • The query "Mexico data roaming Elite" matches chunk 14 because it mentions Mexico and data rates.
  • The LLM sees numbers with no plan labels and borrows the neighbouring Unlimited Max column, where Mexico is included.

Root cause: The bot retrieves a PDF rendering of data the BSS already holds as structured records. The product catalog and rating engine are the source of truth for price; the PDF is marketing collateral generated from them.

Where it breaks: In the ingestion pipeline and the tool layer, not the prompt. No prompt can restore a table header that is not in the context.

Recommended solution

  1. Route every price, allowance and eligibility question to a tool backed by the TMF620 Product Catalog or a rating-engine quote API. The LLM explains the number but never reads it from a PDF.
  2. Parse the remaining PDFs layout-aware (Docling, Azure Document Intelligence) and turn each table row into a self-describing line such as "Unlimited Elite, Zone 2 (Mexico, Canada), 5 GB included, then $2/MB, effective 2026-07-01".
  3. Store plan_id, zone, effective_date and channel as chunk metadata, resolve the customer's actual plan from Product Inventory (TMF637) and filter on it before retrieval.
  4. Require the answer to cite the productOffering id and effective date, and reject any currency amount that is not in the tool response.

Why it succeeds

Trade-off to manage: Tool calls add 200-400 ms and a dependency on catalog uptime. Cache by offer_id plus version, invalidate on catalog change events, and fall back to "I'll text you the exact rate" if the API is down.

How you prove it worked:

  • Golden set of about 300 plan x zone questions whose expected answers are generated from the catalog itself, run in CI on every index or prompt change.
  • Numeric-faithfulness check on 100% of price answers (regex plus comparison, so it is cheap) with an alert on any mismatch.
  • Join bot session ids to billing disputes and goodwill credits within 30 days and alert on a spike for roaming intents.

Same pattern elsewhere: FinTech: a card fee-schedule PDF lists purchase APR, cash-advance APR and FX fee by card tier. Chunking separates tier headers from rates and the bot quotes the Platinum cash-advance APR to a Classic cardholder, a misleading disclosure. Same fix: pull rates from the card product system as a tool.

Reference implementation

def get_roaming_rate(customer_id: str, country_iso: str) -> dict:
    plan = product_inventory.get_active_plan(customer_id)    # TMF637
    offer = catalog.get_offering(plan.offering_id)           # TMF620
    zone = offer.roaming_zones.lookup(country_iso)
    return {"plan": offer.name, "offer_id": offer.id, "zone": zone.name,
            "included_gb": zone.allowance_gb, "overage_per_mb": zone.overage_rate,
            "effective": offer.valid_from}

# Guardrail: every amount in the answer must exist in the tool result
assert all(a in tool_amounts for a in extract_amounts(answer))
Key takeaway

If the BSS already holds a fact as structured data, don't retrieve it from a PDF. Call the system of record, and use RAG only for the explanation around it.

General rule

Chunk by meaning, not by token count.

3.12

Vector-only search confuses chargeback reason codes

QualityFinTech

Problem statement

A card issuer gives dispute analysts a RAG copilot over Visa and Mastercard dispute rules. An analyst asks "evidence required for Visa 13.2". The copilot returns the guidance for 13.1 (merchandise not received) instead of 13.2 (cancelled recurring transaction). The analyst files the wrong evidence, the case loses at pre-arbitration, and the bank absorbs a $2,300 loss plus network fees.

The anti-pattern

Pure dense embeddings for everything.
