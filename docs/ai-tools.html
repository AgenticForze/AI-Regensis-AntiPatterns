19Claude & Other AI Tools

Frontier model APIs, agent frameworks, coding agents and workplace assistants each come with their own adoption traps. These are the ones that recur across enterprise programs.

15 anti-patterns

19.1

Claude: Large stable prompts re-sent without prompt caching

CostLatency

Problem statement

A policy-analysis agent sends a 60K-token system prompt (instructions, tool definitions and a reference handbook) with every turn. Most of each bill is for the same tokens, re-processed on every call.

The anti-pattern

Long, stable prefixes (system prompts, tool schemas, reference documents, conversation history) are sent uncached. Prompts are also structured so that volatile content comes first, which breaks any cache.

Why the current design fails

  • Repeated full-price input tokens on every turn.
  • Higher time-to-first-token from re-processing the prefix.
  • Cache-hostile prompt layout: a timestamp or user ID at the top invalidates everything after it.

Recommended solution

  • Order prompts for caching: tools → system instructions → reference documents → conversation history → the new user turn. Keep volatile values (dates, IDs) out of the prefix.
  • Mark cache breakpoints on the stable prefix, and choose cache lifetimes that match the session pattern.
  • Monitor cache-read versus cache-write tokens in usage metadata, and fix layouts that miss.
  • Combine with context compaction for long sessions, so cached history doesn't grow without limit.

Why it succeeds

Cached prefix reads are billed at a fraction of the normal input price and processed faster, so long-context agents become affordable. Watching usage metadata shows when a layout change has broken the cache.

Reference implementation

import anthropic
client = anthropic.Anthropic()

resp = client.messages.create(
    model="claude-sonnet-5-5", max_tokens=2000,
    tools=TOOLS,                                              # stable
    system=[{"type": "text", "text": SYSTEM_INSTRUCTIONS},
            {"type": "text", "text": HANDBOOK_60K,
             "cache_control": {"type": "ephemeral"}}],        # cache breakpoint on stable prefix
    messages=history + [{"role": "user", "content": f"[{today()}] {question}"}])  # volatile last

u = resp.usage
metrics.record(cache_read=u.cache_read_input_tokens, cache_write=u.cache_creation_input_tokens,
               uncached=u.input_tokens)
Key takeaway

With Claude, prompt layout is a cost decision. Put stable content first, set cache breakpoints, and check the cache-read tokens.

19.2

Claude: Reasoning effort not matched to the task

CostLatencyQuality

Problem statement

One team runs maximum extended reasoning on a ticket classifier, which is slow and expensive. Another runs complex multi-step contract-risk analysis with reasoning switched off and gets shallow answers.

The anti-pattern

Extended reasoning and effort settings are set globally (always maximum or always off) instead of per task. Teams also ask the model to "think step by step" in visible output and then parse around it.

Why the current design fails

  • Over-thinking simple tasks adds cost and latency with no quality gain.
  • Under-thinking complex tasks reduces accuracy on planning, analysis and agentic tool use.
  • Visible chain-of-thought hacks pollute outputs and complicate parsing.

Recommended solution

  • Treat effort / extended thinking as a per-task parameter, tuned on the eval suite like model choice.
  • Use low effort or no extended thinking for classification, extraction and formatting. Use higher effort for planning, complex analysis, coding and multi-step agentic work.
  • Use the platform's thinking features rather than prompt hacks, and keep reasoning out of user-facing output.
  • Track the quality/latency/cost frontier per setting.

Why it succeeds

Reasoning spend tracks task difficulty, so simple paths stay fast and cheap and hard paths get the depth they need. Tuning on evals turns a configuration guess into a measured choice.

Reference implementation

TASK_PROFILE = {                      # tuned on eval suite per task
    "classify_ticket": {"model": "claude-haiku-5-5",  "effort": "low"},
    "extract_invoice": {"model": "claude-haiku-5-5",  "effort": "low"},
    "contract_risk":   {"model": "claude-opus-5-5",   "effort": "high"},
    "agent_planning":  {"model": "claude-sonnet-5-5", "effort": "high"},
}

def run(task, payload):
    p = TASK_PROFILE[task]
    return claude_call(model=p["model"], effort=p["effort"], **payload)   # thin wrapper over the Messages API
Key takeaway

Reasoning effort is a dial, not a switch. Set it per task from eval results, low for routine work and high for planning and analysis.

19.3

Claude: Procedures pasted into every prompt instead of packaged as Skills

CostQualityScale

Problem statement

A finance team's agent prompt includes the full month-end close procedure, the house style for board reports and the Excel modelling conventions: 25K tokens, mostly irrelevant to any given request.

The anti-pattern

Organizational know-how is pasted into system prompts, copied across apps, and loaded on every call whether or not it's needed.

Why the current design fails

  • Context and cost bloat from irrelevant procedures.
  • Copy drift: each app's version of the procedure diverges.
  • No reuse or governance of institutional knowledge.

Recommended solution

Package repeatable know-how as Agent Skills: folders with a SKILL.md (instructions), plus optional scripts, templates and reference files.

  • The agent sees only a short name and description for each skill and loads the full content when a task matches (progressive disclosure).
  • Version, review and distribute skills centrally, and share them across Claude apps, Claude Code, the API and agent SDKs.
  • Put deterministic steps in bundled scripts rather than prose instructions.
  • Review third-party skills like code, since they can include executable content.

Why it succeeds

Context holds only what the current task needs, which cuts cost and improves instruction-following. One governed source of know-how serves every surface, and scripted steps make outputs repeatable.

Reference implementation

# skills/month-end-close/SKILL.md
# ---
# name: month-end-close
# description: Run the month-end close checklist and produce the variance commentary in house format.
# ---
# 1. Run scripts/pull_tb.py for the period ...
# 2. Flag variances > 5% using scripts/variance.py ...
# 3. Draft commentary following templates/commentary.md ...
#
# The agent sees only name + description until a request matches;
# then it reads SKILL.md and runs the bundled scripts in its sandbox.
Key takeaway

Institutional know-how belongs in versioned, on-demand Skills, not pasted into every prompt.

Follow-up to expect

19.4

Claude: One model tier for everything

CostLatency

Problem statement

An enterprise standardizes on the most capable Claude tier for every workload, including high-volume email tagging and simple extraction. Costs are far above plan and throughput limits are hit early.

The anti-pattern

The model tier is chosen once for the brand ("we use Opus") rather than per workload.

Why the current design fails

  • Cost and latency are driven by the top tier.
  • Capacity pressure on the most constrained tier.

Recommended solution

  • Map workloads to tiers with the eval suite: the smallest tier for high-volume, latency-sensitive simple tasks; the middle tier as the general production workhorse; the top tier for complex reasoning, difficult coding and long-horizon agents.
  • Use the top tier as an orchestrator with smaller tiers as sub-agents for parallel subtasks.
  • Combine with batch processing and prompt caching.

Why it succeeds

Cost and capacity follow task difficulty, and quality is protected because tier choice is validated by evals and backed by escalation.

Reference implementation

orchestrator = Agent(model="claude-opus-5-5", tools=[spawn_subagent])
def spawn_subagent(subtask):
    return Agent(model="claude-haiku-5-5", tools=subtask.tools, budget=Budget(steps=8)).run(subtask)
Key takeaway

Use the model family as a portfolio: small tiers for volume, the middle tier for most production work, the top tier where reasoning is the bottleneck.

Follow-up to expect

19.5

Claude: Computer use where an API exists, or without a sandbox

SecurityReliabilityCost

Problem statement

A team automates CRM data entry with a screen-driving agent that clicks through the web UI, even though the CRM has a well-documented API. It's slow, breaks when the UI changes, and runs on a developer's logged-in workstation.

The anti-pattern

GUI automation (computer use or browser agents) is used as the default integration method, running with real user sessions and no isolation.

Why the current design fails

  • Brittle and slow compared with APIs.
  • Security exposure: screen agents see everything on screen and can be steered by injected page content.
  • Over-broad access through the user's live sessions.

Recommended solution

  • Integration order: API / MCP connector → RPA with known selectors → computer use.
  • Use computer use for legacy apps with no API, exploratory or cross-application tasks, and testing.
  • Run it in isolated VMs or containers with minimal privileges, dedicated test accounts, allow-listed domains and no access to secrets.
  • Require human confirmation for submissions, payments and irreversible actions, and record sessions.

Why it succeeds

APIs give speed and reliability where they exist. Computer use fills real gaps safely, and isolation plus checkpoints contain the injection and over-access risks specific to screen-reading agents.

Reference implementation

def integrate(task):
    if (conn := connectors.find(task.system)):            # MCP / API first
        return api_agent.run(task, tools=conn.tools)
    vm = sandbox.vm(image="legacy-erp-client", network=allow_list(task.system_domains),
                    creds=vault.test_account(task.system))
    return computer_use_agent.run(task, env=vm, confirm_before=["submit", "pay", "delete"],
                                  record=True)
Key takeaway

Computer use is the integration of last resort. Use APIs and MCP first, and when you do drive a screen, do it in a sandbox with checkpoints.

Follow-up to expect

19.6

Claude: Not choosing deliberately between direct and cloud-marketplace access

ComplianceCost

Problem statement

Different business units consume Claude through the Anthropic API, Bedrock, Agent Platform and Foundry, each with different data-handling terms, feature sets and billing. Nobody can say which controls apply where.

The anti-pattern

Access routes are chosen ad hoc by each team, without comparing data residency, feature availability, commercial terms and integration with existing cloud governance.

Why the current design fails

  • Fragmented governance and spend.
  • Feature mismatch: some capabilities reach the first-party API before they reach cloud platforms, or vice versa.
  • Residency and contractual terms differ by route and region.

Recommended solution

  • Compare routes on data residency and processing regions, feature availability (newest tools and betas), identity and network integration, commercial commitments and support.
  • Standardize on a primary route. Often that's the client's primary cloud, for governance and committed-spend reasons, with the first-party API approved where specific features are needed.
  • Front all routes with one gateway for metering, guardrails and logging.

Why it succeeds

Governance applies consistently, spend counts toward the right commitments, and teams know where to go for new capabilities.

Reference implementation

CLAUDE_ROUTES = {
    "default":       {"via": "client_primary_cloud", "region": "eu", "reason": "governance + commit"},
    "early_features":{"via": "anthropic_api", "approved_for": ["internal_tools"], "reason": "feature timing"},
}
Key takeaway

Claude is available through several routes. Choose one deliberately on residency, features and governance, and meter them all through one gateway.

19.7

Frameworks: Prompts tuned to one provider's quirks with no portability layer

ReliabilityCost

Problem statement

A company's 200 prompts rely on one model family's formatting conventions and implicit behaviours. A pricing change elsewhere is attractive, but switching breaks most outputs.

The anti-pattern

Prompts, parsers and tool definitions are written against one model's undocumented habits. There are no per-model variants and no cross-model eval.

Why the current design fails

  • Vendor lock-in through prompts, even when the APIs are similar.
  • Fragile to model upgrades within the same provider too.

Recommended solution

  • Specify behaviour with schemas, examples and explicit instructions rather than relying on habits.
  • Keep per-model prompt variants in the registry where needed.
  • Maintain a cross-model eval matrix so switching is a measured decision.

Why it succeeds

Model choice becomes a commercial and quality decision instead of a migration project, and the same discipline protects against regressions from same-vendor upgrades.

Reference implementation

matrix = {(m, p): eval_suite.run(model=m, prompt=prompts.get(p, variant=m))
          for m in CANDIDATE_MODELS for p in CRITICAL_PROMPTS}
viable = [m for m in CANDIDATE_MODELS if all(matrix[(m, p)] >= TARGET[p] for p in CRITICAL_PROMPTS)]
Key takeaway

Pin behaviour with schemas and evals, not model quirks, so switching models is a measured choice.

Follow-up to expect

How long would it take your team to move a production workload to another model family?

19.8

Frameworks: The framework treated as the architecture

ReliabilityCost

Problem statement

A team adopts a heavyweight multi-agent framework for a three-step document workflow. Debugging goes through layers of abstraction, and a minor framework release breaks production.

The anti-pattern

Choosing a framework first and shaping the problem to fit it. Building on framework internals and unpinned versions.

Why the current design fails

  • Accidental complexity: abstractions hide prompts, retries and state, so behaviour is hard to see.
  • Upgrade fragility: fast-moving frameworks change APIs often.
  • Lock-in to a framework instead of to a vendor.

Recommended solution

  • Start from the problem shape (autonomy spectrum, 7.1). Use plain SDK calls for simple chains, graph frameworks for stateful workflows, and agent SDKs or managed harnesses for open-ended agents.
  • Keep prompts, state schemas and tool definitions in your own code, visible and testable.
  • Pin versions, run the eval suite on upgrades, and read changelogs.

Why it succeeds

The architecture stays understandable and debuggable, and framework upgrades become routine. If a framework is abandoned or changes direction, the core logic moves with little rework.

Reference implementation

# requirements.txt pins exact versions; upgrades go through the eval gate
# langgraph==<pinned>
# anthropic==<pinned>

# Simple chain: no framework needed
summary = llm(SUMMARIZE, doc)
facts = llm(EXTRACT, summary, schema=Facts)
memo = llm(DRAFT_MEMO, facts)
Key takeaway

Pick the lightest abstraction that fits the problem. Frameworks are dependencies to manage, not architectures to adopt.

19.9

Coding agents: Measuring adoption by seats and lines of code

AdoptionCost

Problem statement

A CIO reports "90% of developers activated AI coding tools and AI wrote 40% of our code". Delivery speed hasn't changed, change-failure rate is up, and review queues are longer.

The anti-pattern

Success is measured by license activation, suggestion acceptance and AI-generated line counts, not by delivery outcomes.

Why the current design fails

  • Vanity metrics: more code isn't more value, and it can mean more review and maintenance.
  • Bottlenecks move: faster coding exposes slow review, testing and deployment.
  • Quality risk goes unmeasured.

Recommended solution

  • Baseline DORA metrics (lead time, deployment frequency, change-failure rate, time to restore), PR cycle time and developer experience before rollout.
  • Target high-leverage workflows: test generation, migrations and upgrades, code review assistance, incident triage, documentation.
  • Measure outcomes per team, and invest in the moved bottlenecks (review capacity, CI speed).
  • Track quality signals: defect escape, rework, security findings in AI-assisted PRs.

Why it succeeds

Leadership sees whether AI improves delivery, not just usage. Targeting workflows produces visible wins, and measuring bottlenecks prevents gains being lost downstream.

Reference implementation

report = {
    "lead_time_p50_days":  compare(dora.lead_time, before=Q2, after=Q4),
    "change_failure_rate": compare(dora.cfr, before=Q2, after=Q4),
    "pr_cycle_time_hours": compare(git.pr_cycle_time, before=Q2, after=Q4),
    "ai_pr_rework_rate":   rework_rate(prs(labels=["ai-assisted"])) - rework_rate(prs(labels=["human"])),
}
Key takeaway

Measure AI coding tools by delivery outcomes (lead time, change-failure rate, rework), not by seats or lines of code.

Follow-up to expect

19.10

Coding agents: Write access to production repos and systems with no guardrails

SecurityReliability

Problem statement

A developer lets an autonomous coding agent run with broad shell permissions and cloud credentials in their environment. A misinterpreted cleanup instruction deletes a shared staging database.

The anti-pattern

Coding agents run with the developer's full credentials, unrestricted shell access and the ability to push directly, with no sandbox, permission rules or review gate.

Why the current design fails

  • Destructive commands from misunderstanding or prompt injection (via README files, issues, dependencies).
  • Credential exposure to agent context and logs.
  • Unreviewed changes reach shared branches.

Recommended solution

  • Run agents in sandboxes or devcontainers with scoped, short-lived credentials and no production secrets.
  • Configure permission rules (allowed, ask and deny lists for commands and paths) and hooks that block destructive operations.
  • Protect branches: the agent opens PRs, and humans plus CI approve.
  • Treat repository content as untrusted input, and scan for prompt-injection patterns in issues and docs the agent reads.
  • Use the enterprise admin controls of your coding tools (managed settings, audit logs, allowed MCP servers).

Why it succeeds

The agent can work quickly inside a bounded space, and mistakes stay contained and reversible. Review gates keep accountability with humans, and managed settings make the policy consistent across the organization.

Reference implementation

// Managed settings for a coding agent (illustrative; deployed org-wide by IT)
{
  "permissions": {
    "allow": ["Bash(npm test:*)", "Bash(git diff:*)", "Edit(src/**)"],
    "ask":   ["Bash(git push:*)"],
    "deny":  ["Bash(rm -rf:*)", "Bash(terraform apply:*)", "Bash(kubectl delete:*)", "Read(.env*)"]
  },
  "hooks": {"PreToolUse": [{"matcher": "Bash", "command": "./scripts/block_prod_targets.sh"}]}
}
Key takeaway

Give coding agents a sandbox, least-privilege credentials, deny rules for destructive commands, and a PR-only path to shared branches.

Follow-up to expect

How do you roll out coding-agent policies consistently across hundreds of developers?

19.11

Coding agents: No repository context or conventions files

QualityAdoption

Problem statement

Developers complain that the coding agent ignores the team's architecture, test framework and naming conventions. Every session starts with ten minutes of re-explaining.

The anti-pattern

Agents start each session with no persistent, repo-level guidance about build commands, conventions, architecture boundaries or forbidden patterns.

Why the current design fails

  • Inconsistent output that violates conventions and creates review churn.
  • Wasted time re-explaining context.
  • Unsafe defaults (wrong commands, wrong directories).

Recommended solution

  • Maintain repo context files (CLAUDE.md, AGENTS.md, .cursor/rules, Copilot instructions) with build and test commands, architecture map, conventions and do-not rules.
  • Keep them short and current, and review them like code.
  • Package recurring workflows as skills or custom commands (release notes, migrations, review checklists).
  • Measure review comments per AI-assisted PR to see whether guidance is working.

Why it succeeds

Agents start every session with the team's conventions, so output fits the codebase and reviews get faster. Context files also double as onboarding documentation for humans.

Reference implementation

# CLAUDE.md
## Build & test
- `make test` (unit), `make it` (integration, needs docker)
## Architecture
- `api/` → `services/` → `repos/`. Services never import from `api/`.
## Conventions
- Python 3.12, pydantic v2, no raw SQL outside `repos/`
## Never
- Edit `migrations/` by hand; run `make migration name=...`
Key takeaway

Coding agents are only as good as the context they start with. Codify conventions in versioned repo context files and shared skills.

19.12

Coding agents: AI-generated code shipped without security and dependency scanning

Security

Problem statement

An AI-assisted PR adds a dependency whose name was hallucinated. An attacker had registered that package name with malicious code ("slopsquatting"). Another PR introduces an injection-vulnerable query.

The anti-pattern

AI-assisted changes go through lighter review because they "look clean", and dependency additions aren't verified.

Why the current design fails

  • Hallucinated or typo-squatted packages introduce supply-chain attacks.
  • Plausible but insecure patterns (injection, weak crypto, missing authorization checks).
  • Automation complacency among reviewers.

Recommended solution

  • Run SAST, secret scanning and SCA on every PR, and block new dependencies not on an allow-list or without verified provenance.
  • Label AI-assisted PRs and track their findings.
  • Add AI-assisted security review as an extra check, never a replacement for human review.
  • Train reviewers on AI-specific failure patterns.

Why it succeeds

Supply-chain and common vulnerability classes are caught automatically, whoever wrote the code. Tracking AI-assisted findings shows whether the tools are improving or degrading security.

Reference implementation

def check_new_dependencies(diff):
    for pkg in added_packages(diff):
        meta = registry.lookup(pkg.name)
        if not meta or meta.age_days < 90 or meta.downloads_weekly < 1000:
            fail(f"Suspicious or unknown package: {pkg.name}")
        if pkg.name not in ALLOWLIST:
            require_approval("security", pkg.name)
Key takeaway

AI-generated code needs the same or a higher security bar. Scan everything and verify every new dependency.

Follow-up to expect

What is slopsquatting and how do you defend against it?

19.13

Workplace assistants: Enterprise rollout before fixing oversharing

SecurityCompliance

Problem statement

Within a week of an enterprise-wide workplace-assistant rollout, employees discover they can ask "show me salary information" and get spreadsheets from overshared SharePoint sites.

The anti-pattern

Assistants that search the organization's content with the user's permissions are switched on without first cleaning up years of over-permissive sharing.

Why the current design fails

  • The assistant makes oversharing discoverable. Permissions were always wrong, but search hid them through obscurity.
  • Reputational and legal exposure from HR, legal or M&A content.

Recommended solution

  • Run oversharing assessments (access reports, "everyone" links, broad groups) and remediate high-risk sites first.
  • Apply sensitivity labels and DLP, and exclude or restrict search on sensitive sites during remediation.
  • Roll out in phases, starting with groups whose content is well governed.
  • Monitor assistant interactions touching sensitive labels.

Why it succeeds

The assistant is safe because the data estate is. Phasing gives fast value to clean areas while remediation continues elsewhere.

Reference implementation

risky = [s for s in sites.all() if s.has_everyone_links or s.member_count > 5000 and s.label in {"Confidential", None}]
for s in sorted(risky, key=lambda s: s.sensitive_hits, reverse=True):
    remediation.queue(s, actions=["remove_everyone_links", "apply_label", "restrict_search"])
rollout.enable(groups=["finance-ops", "it"], when=lambda g: g.sites_remediated_pct >= 0.95)
Key takeaway

Workplace assistants respect permissions perfectly, including the wrong ones. Fix oversharing before switching AI on.

Follow-up to expect

19.14

Workplace assistants: Licenses with no enablement, use-case catalog or ROI tracking

AdoptionCost

Problem statement

Twenty thousand assistant licenses are purchased. After six months, weekly active usage is 18%, most prompts are "summarize this email", and renewal is in question.

The anti-pattern

Deployment is treated as an IT rollout (provision licenses, send an announcement email) rather than as change management.

Why the current design fails

  • Low adoption: users don't know what to do with a blank prompt box.
  • Shallow use produces little measurable value.
  • Shadow AI continues where the official tool feels limited.

Recommended solution

  • Build a use-case catalog per persona (sales, finance, legal, HR) with worked examples and prebuilt agents or skills.
  • Train champions in each function, and run hands-on sessions on real work.
  • Provide a sanctioned path for advanced users (custom agents, connectors) so they don't go to shadow tools.
  • Track active usage and value: time saved per workflow, survey data, business KPIs.
  • Reallocate licenses based on usage evidence.

Why it succeeds

Users learn concrete, valuable workflows, so adoption deepens. Champions spread practices peer to peer, and value tracking produces the ROI evidence that secures renewal and expansion.

Reference implementation

kpis = {
    "weekly_active_pct": active_users(7) / licensed_users(),
    "advanced_use_pct":  users_with(features=["agents", "connectors", "skills"]) / active_users(30),
    "hours_saved_month": sum(w.minutes_saved * w.runs for w in tracked_workflows) / 60,
}
reallocate(licenses, from_=inactive_users(days=60), to=waitlist_by_function())
Key takeaway

A workplace AI rollout is change management, not provisioning. Use persona playbooks, champions, sanctioned advanced paths and measured value.

Follow-up to expect

19.15

Workplace assistants: Banning AI tools with no sanctioned alternative

SecurityAdoption

Problem statement

A firm blocks public AI chat sites. Survey data later shows 45% of staff use personal accounts on their phones for work tasks, including pasting client data.

The anti-pattern

Policy is prohibition only. There's no approved tool, no guidance on data classes, and no enterprise controls such as SSO, audit, retention or DLP.

Why the current design fails

  • Shadow AI moves usage to channels with zero visibility.
  • Data leakage to consumer services with unknown retention terms.
  • Lost productivity and talent frustration.

Recommended solution

  • Provide sanctioned enterprise AI tools with SSO/SCIM, audit logs, retention controls, DLP integration and contractual terms excluding training on customer data.
  • Publish a one-page acceptable-use policy with clear data-classification rules.
  • Offer a fast intake path for new tools and use cases.
  • Monitor for shadow usage through CASB/SSE tools, and use the findings to improve the sanctioned offering.

Why it succeeds

Usage moves to governed channels because they're better and easier. Visibility returns, and data protection is enforced technically rather than by hope.

Reference implementation

AI_ACCEPTABLE_USE = {
    "public":       ["any approved AI tool"],
    "internal":     ["enterprise assistant", "approved coding agents"],
    "confidential": ["enterprise assistant (labelled workspaces)", "private-endpoint apps"],
    "restricted":   ["approved in-house apps only"],
}
Key takeaway

Banning AI without a sanctioned alternative creates shadow AI. Make the governed path the easiest one.

Follow-up to expect
