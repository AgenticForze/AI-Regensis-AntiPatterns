6.1

One frontier model for every task

CostLatency

Problem statement

A shared-services AI platform routes every request, including classification, extraction, summarization and complex reasoning, to the largest frontier model. The monthly bill reaches seven figures, and 70% of calls are simple classifications.

The anti-pattern

One model is chosen during the PoC (usually the most capable) and hardwired for every workload, regardless of complexity, volume or latency needs.

Why the current design fails

  • Cost scales with the most expensive tier. Per-token prices across model tiers commonly differ by 10–30×.
  • Latency. Larger models are slower, which hurts interactive and high-throughput flows.
  • No leverage. The organization can't respond to price changes or newer, cheaper models.

Recommended solution

Build a model portfolio with routing:

  • Classify tasks by complexity and risk. Map each to the cheapest model that passes its eval threshold.
  • Use rules first (task type), then learned routers (difficulty prediction) as volume grows.
  • Add cascades: try the small model, escalate when confidence or validation fails.
  • Use batch APIs for offline workloads, typically at a large discount.
  • Re-benchmark the portfolio quarterly as new models ship.

Why it succeeds

Most enterprise traffic is simple, so moving it to small models cuts cost dramatically while evals and escalation protect quality on hard cases. Routing also creates leverage: adopting a new model becomes a config change validated by evals rather than a re-architecture.

Reference implementation

PORTFOLIO = {
    "classify": ModelTier("small",    max_cost_per_call=0.0005),
    "extract":  ModelTier("small",    fallback="mid"),
    "summarize":ModelTier("mid"),
    "reason":   ModelTier("frontier"),
}

def call(task, payload):
    tier = PORTFOLIO[task]
    out = llm(tier.model).generate(payload, schema=SCHEMAS[task])
    if tier.fallback and (out.confidence < 0.7 or not validate(out)):
        metrics.inc(f"escalate.{task}")
        out = llm(PORTFOLIO_MODELS[tier.fallback]).generate(payload, schema=SCHEMAS[task])
    return out
Key takeaway

Treat models like a portfolio. Route each task to the cheapest model that passes its eval, and escalate only when needed.

6.2

No fallback or multi-provider strategy

Reliability

Problem statement

During a provider's regional incident, a customer-facing assistant returns errors for three hours. Rate limits during a marketing campaign cause the same outage pattern a month later.

The anti-pattern

The application calls one model endpoint in one region with naive retries. No capacity planning, no failover, no graceful degradation.

Why the current design fails

  • Single point of failure. Provider outages, regional incidents and throttling (HTTP 429) all take the product down.
  • Retry storms. Naive retries amplify load during an incident.
  • Capacity surprises. Shared on-demand quotas aren't guaranteed at peak.

Recommended solution

Put an AI gateway in front of model calls (LiteLLM, Portkey, a cloud API-management layer such as Azure APIM, or an internal gateway):

  • Exponential backoff with jitter, honouring retry-after headers.
  • Circuit breakers per endpoint.
  • Failover order: same model in another region → equivalent model from another provider or hosting route → smaller model in degraded mode.
  • Provisioned or reserved capacity for critical paths, on-demand for overflow.
  • Keep evaluated, equivalent prompts for each fallback model, since prompts don't always transfer.

Why it succeeds

Failures become partial degradation instead of outages. Circuit breakers stop retry storms, and pre-evaluated fallback prompts mean failover doesn't quietly change quality. The gateway also centralizes cost tracking, quotas and logging.

Reference implementation

ROUTES = [
    Route("claude-mid", provider="bedrock", region="us-east-1"),
    Route("claude-mid", provider="vertex",  region="us-central1"),
    Route("alt-mid",    provider="foundry", region="eastus2", prompt_variant="alt"),
    Route("small",      provider="bedrock", region="us-east-1", degraded=True),
]

def resilient_call(req):
    for r in ROUTES:
        if breaker[r.key].open: continue
        try:
            return with_backoff(lambda: client(r).generate(variant(req, r)), max_tries=2)
        except (Throttled, ServerError) as e:
            breaker[r.key].record_failure(e)
    return degraded_response(req)            # cached answer, queue, or human hand-off
Key takeaway

Models are external dependencies with SLAs. Engineer them like payment gateways, with failover, circuit breakers and a degraded mode.

Follow-up to expect

6.3

Fine-tuning too early

CostQuality

Problem statement

In week two of a document-classification project, the team starts fine-tuning on 2,000 labeled examples. Three months later the tuned model is beaten by a newer base model with a good prompt, and the tuning pipeline needs re-running for every model update.

The anti-pattern

Fine-tuning is the first resort, before prompt engineering, retrieval, few-shot examples or a proper eval baseline exist.

Why the current design fails

  • No baseline. Without an eval of prompted base models, nobody knows whether tuning helped.
  • Model churn. Base models improve every few months. Tuned weights pin you to an aging model and must be redone.
  • Data quality. Small, noisy labelled sets teach the model the noise.
  • Hidden operating cost. Custom-model hosting, provisioned capacity and retraining pipelines add up.

Recommended solution

Follow an optimization ladder and measure at each rung:

  1. Build the eval set and success threshold.
  2. Prompting with clear instructions and structured output.
  3. Few-shot examples, ideally retrieved dynamically from similar labelled cases.
  4. RAG or tools for knowledge gaps.
  5. Fine-tune or distill only if a persistent behaviour gap remains and volume justifies the lifecycle cost. Keep the training pipeline reproducible so it can be re-run on new base models.

Why it succeeds

Most use cases are solved at rungs 2–4, which are cheaper and portable across models. When tuning is justified, it's measured against a strong baseline, so the ROI is real. Reproducible pipelines turn base-model upgrades into routine retraining rather than a rebuild.

Reference implementation

ladder = [
    ("zero_shot",   lambda: Pipeline(prompt=P_BASE)),
    ("few_shot",    lambda: Pipeline(prompt=P_BASE, examples=knn_examples(k=5))),
    ("rag",         lambda: Pipeline(prompt=P_BASE, examples=knn_examples(5), retriever=kb)),
]
for name, build in ladder:
    score = eval_suite.run(build())
    report[name] = score
    if score >= TARGET: break
else:
    if monthly_volume > TUNE_THRESHOLD:
        tuned = finetune(base=CURRENT_BASE, data=clean(labelled), eval=eval_suite)
Key takeaway

Fine-tuning is the last rung of the ladder, not the first. Exhaust prompting, examples and retrieval against a baseline before you buy a model lifecycle.

6.4

Ignoring latency budgets and serving modes

LatencyCost

Problem statement

A contact-center agent-assist tool takes 11 seconds to suggest a reply. By then the human agent has already answered. Meanwhile, a nightly document-summarization job runs on expensive real-time endpoints.

The anti-pattern

Every workload uses the same synchronous, non-streaming, real-time API pattern, with no latency budget per step and no distinction between interactive and offline jobs.

Why the current design fails

  • Interactive UX breaks when time-to-first-token and total latency aren't designed for.
  • Sequential chains add up. Five serial LLM calls of two seconds each is ten seconds.
  • Offline jobs overpay on real-time pricing and compete with interactive traffic for quota.

Recommended solution

Design to an explicit latency budget:

  • Set targets per use case (for example TTFT under 800 ms, full response under 4 s for agent-assist).
  • Stream tokens to the UI and start rendering immediately.
  • Parallelize independent calls (retrieval plus classification). Use small models on the critical path.
  • Cache: prompt caching for stable prefixes, and semantic or exact caching for repeated questions.
  • Move offline work to batch inference endpoints, scheduled off-peak.
  • Track p50/p95/p99 per step in traces.

Why it succeeds

Users perceive streaming responses as fast, and parallelism plus small models cut real latency. Caching removes repeated work. Batch processing cuts offline cost and frees real-time quota for users. Per-step traces show exactly where the budget is spent.

Reference implementation

async def assist(turn):
    intent, docs = await asyncio.gather(                    # parallel, not serial
        small_llm.classify(turn.text),
        retrieve(turn.text))
    async for tok in llm.stream(model=pick(intent), context=docs, user=turn.text):
        await ui.push(tok)                                  # TTFT matters more than total time

# Offline: batch API, off-peak, much cheaper
batch_id = llm.batches.create(requests=[mk_req(d) for d in todays_documents], window="24h")
Key takeaway

Latency is a design constraint, not a tuning afterthought. Budget it per step, stream, parallelize, cache, and batch whatever isn't interactive.

6.5

No one knows what a resolved card dispute costs

CostFinTech

Problem statement

A card issuer's AI assistant costs $140k a month. Finance asks whether it pays for itself. The team can report total tokens but not cost per intent, cost per resolved dispute, or how it compares with an agent-handled contact.

The anti-pattern

Only total spend is known.

Think of it this way: A restaurant that knows its total food bill but not what each dish costs to make.

Why the current design fails

  • Cost isn't attributed to intents or outcomes.
  • No comparison with the human baseline.
  • Optimisation targets are guesses.

Root cause: No unit economics.

Where it breaks: Metering and analytics.

Recommended solution

  1. Tag cost per request with intent, outcome and version, and compute cost per successful outcome by intent.
  2. Compare with fully loaded human cost per contact for the same intent.
  3. Prioritise optimisation on high-volume, low-margin intents.

Why it succeeds

Trade-off to manage: Outcome attribution needs joins to downstream systems.

How you prove it worked:

  • Cost per outcome dashboard reviewed monthly.

Same pattern elsewhere: Telco: a carrier can't tell whether its bot is cheaper than care agents for plan changes versus bill explanations.

Reference implementation

def cost_per_resolved(intent, month):
    ai = ledger.sum(intent=intent, month=month)                              # tagged per request
    resolved = outcomes.count(intent=intent, outcome="resolved", month=month)
    human_baseline = contact_center.loaded_cost_per_contact(intent)
    return {"ai_cost_per_resolved": ai / resolved, "human_cost_per_contact": human_baseline,
            "volume": outcomes.count(intent=intent, month=month)}

priorities = sorted(INTENTS, key=lambda i: -(volume(i) * (1 - margin(i))))
Key takeaway

Know the cost of a success, per intent.

6.6

Router sends hard complaints to the small model

CostFinTech

Problem statement

A bank introduces a router that sends "simple" questions to a small model and "complex" ones to a large model, based on message length. Short but serious complaints ("You closed my account and my salary bounced") go to the small model, which handles them poorly. Complaint escalations rise.

The anti-pattern

Route by message length.

Think of it this way: A hospital triaging patients by how long they talk rather than by symptoms.

Why the current design fails

  • Routing criteria don't reflect difficulty or risk.
  • The router wasn't evaluated.
  • High-risk intents can hit the cheap path.

Root cause: Unvalidated routing heuristics.

Where it breaks: Router design.

Recommended solution

  1. Route by intent and risk tier (complaints, vulnerability and disputes always to the stronger path).
  2. Evaluate the router (misroute rate) and each path per intent.
  3. Allow the small model to escalate when uncertain.

Why it succeeds

Trade-off to manage: Lower savings from routing; safer outcomes.

How you prove it worked:

  • Quality by route and intent; escalations after small-model answers.

Same pattern elsewhere: Telco: a router sends short outage complaints from business customers to a small model that can't check incident data.

Reference implementation

ALWAYS_STRONG = {"complaint", "vulnerability", "dispute", "bereavement"}

def route(msg):
    intent = router.classify(msg)
    if intent.name in ALWAYS_STRONG or intent.risk_tier == "high":
        return STRONG_MODEL
    return SMALL_MODEL

def small_with_escalation(msg):
    out = SMALL_MODEL.generate(msg, schema=WithConfidence)
    return out if out.confidence >= 0.75 else STRONG_MODEL.generate(msg)
# eval: router misroute rate + quality per path per intent
Key takeaway

Route by risk and intent, not by message length.

6.7

Voice agent pauses for 3 seconds before every reply

CostLatencyTelco

Problem statement

A carrier's AI voice agent chains speech recognition, an LLM call, a tool call and text-to-speech, each run to completion before the next starts. Callers hear 3 seconds of silence after every sentence and assume the line dropped.

The anti-pattern

Sequential voice pipeline.

Think of it this way: A conversation where the other person waits until they've written their whole reply before saying a word.

Why the current design fails

  • No end-to-end latency budget.
  • Stages run sequentially without streaming.
  • Tool calls happen on the critical path.

Root cause: Voice pipeline designed without a latency budget.

Where it breaks: Voice architecture.

Recommended solution

  1. Set an end-to-end budget (for example under 800 ms to first audio) and per-stage targets.
  2. Stream ASR partials, stream LLM tokens into TTS by sentence, and use a fast model for the first response.
  3. Prefetch likely tool data (account summary) at call start; use filler acknowledgements while slow tools run.

Why it succeeds

Trade-off to manage: Streaming complicates guardrails; check per sentence.

How you prove it worked:

  • Time to first audio per turn; caller hang-ups during silence.

Same pattern elsewhere: FinTech: a bank's voice bot waits for the full balance lookup and answer before speaking.

Reference implementation

BUDGET_MS = {"asr_final": 200, "llm_first_token": 350, "tts_first_audio": 200}   # < 800 ms to first audio

async def on_call_start(call):
    call.prefetch = asyncio.create_task(accounts.summary(call.customer_id))      # prefetch

async def on_utterance(call, partial_text):
    async for sentence in sentences(fast_model.stream(partial_text, context=await call.prefetch)):
        await tts.speak(sentence)                                                 # stream by sentence
    if needs_slow_tool(partial_text):
        await tts.speak("One moment while I check that.")                         # filler while tools run
Key takeaway

In voice, latency is the user experience.

CostLatencyFinTech

Problem statement

A bank's assistant system prompt has grown to 15k tokens covering every product. Ninety percent of conversations are about cards and balances. Each turn pays for the full prompt, and time to first token is 1.8 seconds.

The anti-pattern

One 15k-token prompt for everything.

Why the current design fails

Why it succeeds

Trade-off to manage: Intent detection must be reliable.

How you prove it worked:

6.9

Prompt caching enabled, but the cache expires between turns

CostTelco

Problem statement

A carrier enables prompt caching for its care bot. Hit rates are low because the provider's default cache lifetime is a few minutes, and customers often take longer to reply. The team assumed caching would work for whole conversations.

The anti-pattern

Assume the cache lasts the conversation.

Think of it this way: A coffee machine that switches off between cups.

Why the current design fails

  • Cache lifetime wasn't understood.
  • Traffic patterns weren't analysed.
  • Hit rate wasn't monitored.

Root cause: Caching enabled without understanding its mechanics.

Where it breaks: Caching configuration.

Recommended solution

  1. Check the provider's cache lifetime options and choose them by traffic pattern (longer lifetimes where offered and cost-effective).
  2. Keep the shared prefix identical across all customers so it stays warm from overall traffic.
  3. Monitor cached-token share.

Why it succeeds

Trade-off to manage: Longer cache lifetimes may cost more to write.

How you prove it worked:

  • Cache hit rate by time of day and conversation gap.

Same pattern elsewhere: FinTech: a bank's batch jobs run hours apart and never benefit from prompt caching.

Reference implementation

SHARED_PREFIX = CORE_PROMPT + TOOL_DEFINITIONS          # byte-identical for every customer

def request(customer_ctx, history, msg):
    return {"system": [{"type": "text", "text": SHARED_PREFIX,
                        "cache_control": {"type": "ephemeral", "ttl": CACHE_TTL_BY_TRAFFIC}}],   # lifetime chosen by traffic
            "messages": history + [{"role": "user", "content": f"{customer_ctx}\n{msg}"}]}

metrics.gauge("cached_token_share", u.cache_read_input_tokens / (u.input_tokens + u.cache_read_input_tokens))
Key takeaway

Know how your cache expires before you count the savings.

6.10

Semantic cache confuses cancel my card with cancel my card payment

CostFinTech

Problem statement

A bank's semantic cache uses a similarity threshold of 0.88. "How do I cancel my card?" and "How do I cancel a card payment?" exceed it, so customers who want to stop a payment receive instructions for closing their card.

The anti-pattern

Similarity-only cache hits.

Think of it this way: A receptionist who answers the question they think you asked because it sounded similar.

Why the current design fails

  • Similar wording, different intents.
  • Threshold chosen without evaluation.
  • Cached answers aren't checked against the intent.

Root cause: Over-aggressive semantic caching.

Where it breaks: Cache design.

Recommended solution

  1. Tune thresholds on a labelled set of near-miss pairs, and add intent classification to the cache key.
  2. Cache only for high-volume, stable FAQ intents.
  3. Monitor negative feedback on cache hits.

Why it succeeds

Trade-off to manage: Lower hit rates.

How you prove it worked:

  • Feedback and rephrase rate on cached answers.

Same pattern elsewhere: Telco: "How do I block a number?" gets the cached answer for "How do I unblock my number?"

Reference implementation

CACHEABLE_INTENTS = {"store_hours", "how_to_activate_card", "fee_schedule_general"}

def cache_get(q):
    intent = classify(q)
    if intent not in CACHEABLE_INTENTS:
        return None
    return semantic_cache.get(q, namespace=intent, min_sim=THRESHOLD[intent])   # intent in the key

# thresholds tuned on near-miss pairs: ("cancel my card", "cancel my card payment") must NOT match
# monitor: thumbs-down rate on cache hits vs misses
Key takeaway

Similar isn't the same. Key the cache by intent.

6.11

One conversation costs $40

CostTelco

Problem statement

A carrier's agent costs about $0.08 per conversation on average. A few conversations with long troubleshooting loops and repeated tool calls cost over $40. With no per-conversation cap, outliers make up 20% of spend.

The anti-pattern

No per-conversation cost cap.

Think of it this way: An all-you-can-eat buffet with no time limit.

Why the current design fails

  • No per-conversation budget.
  • Outliers aren't monitored.
  • Long sessions grow context cost quadratically.

Root cause: No cost caps per unit of work.

Where it breaks: Runtime limits.

Recommended solution

  1. Set per-conversation and per-task budgets (tokens and dollars), with graceful handoff to a human when exceeded.
  2. Compact context in long sessions.
  3. Alert on cost outliers and review them weekly.

Why it succeeds

Trade-off to manage: Some long, legitimate sessions get handed off.

How you prove it worked:

  • Cost distribution per conversation (p99).

Same pattern elsewhere: FinTech: a few research-agent runs on complex companies cost hundreds of dollars each.

Reference implementation

class ConversationBudget:
    def __init__(self, usd=0.50, tokens=150_000): self.usd, self.tokens = usd, tokens
    def charge(self, resp):
        self.usd -= price(resp); self.tokens -= resp.usage.total_tokens
        return self.usd > 0 and self.tokens > 0

if not budget.charge(resp):
    return handoff_to_human(summary=compact(conversation))
if conversation.tokens > 40_000:
    conversation = compact(conversation)
Key takeaway

Budget each conversation, not just the month.

Problem statement

A bank's assistant averages 450 output tokens per reply, with long introductions and repeated disclaimers. Customers on mobile scroll past most of it. Output tokens cost several times more than input tokens.

The anti-pattern

No length guidance.

Why the current design fails

Recommended solution

  1. Set length guidance per intent and channel, and appropriate max output tokens.
  2. Show required disclaimers once in the UI, not in every reply.
  3. Measure output tokens and readability.

Why it succeeds

Trade-off to manage: Too short can drop needed information; evaluate.

How you prove it worked:

  • Output tokens per intent; scroll and engagement data.

LENGTH = {("balance", "chat"): 40, ("plan_compare", "chat"): 150, ("balance", "voice"): 25}   # words

def generate(intent, channel, msg):

6.14

Extended reasoning turned on for every request

CostLatencyFinTech

Problem statement

A bank switches its whole assistant to a reasoning model with a large thinking budget after it performed well on complex mortgage questions. Simple questions ("What's my sort code?") now take 9 seconds and cost 10 times more, with no quality gain.

The anti-pattern

Maximum reasoning for every request.

Think of it this way: Calling a committee meeting to decide what to have for lunch.

Why the current design fails

  • Reasoning effort applied uniformly.
  • Thinking tokens are billed and add latency.
  • Simple tasks gain nothing.

Root cause: No effort routing.

Where it breaks: Model and parameter selection.

Recommended solution

  1. Route by complexity; enable extended reasoning (or a higher effort setting) only for intents that benefit in evals.
  2. Set thinking budgets per intent.
  3. Measure quality, latency and cost per intent.

Why it succeeds

Trade-off to manage: Routing errors may under-think hard questions; allow escalation.

How you prove it worked:

  • Thinking tokens per intent.

Same pattern elsewhere: Telco: a care bot uses deep reasoning to answer "what's my balance?"

Reference implementation

REASONING = {"complaint_resolution": "high", "plan_comparison": "medium"}   # chosen from evals

def call(intent, msg):

    kwargs = {"thinking_budget": BUDGET[effort]} if effort else {}         # off by default

6.19

Retry storm doubles cost during a provider incident

CostLatencyTelco

Problem statement

During a provider slowdown, a carrier's services retry failed calls immediately up to five times, at several layers (SDK, gateway, application). Each customer message generates up to 125 attempts. The anti-pattern

Immediate retries at every layer.

Think of it this way: Everyone in a traffic jam honking harder.

Why the current design fails

  • Retries at multiple layers multiply.
  • No backoff or jitter.
  • No circuit breaker.

Where it breaks: Resilience configuration.

Recommended solution

  1. Retry in one layer only (usually the gateway) with exponential backoff and jitter.
  2. Add circuit breakers and fall back to degraded mode.

How you prove it worked:

  • Attempts per request; retry ratio during incidents.

    on_open=degraded_mode)

def nightly_index(docs):
    for doc in docs:
        for c in chunk(doc):
            h = sha256(normalize(c.text))
            if registry.hash(c.id) == h:
                continue                                   # unchanged → no embedding call
            vdb.upsert(c.id, embed(c.text), meta={"hash": h}); registry.set(c.id, h)
    for gone in registry.ids() - current_chunk_ids(docs):

    return "".join(p if p.protected else compressor.compress(p.text, ratio=0.5) for p in parts)
